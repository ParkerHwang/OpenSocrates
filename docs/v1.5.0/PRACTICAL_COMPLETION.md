# v1.5.0 practical completion and release-candidate authority

Effective 2026-09-26, by the user's explicit revised instruction. This document
governs current completion planning and supersedes earlier requirements that made
held-out studies, power calculations, numerical noninferiority margins, human
recruitment, billing/backend echoes, account-side memory isolation or broad model
superiority prerequisites for this version. Historical protocols, manifests,
artifacts, outcomes, scores and reviews remain immutable evidence of their own runs.

The objective is a usable product: adaptive assistance, useful continuity,
appropriate initiative, coding support and natural English/Korean collaboration.
Functional correctness, privacy, authority, migration, deletion and package/platform
checks remain required. Claims must match observed examples; a green build or an
emitted context pack alone is insufficient.

## Completion and authorization

The integrator owns implementation, checks, a small matched v1.4.0 comparison and
a concrete release-candidate handoff. Existing valid evidence may be reused.
Rerun changed, inadequately measured or unresolved behavior only. Normal use keeps
the working task-based fallback; model-specific profiles stay experimental when
no useful benefit is established. No hidden model or effort change is allowed.

Once functional qualification passes, version metadata, release notes, generated
assets and package artifacts may identify **1.5.0**, explicitly as a release
candidate. The feature branch may be committed/pushed and PR #95 / issue #94
updated. Keep the PR Draft. Merge, tag, publication, deployment and active-plugin
replacement still require separate explicit authority.

Use disposable projects/profiles only. Do not change global memories/settings,
enroll a real project, create credentials/services, consume a reset credit, or run
destructive account-home purge/reinstall. Record unavailable live Windows once
and narrow the support statement while completing available qualification.

The comparison uses approximately six representative scenarios, one matched
episode per version and one fixed model/effort/client. The initial ceiling is 24
model invocations including failures and every session. A 20-call design leaves
four calls for diagnosed execution failures, not discretionary score chasing.
Any later repair/retest is separately identified and narrowly scoped. Freeze task,
source state, package identities, permissions, checks and limits before calls.
Give released v1.4.0 competent instructions and the same relevant facts/tools,
including an explicitly named maintained note for continuity. Never weaken it to
manufacture a win. Report improvements, ties, regressions, failures and null usage.

## Failure register and controls

The boundary is the disposable qualification workflow and resulting candidate,
not global account lifecycle or a population-level efficacy study. Priority is
ordinal: **required** blocks this candidate until controlled; **material** needs
a bounded check and honest limitation; **claim-only** restricts a stronger claim.
The primary integrator owns every action below.

| Mode and observed basis | Effect / cause | Current control and next verification | Priority / reopening condition |
| --- | --- | --- | --- |
| Privacy, ownership or wrong-scope deletion; known risk surface, no new demonstrated defect | User data loss or leakage through unsafe state transitions | Existing native/source adversarial fixtures; inspect exact before/after scope; no real-project enrollment | Required; any boundary violation stops affected lane |
| Generated programs miss free-item shipping or seat rules; observed in old artifacts | Incorrect results escape a shallow checker | New fixture explicitly defines nonempty zero-price orders and integer seat domain; retain old outcomes | Material; new functional failure requires diagnosed repair/retest |
| Proposed text mistaken for accepted memory; observed judge error | Unsupported authority is treated as user intent | Assert lifecycle separately from summary text, and audit record/accept/delete receipts | Required for memory acceptance; accepted-state mismatch reopens |
| Questions before final text or operation receipts omitted; observed harness/packet gaps | False failure or unverifiable completion | Retain all public messages, actual artifacts, request-correlated operation receipts and persisted state in the synthetic evaluation boundary | Material; missing evidence stays missing and triggers only the necessary targeted check |
| Optional guidance fails to preserve side-question continuity; specification-to-guide gap | Main task stalls or settled permissions are reopened | Guide 5 adds equivalent EN/KO wording; practical two-stage collaboration checks | Material; an observed failure justifies a bounded guide fix |
| Profile efficacy unestablished; known limitation | Added instructions/work without demonstrated value | Keep candidate profiles out of normal routing; test task fallback | Material; no profile promotion is needed to finish |
| Missing human/billing/backend/account-isolation/statistical evidence | Broad causal or monetary claims unsupported | Preserve limitations and describe bounded examples only | Claim-only; relevant evidence reopens that claim, not all product work |

Stop once intended features are usable, required functional/safety checks pass,
the bounded comparison is honestly reported, and the candidate is reviewable.
Do not expand the matrix or commission another 60-packet review to defer completion.
