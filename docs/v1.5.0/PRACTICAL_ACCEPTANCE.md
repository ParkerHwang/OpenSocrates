# Practical acceptance for the revised product

The primary evaluates whether a non-expert user can understand the situation,
make a grounded decision, and use the resulting communication. Keep mechanical
entry correctness, complete procedure reading, final usefulness and distribution
lifecycle separate. Coding scores and statistical superiority are not release
prerequisites for this scope.

First compare the released core with the changed guidance on these small cases,

or give one arm stronger-model repairs. Record every call, failure and correction;
missing usage is unknown. Examine concrete regressions before expanding tests.
Any later new comparison keeps original outcomes and freezes its own changed
condition first. No large repeated matrix is needed to defer usable completion.

## Reader review

For each judgment result inspect factual fidelity, context connections,
stakeholder distinctions, supported uncertainty, explanation order and useful
next action. Ask whether the intended reader can use it with less reconstruction
or editing. Concision alone, a grounding line, internal approvals or friendly
feedback do not establish the full result. Record improvement, tie, regression
and insufficient evidence independently; do not invent a numerical gain.

## Host cells and evidence

Required target families are Codex regression; Claude Code CLI and Desktop local
Code on Apple-silicon macOS/Windows x64; Claude account Web/Desktop Chat and
current Cowork; Antigravity conversation app on macOS/Windows11 x64. Old local
Cowork, IDE and remote environments are separate compatibility cells.

For a first supported-cell check use two ordinary judgment requests, one
mechanical control, a changed-fact continuation and a fresh-session lifecycle
check. Do not name OpenSocrates in the request to manufacture automatic entry.
Use disposable projects/profiles and synthetic inputs. Separate technical
delivery checks from usefulness comparisons to avoid unnecessary model calls.

Record capability and exact origin/version/digest; entry observation; complete
canonical-reading evidence or unknown; reported application state; artifact
result; settings-preservation result. An agent acknowledgment or status text is
not native proof of applied reasoning. UI visibility is availability evidence.
No private prompts, transcripts, account identifiers, auth material, screenshots
or unrelated configuration belong in the public product evidence.

## Lifecycle and stop rules

Qualify checksum validation, install/restart, ordinary entry, partial-read and
unavailable-runtime fallback, compaction/continuation, disabled entry, update,
remove and rollback. Preserve an unrelated sentinel rule and existing enabled
states. Refuse changed or unowned files; do not weaken permissions to obtain a
pass. Account upload and local filesystem installation are separate lifecycles.

Fix diagnosed implementation defects and run only affected checks; retain failed
versions. Stop an unchanged environment/access blocker and continue independent
work. An unsupported host remains unknown/unavailable and restricts the support
claim. Every requested claimed support cell requires its own usable evidence;
package CI cannot substitute for a live Windows or cloud result.

Finish the release candidate when the intended core behavior is usable, each
claimed host/lifecycle has the required checks, privacy and rollback hold, and
documentation describes the evidence accurately. Human recruitment, account-side
isolation, billed savings or universal model advantage are not added as universal
gates. Merge/tag/publication and active installation replacement remain separately
authorized steps.
