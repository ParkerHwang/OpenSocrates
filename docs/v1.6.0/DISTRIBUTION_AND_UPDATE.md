# OpenSocrates v1.6.0 배포와 자동업데이트

직접 배포한 Go 설치 프로그램이 설치·진단·업데이트·제거를 관리한다. 예약 실행과 수동 명령은 같은 업데이트 엔진을 사용한다. 최초 설치 신뢰, 기존 설치 인수, 버전 묶음, 호스트별 적용과 중단 복구를 한 설계로 다룬다.

## 최초 설치와 릴리스 구성

정식 자산은 GitHub Releases의 macOS ARM64와 Windows x64/ARM64용 Go 설치 프로그램 및 검증된 패키지다. [GoReleaser](https://goreleaser.com/getting-started/quick-start/)를 빌드·아카이브·릴리스 준비 후보로 사용한다. 런타임과 호스트 콘텐츠가 같은 릴리스·콘텐츠 식별자를 갖도록 전체 파일 목록과 해시를 포함한다.

첫 버전은 Go 설치 실행파일과 플랫폼별 아카이브로 제공한다. `.pkg`·GUI 설치물이나 추가 패키지 관리자는 사용자 경험이 필요할 때 확장한다. 설치 관리 CLI는 안정된 위치에서 호출되며 사용자는 Go·Python·Node.js를 설치하지 않는다. 신규 네이티브 호스트 통합의 신뢰 승인은 해당 호스트가 요구하는 절차를 따른다.

업데이트 서명과 macOS 코드 서명·notarization, Windows 코드 서명·SmartScreen 평판은 각각의 검증 대상이다. 최초 설치 프로그램에 신뢰 루트를 포함하고 공식 전달 경로와 코드 서명 정책을 릴리스 전에 고정한다. 설치물 옆의 체크섬만으로 최초 설치의 진위를 보장한다고 주장하지 않는다.

## 기존 v1.5.0·v1.5.1·v1.5.2 설치 인수

현재 Codex의 `desired-state.json`·예약 작업과 추가 호스트의 소유 마커는 서로 다른 상태다. 새 관리 상태는 실제 등록·소유 파일을 검사해 가져오며, 이전 호스트 집합을 추가 프로필로 재해석하지 않는다.

1. 기존 설치의 버전·소유권·파일 목록·등록·비활성 상태와 예약 작업을 확인한다. 수정된 파일이나 모르는 등록은 보존하고 충돌을 보고한다.
2. 기존 관리 상태와 스케줄러 설정의 검증한 복구본을 만들고 인수 작업을 기록한다.
3. Go 관리 도구와 버전 묶음을 별도 위치에 준비하고, 기존 설정과 훅 신뢰를 유지하는 새 상태를 작성한다.
4. 기존 npm LaunchAgent의 현재 작업을 안전하게 조정하고 예약 실행을 중지한다. 새 작업과 이전 작업이 동시에 변경을 수행하지 않도록 인수 잠금과 동시 실행 정책을 적용한다. 안전하게 배타권을 얻을 수 없으면 인수를 보류한다.
5. 새 설치와 호스트 등록을 확인한 뒤, 기존 자동업데이트 선택을 반영해 Go 예약 작업을 등록한다. 호스트 신뢰를 자동 승인하거나 꺼진 통합을 켜지 않는다.
6. 확인이 끝나면 인수를 완료한다. 실패하면 파일·등록·상태와 이전 예약 작업까지 복원하거나 검증한 복구본을 남긴다.

v1.5.0·v1.5.1·v1.5.2의 원래 패키지·설정·언어 선호·꺼진 통합을 각각 보존한다. 두 언어/96개 참조, 네 언어/192개 참조, 열 언어/480개 참조의 검증 조건을 버전별로 유지하며 과거 패키지를 자동으로 새 언어 기준으로 바꾸지 않는다.

현재 npm 설치자는 새 릴리스의 Go 채널을 자동으로 알아낸다고 가정할 수 없다. 기존 사용자는 새 Go 설치 프로그램을 한 번 실행해 인수한다. 전환 안내를 제공하며, 기존 npm 패키지를 소유권 확인 없이 삭제하지 않는다. 이전 버전으로 돌아가는 절차도 상태와 스케줄러의 복원 범위를 명시한다.

## 버전 묶음과 설치 상태

Go 관리 도구, 실행파일, 호스트 콘텐츠, 스키마와 목록을 식별한 버전별 디렉터리에 설치한다. 후보를 준비하는 동안 현재 버전을 유지하고, 검증 후 작은 활성 참조를 교체한다. 프로그램은 시작한 묶음의 경로와 식별자를 고정한다. 설정과 관리 상태는 버전 디렉터리 밖에 둔다.

v1.6.0은 출시된 v1.5.2의 열 언어·리비전 5 본문을 포팅하고, 48개 본문 업그레이드는 v1.6.1 등 후속 버전의 콘텐츠 묶음으로 전달한다. 제품 버전과 콘텐츠 리비전을 구분해 새 본문을 받을 수 있게 하되, 스키마·런타임 호환성과 실제 계정·호스트 적용 경계는 같은 검증 계약을 적용한다.

설치 상태에는 전역 관리 도구 버전뿐 아니라 호스트·scope별 설치 버전, 비활성 여부, 무결성, 예정된 후보와 확인 결과를 포함한다. 서로 다른 호스트에 서로 다른 버전이 남는 경우를 표현한다. 전체 호스트가 포인터 하나로 동시에 적용됐다고 기록하지 않는다.

실행 중 `.exe`를 덮어쓰는 대신 Windows Go 보조 프로세스가 필요한 종료·교체를 수행한다. 관리 도구와 업데이터 자체의 갱신도 릴리스에 포함한다. 보조 프로세스의 위치·소유권·입력을 검증하고 실패 시 이전 관리 도구를 사용할 수 있게 한다. 현재 실행 중이거나 복구에 필요한 버전은 정리 대상에서 제외한다.

## 업데이트 메타데이터와 신뢰

안전한 갱신 계약의 기본 후보는 [The Update Framework](https://theupdateframework.io/docs/overview/)와 [go-tuf](https://github.com/theupdateframework/go-tuf)다. V6에서 현재 지원 API와 운영 비용을 확인하고 고정한다. 다른 구현을 선택하더라도 아래 신뢰 계약은 유지한다.

| 항목 | 계약 |
| --- | --- |
| 최초 신뢰 | 검증한 최초 설치물에 신뢰 루트 포함. 업데이트 서버의 파일을 그대로 신뢰 루트로 채택하지 않음 |
| 릴리스 식별 | 제품·콘텐츠 버전, 채널, 플랫폼·아키텍처, 패키지 목록과 대상 해시 |
| 호환성 | 최소 관리 도구 버전, 데이터 스키마·변환 버전, 호스트 프로필 지원 조건 |
| 메타데이터 검증 | 서명·만료·단조 증가 버전·일관된 묶음 확인, 허용한 전송 대상과 크기 제한 |
| 키 변경 | 기존 신뢰에 연결되는 키 교체·폐기 절차, 복구 경로, 키 손실 시 운영 절차 |
| 키 운영 | 서명 비밀키를 소스·배포물·로그에 포함하지 않음. 신뢰 루트와 온라인 릴리스 서명 역할 분리 |
| 명시적 복구 | 검증한 이전 로컬 묶음으로 돌아가는 별도 복구 명령. 네트워크의 오래된 릴리스를 정상 업데이트로 수락하지 않음 |

불완전·만료·서명 불일치·지원하지 않는 메타데이터는 현재 설치를 유지하는 결과로 처리한다. 재시도 정책은 오류 코드로 결정한다. 버전·신뢰·스키마 검사를 통과하지 못한 후보를 자동 실행하지 않는다. 자동 복구는 해당 로컬 작업에서 보존한 검증된 이전 상태를 사용한다.

## 예약 실행과 적용 정책

macOS는 사용자 LaunchAgent, Windows는 사용자 작업 스케줄러를 사용한다. 설치 당시의 명시적 선택을 보존하며 관리자 서비스나 상시 프로세스를 기본값으로 만들지 않는다. 운영체제별 로그인·주기 실행 조건은 [Apple 안내](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)와 [Windows 작업 안내](https://learn.microsoft.com/en-us/windows/win32/taskschd/starting-an-executable-when-a-user-logs-on)를 따른다.

- 기본 정책은 사용자 opt-in, `stable`, 24시간 간격과 로그인 후 지연 확인이다. 오프라인·절전 후에는 제한된 재시도로 다음 기회를 사용한다.
- 로그인된 사용자 권한으로 그 사용자의 등록된 설치만 관리한다. 암호·인증 토큰을 예약 작업에 저장하지 않는다.
- 메이저 또는 호환성을 깨는 데이터 전환은 준비·안내까지만 하고 자동 적용하지 않는다. 호환 가능한 패치·마이너만 자동 적용 후보로 삼는다.
- 훅 실행 중에 네트워크 확인이나 설치를 수행하지 않는다. 자동업데이트가 대화 지연이나 훅 시간 제한을 늘리지 않도록 분리한다.
- 시작한 Go 프로세스는 버전을 유지한다. 호스트 대화의 로딩 시점은 프로필별로 검증하며 세션을 읽거나 강제로 종료하지 않는다.
- 안전한 호스트 적용 시점을 확인할 수 없으면 후보 다운로드·검증 후 적용 대기로 남긴다. 파일 교체를 실제 대화 적용으로 보고하지 않는다.

macOS/Windows Codex가 필수 자동업데이트 범위다. native Claude와 Antigravity는 설치 범위별 등록·비활성 상태·참조 경로·reload·복구를 확인한 뒤 프로필별로 활성화한다. 계정 ZIP은 로컬 생성·검증·내보내기만 관리하고 계정 업로드·활성화는 별도 UI 작업으로 유지한다.

workspace 등록에는 사용자가 명시한 설치 위치를 안전한 로컬 관리 상태로 보관할 수 있다. 작업 공간을 자동 탐색·등록하거나 내용을 수집하지 않는다. 업데이트 결과 기록과 공개 검증 결과에 작업 공간 경로를 포함하지 않는다.

## 작업 단계와 재시작 복구

저널은 소유권을 확인한 관리 상태에 저장하며 단계, 작업 대상의 관리 식별자, 사전·적용 후 목록과 해시, 검증한 복구본, 스케줄러 변경을 기록한다. 재시작 시 잠금과 실제 파일·등록을 다시 확인하고 저널의 내용만으로 소유권을 추정하지 않는다.

| 단계 | 처리 | 중단 후 처리 |
| --- | --- | --- |
| 확인 | 정책·예약 시각·신뢰 메타데이터·배타권 확인 | 현재 버전 유지. 검증된 관리 상태에서 재확인 |
| 준비 | 제한된 다운로드, 서명·해시·목록 검증, 후보 스테이징 | 활성 상태를 바꾸지 않은 후보만 안전하게 재사용·정리 |
| 적용 대기 | 패키지 내부 버전·내용·오프라인 실행 확인, 호스트 적용 조건 판단 | 검증한 후보 유지 또는 현재 버전 유지 |
| 적용 | scope별 파일·등록·활성 참조·필요한 예약 작업 변경 | 실제 대상이 사전/적용 후 해시 중 무엇인지 확인하고 완료·복원·수동 복구 판단 |
| 확인 | 호스트 등록·버전·비활성 상태·파일 무결성 확인 | 조건이 맞으면 완료. 실패 시 검증한 이전 상태로 복원 |
| 완료 | 결과와 관리 상태 확정, 안전한 오래된 묶음 정리 | 같은 작업 재실행이 중복 등록·삭제를 만들지 않음 |

복구는 순서와 내구성까지 포함한다. 데이터 스키마 변환이 필요하면 해당 작업 전에 복구 가능한 상태를 확보한다. 실행파일만 이전 버전으로 바꾸고 되돌릴 수 없는 데이터에 연결하지 않는다.

확인되지 않은 잠금, 외부에서 수정된 대체 파일, 다른 소유자, 링크/reparse 대상과 변경된 백업을 임의로 삭제하지 않는다. Windows는 기존 DACL·부모 핸들 보호를 유지한다. 복구할 수 없을 때 현재 대상과 검증한 복구본을 보존하고 로컬 진단에서 명확한 다음 행동을 제공한다.

## 사용자 명령과 결과

기존 호스트·설치 명령과 호환을 유지하고 필요한 Go 관리 명령을 추가한다. 다음은 기능 범위이며 인수의 최종 문법은 V5에서 고정한다.

| 기능 | 제공할 결과 |
| --- | --- |
| 설치·이전 설치 인수 | 소유권과 충돌 확인, 비활성·신뢰·관련 없는 파일 보존 |
| 상태·진단 | 관리 도구와 scope별 버전, 무결성, 후보, 적용 대기·사용 불가 이유 |
| 수동 업데이트 | 예약 업데이트와 같은 검증·작업·복구 엔진 사용 |
| 자동업데이트 켜기·상태·끄기 | 대상 범위, 정책, 다음 확인과 예약 작업의 실제 상태 |
| 복구 | 검증한 이전 버전·상태로 복원 또는 안전한 수동 복구 안내 |
| 제거 | 소유한 설치·예약 작업 제거, 실행 중 버전과 관련 없는 사용자 데이터 보존 |

업데이트 결과 기록에는 버전, 시간, 호스트/scope 종류, 작업 단계와 닫힌 오류 범주만 포함한다. 프롬프트·대화·스크린샷·인증값·작업 공간 경로·원문 오류를 기록하지 않는다. 명령의 성공은 파일·등록의 확인 결과이며, 모델이 방법을 적용했다는 증거를 대신하지 않는다.

## 추가 배포 채널

Homebrew·WinGet을 추가할 때는 실행파일의 업데이트 소유자를 하나로 정한다. 패키지 관리자가 소유하는 설치를 자체 업데이터가 동시에 덮어쓰지 않도록 정책을 분리한다. 이 채널과 GUI 설치물은 필수 Go 전환·직접 배포·자동업데이트 이후의 확장이다.
