# OpenSocrates v1.6.0 준비 인계

상태는 **v1.6.0 구현 준비 문서 작성**이다. 사용자는 48개 본문 업그레이드를 v1.6.0에서 제외하고 v1.6.1 등 후속 릴리스로 분리했다. 본문 완료 대기 없이 현재 릴리스의 콘텐츠를 기준으로 구현할 수 있도록 정리한다. 실제 작업 묶음은 [구현 계획](IMPLEMENTATION_PLAN.md)을 따른다.

## 준비 기준

- 작성일: 2026-10-12.
- 저장소: [ParkerHwang/OpenSocrates](https://github.com/ParkerHwang/OpenSocrates).
- 확인한 당시 `main`: `9572db2c71a455d4ada24c78402d0f874002cec9`.
- 본문 기준: 출시된 [v1.5.0](https://github.com/ParkerHwang/OpenSocrates/releases/tag/v1.5.0)의 태그 커밋 `cf6634310afcf5d5ce58484e67a73151bb4c5999`. 준비 기준의 `content/`, `plugin-src/`, `schemas/source/`는 이 태그와 차이가 없다.
- 준비 문서 소유 범위: `docs/v1.6.0/`.
- GitHub 추적: 준비 작업의 issue/PR은 이 문서가 포함된 PR의 Tracking을 따른다. 구현 착수 시 구현 추적 작업을 별도로 만든다.

## 정리한 작업

Go 전체 전환, 공통 설치 엔진, 언어 중립 계약, 기본 선택·이전 연결 분리, OS별 파일 보호, 기존 npm 설치 인수, 직접 배포, 예약 자동업데이트, 자체 갱신과 중단 복구를 작업 묶음으로 정의했다.

본문을 변경하거나 생성 결과를 다시 만들지 않았다. 버전·실행·설치·기존 사용자 안내와 현재 지원 주장은 준비 단계에서 변경하지 않는다. 본문 세션과 분리된 작업 공간과 문서 브랜치에서 준비한다.

## v1.6.0 기준 기록

| 항목 | 기준과 확정할 내용 |
| --- | --- |
| 소스 기준 | 준비 당시 main SHA는 위에 고정. 구현 시작 시 최신 소스와 후속 본문 변경의 혼입 여부 확인 |
| 방법과 언어 | v1.5.0의 48개 방법과 EN/KO 본문·선택 메타데이터 유지 |
| 콘텐츠 묶음 | V0에서 기존 콘텐츠의 `content_revision`, `source_tree_hash`, `normalized_semantic_hash`와 기준 생성물 위치 기록 |
| 관련 입력 | 기존 teacher-question overlay, 공통 시스템·응답 정책과 공유 reader·decision 가이드 유지. Go 실행 경로에 필요한 프로필 변경은 별도 |
| 데이터 계약 | 기존 소비자·저장 상태와 호환되는 타입·검증. 의도한 형식 변경은 버전과 변환 규칙으로 구분 |
| 생성 결과 | 기존 컴파일 콘텐츠·스키마·호스트별 패키지와 Go 생성 결과 비교 |
| 실제 검증 | 정확한 커밋·명령·결과·환경, 실패와 수정, 재사용할 수 있는 동일 기준 증거 |

콘텐츠 기준 SHA는 확정돼 있으며 V0에서 해당 리비전·해시와 생성물 식별자를 구체적으로 기록한다. 이는 본문 업그레이드 완료 정보를 기다리는 단계가 아니다. 후속 릴리스에서는 새 본문 완료 SHA·관련 입력·생성 결과·검증 기록을 따로 받아 새 콘텐츠 기준으로 전환한다.

## 구현 시작 절차

1. 최신 `main`, v1.5.0 콘텐츠 기준과 저장소 지침을 다시 확인한다. 기존 issue/PR과 겹치는 구현 작업을 검색한다.
2. 위 기준 항목을 고정하고 소스·계약 차이를 확인한다. v1.6.1 등 후속 본문 작업의 커밋과 생성물을 v1.6.0에 섞지 않는다.
3. 구현 브랜치와 추적 작업을 만들고 V1의 데이터 계약·배포 프로필·파일 소유권을 확정한다.
4. V2-V7을 구현하고 공유 변경을 통합한다. 일반 구현 중 검사를 반복 실행하지 않는다.
5. 안정된 최종 리비전에서 V8의 검사와 검토를 수행한다. 실패를 수정한 뒤 영향받은 검사만 재실행한다.
6. 구현·검증·누락 증거를 분리한 인계를 PR에 남기고 보호된 브랜치 절차를 따른다. 릴리스 태그·배포 게시의 실행 조건은 해당 단계에서 확인한다.

## 구현에서 고정할 기본값

| 항목 | 계획의 기본값 | 확정 조건 |
| --- | --- | --- |
| 언어와 도구체인 | 자체 활성 구현 Go 통일 | 구현 시작 시 안정 버전·의존성 고정 |
| 배포 | GitHub Releases의 Go 설치 실행파일과 플랫폼별 아카이브 | 최초 설치 신뢰·서명·정확한 자산 목록 확인 |
| 자동업데이트 | opt-in, stable, 24시간, major·비호환 전환 차단 | Codex macOS/Windows 네이티브 수락 |
| 추가 로컬 호스트 | 수동 lifecycle 유지 후 프로필별 자동업데이트 확장 | 해당 scope의 적용·비활성 상태·복구 검증 |
| 계정 스킬 | 완전한 ZIP 생성·검증·내보내기 | 계정 UI 업로드·활성화는 별도 |
| 업데이트 신뢰 | TUF와 go-tuf 우선 검토 | 실제 API·신뢰 루트·키 운영·최초 설치 정책 확정 |
| 이전 SDK 경로 | 별도 Go app-server 연결 | 기존 프로토콜·격리·취소 동등성 확인 |

이 기본값들은 구현 시 결정할 위치를 정한다. 새 플랫폼 지원이나 계정 자동화, 호스트 신뢰 자동 승인으로 확대하지 않는다. 코드 서명에 필요한 운영 자원은 릴리스 전에 마련하며 준비 문서 작성의 선행 조건으로 두지 않는다.

## 검증 기록과 범위

준비 문서의 최종 점검 명령과 결과는 이 문서가 포함된 PR의 Validation과 Handoff에 기록한다. 기준 커밋은 위 준비 기준과 문서 변경 커밋을 구분한다.

준비 문서의 점검은 Go 구현·자동업데이트·본문 품질·네이티브 패키지·실제 호스트 적용 증거가 아니다. 이 작업은 그런 증거를 만들 단계와 수락 조건을 정리한다. 별도 본문 세션과 과거 릴리스의 증거는 각자의 커밋·환경·릴리스 범위와 함께 보존한다.
