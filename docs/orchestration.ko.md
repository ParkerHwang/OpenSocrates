# 선택형 전문 제작과 독립 승인 검증

미공개 v1.5 후보의 명시적 `orchestrate` 명령은 범위가 정해진 텍스트, 소스 코드,
JSON 계산 결과와 Markdown 문서를 제작합니다. 새 제작자, 별도의 독립 검토자,
승인된 읽기 전용 실행 검사, 세 번째 새 실행 검증자가 차례로 작업합니다.
주 에이전트는 분류, 채택된 의도, 권한과 최종 통합을 책임집니다. 일반 훅과 기본
`decision` 명령은 이 흐름을 시작하지 않습니다. 바이너리 문서 제작과 시각적
렌더링 검사는 이 어댑터 범위 밖입니다.

`run`은 호출자가 인증한 Codex의 사용량을 소비합니다. 선택한 작업 제약, 범위가
정해진 소스 본문, 의존 산출물, 선택된 기억 투영과 전체 역할·분야 지침을 해당
클라이언트에 전달합니다. 모든 역할은 호출자가 승인한 동일한 모델·추론 강도를
쓰며 다른 모델로 대체하거나 역할별로 바꾸지 않습니다. 설정한 모델명은 독립적인
백엔드 증명이 아닙니다. 새 프로세스와 읽기 전용 도구 샌드박스는 계정 격리나
무관한 모든 파일의 읽기 차단을 입증하지 않습니다. 전역 설정을 바꾸지 않고
네이티브 기억, 훅, 앱, 플러그인, 하위 에이전트와 호스트 스킬 탐색을 비활성화합니다.

## 호출과 닫힌 계획

소스 실행은 `python -m opensocrates orchestrate`, 설치된 실행기는
`bin/launch.sh orchestrate codex`와 `node bin/launch.mjs orchestrate codex`입니다.
표준 입력으로 완전한 JSON 문서 하나를 받습니다. `operation: prepare`는 모델 호출과
후보 파일 쓰기 없이 계획과 제한된 소스를 확인합니다. `operation: run`은 명시된
클라이언트를 실행합니다. 현재 검증 대상 어댑터는 macOS와 `codex-cli 0.158.0-alpha.2`,
그 버전의 `sandbox -P :read-only` 경계를 요구합니다. 다른 클라이언트·운영체제는
사용 불가를 반환합니다. 패키지가 제공되는 플랫폼이라고 이 어댑터까지 지원되는
것은 아닙니다.

[전체 예시](../plugin-src/shared/orchestration/request.example.json)와
[요청 스키마](../schemas/v1/orchestration-request.schema.json)를 사용하세요.
절대 소스·클라이언트·후보 경로를 실제 경로로 바꾸고 소스의 실제 SHA-256을 확인해야
합니다. 예시의 `requirements.txt`는 정확히 `Reviewed candidate.`와
뒤따르는 LF 한 글자입니다. 후보 폴더는 소스 밖의 아직 존재하지 않는 경로여야 합니다.
예시는 모델이 만든 명령 대신 성공 종료값 0을 요구하는 정확한 한 줄 검사를 씁니다.
모든 검사는 실제 호스트 실행 파일과 승인된 전체 인수 배열을 지정하세요.

계획은 다음 세 축을 구분합니다.

- `domain`: `software`, `data`, `document`, `research`, `unknown`
- `task_kind`: `judgment`, `mechanical`
- 제작 `role`: `design`, `production`. 실행기가 각 버전에 별도의 `review`와
  `execution_verification` 역할을 배정합니다.

각 단위는 한 제작자, 정확한 소유 경로, 의존성, 관련 소스 ID, 지배 요구사항 ID와
공개 완료 의무를 지정합니다. 최상위 `required_artifacts`로 소유자가 없는 필수
산출물을 거부합니다. 중복·대소문자 충돌 경로, 없는 의존성과 순환 그래프도 거부합니다.
기계적인 작업은 선택적 추론·분야 절차를 건너뛰지만 독립 승인 검증은 수행합니다.
알 수 없는 분야는 분류 공백을 반환하고 무관한 준비된 단위는 계속 진행합니다.
프로그램이 필요한 문서는 명시적인 소프트웨어 단위로 나눠야 합니다.

`constraints`는 현재 채택된 계약 전체입니다. `permissions`와 `prohibitions`는
기존 권한을 설명하며 필드 자체가 동의를 증명하지는 않습니다. `specialists`는
소프트웨어 판단 작업에 전체 전문 절차 `contracts`, `transitions`, `ownership` 중
0~2개를 지정합니다. 일반 기법을 먼저 거칠 의무는 없습니다. 전체 한영 역할·분야
참조, 필요한 검증 지침과 선택한 전문 절차를 자르지 않고 전달합니다. 요청·소스·할당
한도를 넘으면 제약을 버리지 않고 거부합니다.

범위가 정해진 소스는 새 작업 폴더의 `inputs/<source-id>/<원래 파일명>`에 놓입니다.
의존 산출물과 현재 후보는 폴더 루트의 선언된 상대 경로를 씁니다. 새 맥락마다 정확한
입력·지침 해시와 닫힌 출력 계약을 제공합니다. 검토자에게 제작자의 자기 평가, 이전
점수나 수정 지적 사항을 전달하지 않고 실행 검증자에게 검토 판정을 전달하지 않습니다.
수정하는 제작자만 공개 결함 지적, 정확한 버전에 묶인 실패·미확인 의무 판정과 실제
검사 영수증을 받습니다. findings가 비어 있어도 의무 증거를 버리지 않으며, 실행 가능한
수정 근거가 없으면 수정을 명시적으로 거부합니다.

## 검사, 수정과 결과 파일

검사는 절대 실행 파일, `authorization_reference`, 담당 `obligation_ids`,
`expected_exit_code: 0`을 가진 호출자 승인 `argv` 배열입니다. 부정 테스트는
예상한 거부를 확인한 뒤 0으로 종료해야 합니다. 샌드박스 오류를 정상적인 프로그램
거부로 착각하지 않도록 0이 아닌 값을 성공으로 선언할 수 없습니다. 통제된 환경과
네트워크 차단이 적용된 지원 읽기 전용 샌드박스에서 이 배열만 실행합니다.
V1에서는 임시 경로를 포함해 파일을 쓰는 검사를 허용하지 않습니다. 각 검사·역할 뒤
후보·의존·소스 입력 해시를 다시 확인하며 샌드박스 없는 실행으로 대체하지 않습니다.
셸 정책의 제한과 클라이언트 계정·백엔드 경계는 별개입니다.

별도의 검증자가 실제 종료 상태, 입력 무결성, 출력 해시 영수증을 해석합니다.
각 필수 의무를 담당한 모든 통과 검사에 대해 `check:<check_id>`를 인용해야 합니다.
검토·검증 지적은 정확한 산출물 해시, 요구사항, 파일 위치, 기대·관찰 결과, 독립 재현,
영향과 누락 증거를 포함합니다. 다른 검사가 통과해도 필수 의무가 미확인·실패이면
후보가 통과하지 못합니다. 실행 검사가 없으면 미확인입니다. 프로세스 종료만으로
의미적 승인 검증을 완료하지 않습니다.

조정 실행기만 후보 파일을 씁니다. 검토자는 파일을 수정할 수 없습니다. 지정된
제작자가 `repair_limit` 0~2회 안에서 수정하고 새 버전마다 새 독립 검토와 실행 검증을
받습니다. 의존 작업은 통과한 버전으로만 제작됩니다. 소스나 이미 통과한 의존성이
바뀌면 영향받는 단위의 통과를 무효화하고 재검사 의무를 남깁니다.

새 `candidate_root`에는 다음 결과가 있습니다.

- `versions/<unit-id>/v<번호>/<owned-path>`: 실패한 버전을 포함한 모든 반환 산출물.
  응답에는 제작자 계보가 명시됩니다.
- `artifacts/<owned-path>`: 최종 검증을 통과한 후보 바이트만 포함합니다.

제한된 [응답](../schemas/v1/orchestration-response.schema.json)은 명세, 구조화된 공개
지적, 프로세스 실패, 오류 이벤트 수와 노출된 사용량 다섯 필드를 유지합니다. 없는
사용량과 관찰할 수 없는 백엔드 시도 횟수는 null입니다. 원시 JSONL, 프롬프트, 사고
과정, 표준 오류와 검사 출력 덤프는 버리며 제품에서 저장하지 않습니다. 임시 입력은
각 역할·검사 뒤 제거합니다. 반환한 파일은 의도된 산출물이며 기억 레코드가 아닙니다.
어댑터의 출력 처리 밖에서 일어나는 클라이언트 동작은 Codex 호스트 경계에 속합니다.

응답의 `publication`은 `not_started`, `incomplete`, `complete`를 구분하고 완료한
파일의 식별 정보와 쓰기 중이었을 수 있는 경로를 담습니다. 중단되면 검증 통과 기록은
남아도 파일 게시가 끝나지 않았을 수 있습니다. `complete`와 `location_verified: true`가
함께 있어야 후보 게시 완료입니다. 취소나 처리 가능한 실행 오류가 나도 누적된 실행,
호출, 사용량, 버전과 검사 기록을 보존하며 미시작 응답으로 초기화하지 않습니다.
일부 파일은 광범위한 정리 없이 확인할 수 있게 남깁니다.

게시는 승인된 소스·출력 조상의 디렉터리 핸들을 유지합니다. 링크를 따르지 않는
디렉터리 상대 연산으로 새 하위 경로만 만들고 쓰며 소스·출력 조상이나 후보 루트가
바뀌면 거부합니다. 알려진 시스템 경로 별칭은 핸들을 묶기 전에만 정규화합니다.
이 기능이 없는 호스트는 모델 호출 전에 사용 불가를 반환하며 읽기 전용 준비는 유지합니다.

`integration_pending`는 모든 단위가 후보로 통과했고 후보 게시도 완료했다는 뜻입니다. 어댑터는 기존
프로젝트에 쓰거나 최종 통합을 주장하지 않습니다. 주 에이전트가 승인된 바이트를
통합하고 영향받는 의존성을 찾아 정확한 최종 바이트에 관련 검사와 독립 승인 검증을
다시 수행해야 합니다. `candidate_root`로 기존 프로젝트 수정을 우회할 수 없습니다.
수동 변경 후 새로 명시한 계획에서 `seed.author: external_author`와 현재 최종 내용을
써 독립 검증할 수 있습니다. 통제된 결함 예시는 `synthetic_fixture`를 쓰고 모델이
만든 결함으로 돌리지 않습니다. seed는 최초 제작만 건너뛰며 검토·실행 검증과 제한된
제작자 수정을 유지합니다.

종료값 0은 `blocked`, `partial`, `integration_pending`를 포함한 응답 처리 완료를
뜻하므로 의미 상태를 확인해야 합니다. 잘못된 입력은 2, 실행 기능 사용 불가는 3으로
종료합니다. 임의의 모델 실행 시간 제한을 두지 않으며 호출자 취소를 보존합니다.
기능이 없으면 검증한 같은 계획을 지원 호스트에 넘길 수 있습니다. `prepare`나 가짜
어댑터 결과는 실제 실행 완료가 아닙니다.

## 범위가 정해진 기억과 검증 수준

`memory: null`은 호출자가 명시한 `handoff`와 현재 제약을 씁니다. 선택적 기억 연결은
이미 등록된 프로젝트·작업공간과 레코드 ID를 지정하며 등록·마이그레이션·기록을 하지
않습니다. 빈 ID 목록은 적용 가능한 레코드를, 비어 있지 않은 목록은 선택적 지식을
좁혀 가져옵니다. 어느 쪽도 적용 가능한 채택 결정의 제약을 지울 수 없습니다.
작업·모듈 범위를 지키며 전체 요약·공개 근거와 필요한 체크포인트 제약을 보존합니다.
한도를 넘으면 채택 의도를 자르지 않고 맥락을 거부합니다.

제작 전에 적격 레코드 ID·버전을 고정합니다. 검토 맥락은 같은 시도의 자기 평가,
체크포인트와 독립 증거가 없는 교훈을 제외합니다. lifecycle, support, 소스 freshness,
review_state를 구분합니다. 기존 레코드에는 정확한 버전의 독립 검토 영수증이 없어
review_state는 unknown입니다. 교훈은 공개 rationale에 `conditions`, `mechanism`,
`exceptions`, `provenance`, `evidence_refs`를 가진 JSON을 쓸 수 있으며 SQLite 필드나
마이그레이션은 추가하지 않습니다. 소스에 의존하는 지식은 원래 스냅샷 범위로
재검증합니다. 고정 레코드 삭제·변경은 재사용을 무효화하며 후속 실행이 별도 캐시에서
삭제된 내용을 되살리지 않습니다.

기억이 없거나 비활성·사용 불가이면 저장소를 만들지 않고 잃은 연속성을 명시합니다.
현재 계획의 제약과 인계 내용은 유지됩니다. 별도 승인된 저장은 기존 기억 등록·기록·
CAS·채택·삭제 API를 쓰세요. 채택되었다고 독립 검토되었거나 참인 것은 아닙니다.

`make orchestration-check`는 명확히 가짜로 표시된 모델 어댑터로 라우팅, 맥락,
소유권, 실패, 수정, 기억과 개인정보 경계를 결정적으로 검사합니다. 실제 모델 동작,
호스트 전달, 네이티브 패키지와 품질 향상에는 각각 정확한 버전의 별도 증거가 필요합니다.
구현은 문서화된 [Codex 비대화형 기능](https://learn.chatgpt.com/docs/non-interactive-mode)을
사용하며 공식 문서가 실제 호스트 검증을 대신하지는 않습니다.

## 범위가 정해진 검증 기록

[버전별 검증 보고서](../evals/v1.5/orchestration/v1/REPORT.md)에 고정된 소프트웨어
설계·수정, 계산에서 문서로 이어지는 작업, 한국어 후속 작업과 독립 검사, 실패 기록,
노출된 사용량을 남겼습니다. 문서에 명시한 클라이언트에서 실행한 합성 정확성 예시이며
품질 벤치마크나 활성 플러그인 설치의 증거가 아닙니다. 각 지적의 `location`은 현재
담당 후보 파일 경로와 정확히 같아야 하며, 선택적인 줄 번호·범위는 `reproduction`에
적습니다. 실행기는 정확한 경로·해시·요구사항의 연결을 계속 검사합니다.

후속 [플랫폼 형식 검사 기록](../evals/v1.5/orchestration/ci-repair-v1/README.md)은
Windows 빌드·형식 검사 수정을 따로 기록합니다. 실제 실행 어댑터의 macOS 전용
경계를 유지하며, 이전 실제 모델 결과를 새 패키지에서 실행한 것으로 바꾸지 않습니다.
