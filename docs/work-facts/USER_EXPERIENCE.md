# 업무 사실 라이브러리: 사용자 경험 명세

상태: 개발을 위한 설계 제안. 구현·출시·실제 사용 효과가 확인된 문서가 아니다.
이 문서의 화면 이름과 안내 문구는 제품이 제공해야 할 경험을 설명한다. 현재
Claude 화면에 해당 기능이 있다는 뜻이 아니다.

첫 실제 사용 검증은 사용자의 결정에 따라 Claude에서 수행한다. Claude 일반
Chat과 Cowork는 별개의 검증 환경으로 기록한다. Claude Code의 훅이나 파일 접근
결과를 일반 Chat·Cowork의 지원 증거로 사용하지 않는다. ChatGPT·Antigravity·Cursor는
향후 지원 목표이며, Claude의 결과를 해당 앱의 결과로 일반화하지 않는다.

## 1. 사용자에게 제공할 약속

비개발 직군의 모든 일반 사무직 사람들이 자기 직무의 반복 업무와 일회성 업무에
사용할 수 있는 경험을 목표로 한다. 특정 부서·산업·직무를 지원 대상으로 제한하지
않는다. 아래 업무 예시는 사용 경험을 설명하기 위한 것이며, 예시에 없는 직군을
배제하거나 모든 직군의 효과가 확인됐다는 뜻이 아니다.

사용자는 평소처럼 일을 요청한다. 제품은 관련된 이전 업무 기록을 AI가 작업을
시작할 때 먼저 건네고, 작업 중 새로 확인된 사실을 작업 마지막에 자동으로
분류·저장한다. 사용자가 업무마다 저장을 지시하거나 저장 승인 버튼을 누르는
흐름으로 만들지 않는다.

사용자가 얻어야 할 것은 쓸 수 있는 결과물과 다음 업무로 이어지는 맥락이다.
분류 체계, 방법 이름, 데이터베이스 상태를 배워야 일을 진행할 수 있게 만들지
않는다. 확인 질문은 답에 따라 이번 작업의 대상이나 내용이 달라질 때만 한다.

라이브러리 기록이 없거나 저장할 내용이 없을 때도 새로운 문서, 아이디어,
분석, 조사, 계획과 같은 업무를 계속 돕는다. 현재 요청과 제공된 자료를 바탕으로
필요한 사고 지원을 수행하되, 사용자가 기록을 먼저 만들거나 특정 사고 방법을
선택해야만 일을 시작할 수 있는 흐름으로 만들지 않는다.

사용자는 다음 네 가지를 이해할 수 있어야 한다.

- AI가 어떤 이전 기록을 참고했는지와 그 기록의 확인 시점
- 무엇을 새로 저장했으며 무엇은 확인하지 못했는지
- 잘못된 기록을 어떻게 고치거나 지울 수 있는지
- 기록과 원래 자료가 어느 범위에서 사용·보관되는지

## 2. 현재 정책과 설계의 경계

현재 저장소의 [AGENTS.md](../../AGENTS.md)는 작업공간 내용 보관을 금지하며,
[SECURITY.md](../../SECURITY.md)는 현행 제품의 무보관 동작을 설명한다. 업무 사실을
지속 보관하려는 새 기능은 이 계약과 조정이 필요하다. 이 문서는 기존 지침을
바꾸거나 실제 업무 정보 저장을 허용하지 않는다. 정책이 조정되기 전의 구현·호스트
확인은 허구의 업무 자료와 격리된 시험 저장소를 사용해야 한다.

초기 설정에서 사용 범위를 설명하고 사용자가 기능을 켜는 일과, 매 작업마다 저장
승인을 받는 일은 구별한다. 초기 연결·기능 활성화·호스트 신뢰는 해당 앱과 조직의
정책을 따른다. 조직이 관리하는 범위는 개인 사용자가 임의로 넓힐 수 없다.

## 3. 작업 전체 흐름

| 단계 | 사용자 행동 | 제품의 동작 목표 | 사용자에게 보일 것 |
| --- | --- | --- | --- |
| 시작 | 평소 AI 입력창에 반복 또는 새로운 일을 요청 | 작업·프로젝트·주제와 관련된 맥락을 선별 | 필요한 경우에만 대상·적용 범위 확인 질문 |
| 사전 전달 | 추가 조작 없이 진행 | 관련 기록·출처·확인 시점·미확인 부분을 AI 작업 맥락에 먼저 전달 | 참고 기록을 확인할 수 있는 짧은 표시 또는 펼치기 수단 |
| 업무 수행 | 결과 확인·추가 설명·수정 | 현재 요청·자료와 전달한 맥락을 바탕으로 작성·분석·탐색·계획·판단을 지원하고, 현재 유효성이 작업을 바꿀 때 필요한 부분만 확인 | 바로 쓸 수 있는 결과물과 실제로 남은 확인 사항 |
| 자동 정리 | 저장 명령 없이 다음 일로 이동 | 보관 가치가 있고 허용된 새 내용을 분류하여 저장 | 작업을 막지 않는 저장 결과 표시 |
| 이후 활용 | 후속 업무나 관련된 다른 프로젝트의 일을 요청 | 적용 범위와 권한이 맞는 이전 기록·공통 기준·변경 이력을 선별해 재사용 | 무엇을 어느 범위·시점 기준으로 이어받았는지 확인 가능 |
| 사후 통제 | 잘못된 기록을 정정·삭제 | 후속 선별과 자동 추출에 정정·삭제 상태를 반영 | 적용 결과와 실제 삭제·보관 범위 |

사전 전달의 성공은 AI가 관련 작업을 시작하기 전에 필요한 기록이 전달되는 것이다.
AI가 이미 원문을 처음부터 검색한 뒤 기록을 보여주는 동작은 이 목표의 성공으로
세지 않는다. 전달한 기록이 실제 답변에 적절히 반영됐는지는 별도 평가한다.

호스트가 자동 전달이나 자동 저장 경로를 제공하지 않는다면 수동 복사·붙여넣기를
제품 목표 달성으로 표현하지 않는다. 수동 과정은 제한된 개념 시험 또는 대안으로
표시하고, 지원 여부를 확인한 뒤 정식 사용 흐름을 정한다.

## 4. 첫 사용과 연결 화면

일반 직장인은 첫 화면에서 코드나 설정 파일 대신 다음 내용을 확인한다. 정확한
배포·연결 방법은 호스트 기능 확인 후 확정한다.

| 화면 항목 | 이해해야 할 내용 | 설계 상태 |
| --- | --- | --- |
| 사용하는 환경 | 일반 Chat인지 Cowork인지, 어떤 계정·작업 범위에 적용되는지 | 호스트별 확인 필요 |
| 사용할 자료 | 허용한 업무 자료나 시험 자료의 범위, 연결하지 않은 곳은 알 수 없다는 점 | 접근·조직 정책에 맞춰 결정 |
| 저장할 내용 | 업무 사실·자료·기준·수치·정의·결정·시점·근거 중심이며, 선호·제안·초안과 실제 실행을 구분한다는 점 | 제품 목표 |
| 보관 위치와 통제 | 누가 저장소를 관리하고 누가 열람할 수 있는지 | 구현 방식과 정책 결정 필요 |
| 자동 동작 | 켠 범위에서 작업 후 자동 기록하며, 매번 승인을 요청하지 않는다는 점 | 핵심 목표, 실제 동작 미검증 |
| 멈추기와 삭제 | 새 저장을 멈추는 일, 기존 기록의 삭제, 원본 자료 삭제가 다르다는 점 | 동작 계약 필요 |

초기 상태가 불완전하면 필요한 단계와 이유를 구체적으로 알린다. 예를 들어 호스트
연결을 확인하지 못한 상태를 "준비 완료"로 표시하지 않는다. 제품을 켰다는 사실만으로
자료 접근이나 자동 실행이 보장되지 않는다.

## 5. 작업 전 참고 기록

### 5.1 정보의 구성

AI에게 전달할 업무 맥락에는 필요한 항목만 포함한다. 아래는 화면에 매번 모든 칸을
펼치라는 요구가 아니라, 참고 기록에서 확인할 수 있어야 할 정보다.

- **적용 범위:** 현재 작업, 프로젝트, 주제 또는 공통 기준. 같은 상대·이름의 다른
  안건과 구별되는 단서와 여러 업무에 적용할 수 있는 범위
- **기록된 내용:** 자료·기준·수치·정의·요청·결정·이유·약속·진행 변화 또는
  사용자가 명시한 작업 선호. 내용 종류에 따라 근거와 상태를 구분
- **시점:** 일이 일어났다고 기록된 시점과 자료를 확인한 시점의 구별
- **근거:** 어느 자료 또는 누구의 직접 진술을 바탕으로 기록했는지
- **확인 수준:** 자료에 기재된 내용, 사용자 진술, AI 해석·추론, 충돌·미확인 상태
- **미확인 부분:** 기록 이후 변경을 관찰하지 못한 범위 등 이번 업무에 관련된 한계

예를 들어 지표 수치는 단위와 집계 기간·정의를 함께 보여주고, 보고서 기준은
누가 정한 어느 프로젝트의 기준인지 표시한다. 사용자가 말한 문체 선호는 그
사용자의 선호로 표시하며 회사의 공식 규칙으로 표현하지 않는다. AI가 제시한
아이디어·잠정 해석과 산출물 위치는 확정된 현실 사실과 별도로 다룬다.

"원문을 읽음"은 "내용이 사실임", "결정 권한을 확인함", "현재도 유효함"과 다르다.
이 축을 하나의 초록색 확인 표시로 합치지 않는다. 정확한 내부 필드와 전달 계약은
기술 설계에서 정의한다.

### 5.2 사용자 노출 선택지

참고 기록의 사용자 노출 방식은 검증할 설계 선택지다. AI에게 먼저 전달하는 핵심은
유지하면서, 짧은 출처 표시·접힌 참고 영역·현재 상태가 중요한 경우의 강조 등을
비교한다. 사용자가 기록을 펼치거나 읽어야만 작업이 시작되는 구조는 기본으로
두지 않는다. 참고 기록이 없어도 가능한 일반 작업은 계속할 수 있다.

안내 문구 예시:

> 참고 기록: A사 납품 요청 · 10/29 확인 · 계약 미체결 사유로 반려 안내.
> 이후 변경은 확인되지 않았습니다. [기록 보기]

"이후 변경 없음"이라는 문구는 실제로 그 범위의 변경 부재를 확인했을 때만 쓴다.
기록이 검색되지 않았다는 이유로 "그런 일은 없었다"고 말하지 않는다.

## 6. 여러 업무에서의 가상 사용자 여정

아래 회사·인물·사건은 전부 허구다. 저장·자료 접근·호스트 실행이 허용되고 관련
기능이 구현됐다고 가정한 목표 경험이며, 실제 동작 증거가 아니다.

### 6.0 업무군별 같은 흐름의 다른 사용

| 요청 예 | 작업 전에 건넬 수 있는 맥락 | 업무·사고 지원 | 작업 후 남길 수 있는 기록 |
| --- | --- | --- | --- |
| “이번 달 운영 보고서 정리해줘” | 보고 목적, 적용 지표의 정의·단위·기간, 프로젝트 기준 | 자료를 확인하고 표·설명·보고 문안을 구성 | 확인한 수치와 정의, 자료 위치, 새로 확정된 보고 기준. 초안은 승인된 보고로 쓰지 않음 |
| “다음 정례회의 준비해줘” | 이전 회의의 결정, 미해결 질문, 후속 조치 | 안건·질문·필요 자료를 준비 | 실제로 확인된 결정과 담당·기한. 논의 아이디어나 예정 회의는 합의·실행과 구분 |
| “새 캠페인 방향을 같이 생각해줘” | 목표, 제약, 관련 조사 결과와 이미 검토한 가정 | 여러 방향을 탐색하고 근거·상충을 설명 | 출처로 확인된 전제나 사용자가 채택한 방향. 생성한 아이디어는 채택 사실로 저장하지 않음 |
| “지난 분석 기준으로 이번 자료를 비교해줘” | 이전 정의·계산 기준, 집계 범위, 알려진 자료의 한계 | 기간·단위가 맞는지 확인하고 비교·해석 | 재현 가능한 계산 결과와 사용한 기준·가정. 추정을 관찰값으로 승격하지 않음 |
| “이 규정이 이번 일정에 영향을 주는지 봐줘” | 적용 가능한 지침, 확인 시점과 대상 범위 | 지침과 일정의 관계를 설명하고 미확인 조건을 짚음 | 확인한 적용 범위·조건과 근거. 잠정 해석을 공식 승인으로 바꾸지 않음 |

첫 업무나 일회성 요청에서는 이전 기록이 없어도 현재 자료로 진행한다. 예를 들어
새 행사 안내문 작성은 저장된 거래처 이력이 필요하지 않다. 초안을 완성했지만
재사용할 새 사실이 없다면 기록을 추가하지 않고 결과물을 전달한다. 같은 흐름이
각 직무에 적합한지는 여러 업무군의 사용자와 사례에서 따로 확인해야 한다.

아래 거래처 회신은 시점·초안·실행·정정 처리를 자세히 설명하는 예시 하나다.

### 6.1 10월 29일: 반려 안내 처리

사용자는 "A사 요청은 계약이 아직 안 돼서 책임자 지시로 반려하고, 계약 후
진행한다고 회신해줘"라고 요청한다. AI는 메일 초안을 준비한다.

초안 작성만 확인된 시점에는 발송이나 승인으로 기록하지 않는다. 사용자에게
반복적으로 "보냈나요? 저장할까요?"라고 묻지 않는다. 실제 발송 자료나 사용자의
"보냈어"라는 진술을 관찰했다면 그 근거 종류를 구분하여 다음 내용을 저장한다.

| 기록 | 확인 근거와 한계 |
| --- | --- |
| A사 요청에 관해 반려 안내 | 실제 발송 자료가 확인됐다면 발송 기록, 사용자 말만 있다면 사용자 진술 |
| 반려 사유로 계약 미체결이 제시됨 | 10/29 자료에 기재된 당시 이유이며 현재 계약 상태가 아님 |
| 책임자 지시라고 전달됨 | 지시자와 결정 권한은 확인된 근거 범위로만 표기 |
| 계약 체결 후 진행하겠다고 안내 | 조건부 안내를 지금 재진행이 승인됐다는 뜻으로 바꾸지 않음 |

저장 결과는 작업을 막지 않는 형태로 보여준다. 예:

> A사 요청의 안내 내용과 사유를 기록했습니다. [보기·고치기]

확정 저장이 끝나지 않았으면 "기록했습니다" 대신 실제 상태를 쓴다. 저장할 만한
새 사실이 없으면 영수증을 만들기 위해 중복·불필요한 내용을 저장하지 않는다.

### 6.2 10월 31일: 후속 요청

사용자가 "A사에 회신해줘"라고 입력하면 관련 건의 이력을 먼저 전달한다. 같은 A사의
납품과 유지보수 건이 모두 해당할 수 있고 대상에 따라 회신 내용이 달라진다면,
"납품 요청 건인가요, 유지보수 건인가요?"처럼 답을 바꾸는 질문 하나를 한다.

단순히 "왜 반려했었지?"라고 묻는 경우에는 10/29 기록에 근거해 과거 이유를
설명한다. 기록이 오래됐다는 이유만으로 현재 메일함 전체를 검색하지 않는다.

"계약됐으니 이제 진행한다고 보내줘"처럼 현재 계약·승인이 결과를 좌우하면
사용자의 직접 지시와 제공된 사실을 먼저 반영한다. 이미 알려준 내용을 다시
질문하지 않는다. 최신 상태에 실제 공백이나 충돌이 있으면 해당 계약 건과 필요한
기간의 자료만 확인하거나, 확인할 수 없는 부분을 분명히 한 초안을 작성한다.
계약이 체결됐다는 말에서 재진행 승인·진행 일정까지 만들어내지 않는다.

### 6.3 11월 3일: 계약 체결과 재진행 지시

계약 체결과 재진행 지시를 각각 확인했다면 두 사건을 구분해 기록한다. 10/29 반려
이력을 지우지 않고, 11/3 변경 내용과 연결한다. 책임자의 재진행 지시만 확인됐다면
실제 작업 완료나 상대방 수신까지 자동으로 확정하지 않는다.

다음 업무에서 참고 이력은 다음처럼 표시할 수 있다.

> 10/29에는 계약 미체결 사유로 반려 안내했습니다. 11/3 기록에는 계약 체결과
> 재진행 지시가 확인됩니다. [시점별 근거 보기]

### 6.4 사용자의 정정

사용자가 "그 반려 지시자는 B가 아니라 C였어"라고 하면 정정을 자동 반영하되
근거를 사용자 정정으로 남긴다. "저장해도 될까요?"를 다시 묻지 않는다. 이전
자료와 충돌하는 경우 사용자 진술과 자료 기록을 구별하고, 무조건 원문을 지우거나
사용자의 정정을 모든 출처의 사실로 바꾸지 않는다. 이후 자동 추출이 이전 자료를
다시 읽어도 사용자 정정이 조용히 사라지지 않아야 한다.

## 7. 실패·불충분 상태의 사용자 경험

| 상황 | 안내와 다음 동작 | 피해야 할 결과 |
| --- | --- | --- |
| 관련 기록 없음 | 기존 기록을 찾지 못했음을 알리고 현재 자료로 가능한 작업을 진행 | 실제 과거 일이 없었다고 단정 |
| 관련성이 불확실하거나 다른 안건 가능 | 답을 바꾸는 대상 확인만 요청하거나, 적용 전 후보를 구별 | 다른 계약의 이력을 조용히 사용 |
| 필요한 기록 일부 누락 | 확인한 것과 부족한 부분을 나눠 진행 | 참고 기록이 완전한 업무 이력이라고 표현 |
| 기록 이후 상태 미관찰 | 마지막 확인 시점을 표시하고 현재 상태에 의존하는 판단만 좁게 확인 | 과거 반려를 오늘의 반려 상태로 단정 |
| 출처 사이 충돌 | 출처·시점·주장 차이를 제시하고 가능한 작업을 계속 | 최신 날짜 하나만으로 모든 충돌 해결 |
| 출처 접근 권한 불명·회수 | 정책에 따른 비노출·중지 상태를 적용하고 접근 불가를 필요한 범위에서 설명 | 요약을 먼저 보여준 뒤 원문 권한만 점검 |
| 원문 링크를 열 수 없음 | 링크 실패, 자료 삭제, 권한 문제를 확인된 만큼만 구별 | 링크 실패를 기록이 거짓이라는 뜻으로 처리 |
| 저장할 새 사실 없음 | 저장 건수나 성공 알림을 만들지 않고 작업을 마침 | 대화 전체 또는 초안을 불필요하게 보관 |
| 자동 저장 미완료·실패 | "작업 결과는 준비됐지만 새 기록은 저장하지 못했습니다"처럼 실제 상태를 표시 | 답변 생성 성공을 저장 성공으로 표현 |
| 종료 감지 불가 | 현재 세션의 휘발성 후보가 저장되지 않았다면 누락을 알림. 다음 진입에서는 이미 커밋된 기록만 정상 조회 | 창 닫음·응답 완료를 실제 발송·승인으로 해석하거나 보관하지 않은 후보를 복구했다고 주장 |
| 재시도·중복 종료 신호 | 같은 업무 사건의 중복 저장을 막고 결과를 일관되게 표시 | 같은 사실이 여러 독립 근거처럼 쌓임 |

확인 실패가 업무 전체를 항상 중단시키지는 않는다. 예를 들어 현재 재진행 여부를
확인하지 못해도 과거 안내의 정리, 중립적인 회신 초안, 필요한 확인 항목은 준비할
수 있다. 실제 발송·외부 시스템 변경은 사용자의 요청과 해당 호스트 권한을 따른다.

저장 실패의 재시도·복구를 위해 대화 원문을 숨겨 보관하는 설계를 도입하지 않는다.
어떤 최소 데이터가 언제 남을 수 있는지는 정책·기술 설계에서 정하고 사용자에게
설명한다. 자동 저장이 중지된 상태는 다음 작업에서도 정상 동작처럼 숨기지 않는다.

## 8. 기록 열람·정정·삭제

기록 목록은 작업·프로젝트·주제·공통 기준·관련 상대·시점을 기준으로 찾을 수
있어야 한다. 특정 거래처나 단일 안건이 없는 지표 정의·자료 위치도 찾고 재사용할
수 있어야 한다. 기본 목록에는
업무 요약과 확인 시점을 두고, 출처·주장 종류·변경 관계는 펼쳐볼 수 있게 한다.
"고급 사용자"만 고칠 수 있는 파일 편집을 사후 통제의 유일한 수단으로 삼지 않는다.

| 사용자 행동 | 필요한 결과 |
| --- | --- |
| 기록 보기 | 원래 근거, 확인 시점, 마지막 정정과 현재 사용 여부를 이해할 수 있음 |
| 내용 고치기 | 정정 대상과 적용 결과가 분명하고 이후 자동 추출이 조용히 되돌리지 않음 |
| 이번 작업에서만 제외 | 장기 삭제와 구분하고 이번 AI 작업에서의 적용 범위를 표시 |
| 삭제 | AI의 후속 선별에서 제외되는지, 보관 유예·파생물·백업에 무엇이 남는지 실제 정책대로 설명 |
| 삭제 후 같은 내용 재발견 | 자동 재수집 방지 또는 재허용 정책을 적용하며 조용히 부활시키지 않음 |
| 기능 중지·연결 해제 | 새 접근·자동 저장 중지와 기존 기록 처리 범위를 구분해 설명 |
| 기록 내보내기·인계 | 권한과 보관 정책이 허용하는 범위에서만 제공; 초기 범위 포함 여부는 제품 명세에서 결정 |

삭제된 주장의 재생성을 막는 표식도 민감정보나 재식별 단서가 될 수 있다. 완전
삭제·재수집 억제·복구 중 무엇을 제공하는지, 보존 기간과 조직 정책이 충돌하면
어떻게 알리는지는 명시적 설계 과제다. 현재 기획 단계에서 임의의 보관 일수나
"완전히 사라짐"을 약속하지 않는다. 기존 AI 대화에 이미 전달된 기록을 삭제할 수
있는지도 호스트별로 확인해야 하며, 라이브러리 삭제만으로 해당 대화가 지워졌다고
안내하지 않는다.

## 9. 접근성 및 방해 최소화

- 저장 성공·미확인·충돌을 색상만으로 구별하지 않고 짧은 상태 문구를 함께 쓴다.
- 작은 아이콘이나 토스트만을 저장 실패·권한 문제의 유일한 표시로 사용하지 않는다.
  관련 기록 화면이나 작업 상태에서 다시 확인할 수 있어야 한다.
- 기록 펼치기, 근거 열기, 수정·삭제, 실패 상태 확인은 키보드와 보조기술로 접근할
  수 있어야 한다. 조작 뒤 초점이 어디로 이동하는지도 명세한다.
- 화면 확대·저시력 환경에서 내용이 겹치거나 중요한 시점·출처가 사라지지 않도록
  한다. 기록 요약은 읽기 쉬운 문장으로 쓰며 내부 식별자를 전면에 노출하지 않는다.
- 비차단 알림은 작업 중 입력을 가로채거나 새 포커스를 빼앗지 않는다. 저장 성공은
  반복적으로 읽어주지 않고, 결과를 바꾸는 실패는 사용자가 인지할 수 있게 한다.
- "확인 필요"는 실제로 이번 작업을 바꾸는 누락과 연결한다. 모든 기록을 상시
  경고로 표시해 사용자가 경고를 무시하도록 만들지 않는다.

이 항목들은 구현 수용 기준이며 접근성 준수나 사용성 개선이 이미 확인됐다는
주장은 아니다.
