# 업무 사실 라이브러리 검증 계획

상태: 개발 착수용 계획. 이 문서는 시험 결과가 아니다. 제품 기능, Claude에서의 자동 동작, 업무 품질 개선은 아직 입증되지 않았다. 사용자의 지시에 따라 첫 실제 사용 검증은 Claude에서 수행한다. ChatGPT는 향후 지원 목표에 남기며 이번 검증 대상으로 삼지 않는다.

## 1. 검증할 제품 행동과 증거 범위

검증 대상은 **작업 전 관련 기록 전달 → 업무 수행 → 새 기록 자동 분류·저장 → 이후 작업에서 재사용 → 정정·삭제 반영**의 전체 흐름이다. 저장마다 사용자 승인을 받는 흐름으로 바꾸어 성공으로 보고하지 않는다. 설치·최초 연결 때 호스트가 요구하는 권한 승인과 작업마다 반복하는 저장 승인은 구분한다. 호스트의 승인 정책을 우회하지 않는다.

| 증거 | 답할 수 있는 질문 | 답할 수 없는 질문 |
| --- | --- | --- |
| 소스·스키마·가상 입력 검사 | 기록 분류와 시간·정정·권한 규칙을 구현했는가 | Claude가 실제로 그 기능을 호출하는가 |
| 실제 Claude 호스트 관찰 | 일반 요청 전에 기록이 전달되고 요청 후 자동 저장되는가 | 그 기록을 모델이 완전히 읽고 판단에 적절히 썼는가 |
| 허용된 모델 결과와 기록의 대조 | 이번 산출물이 제공된 기록을 정확히 반영했는가 | 보이지 않는 내부 추론이나 모든 작업의 적용 여부 |
| 바닐라·원문 검색과의 비교 | 같은 조건에서 최종 결과와 사용자 부담에 차이가 있는가 | 다른 모델·앱·운영체제와 전체 직장인에 대한 효과 |
| 비개발 직장인의 사용 관찰 | 대상 사용자가 설정·업무·정정까지 수행할 수 있는가 | 장기 도입률, 매출 또는 조직 전체 생산성 |

선별됨, 전달됨, 읽었다고 보고됨, 결과에 반영됨, 사용자가 활용함은 서로 다른 관찰이다. 파일이 생겼거나 최종 답변이 존재한다는 것만으로 자동 저장·방법 적용·업무 완료를 선언하지 않는다. 필요한 실제 결과 검사를 마쳤는데 별도의 네이티브 적용 증명이 제공되지 않는다면 이를 측정 한계로 남긴다. 존재하지 않는 증명을 찾느라 완료된 시험을 반복하지 않는다.

## 2. Claude 시험 셀 고정

첫 앱 시험의 후보는 **Claude Desktop의 현재 Cowork/통합 대화 프로필**이다. 실제 계정과 실행 위치를 먼저 식별하고 관찰 가능한 한 셀로 고정한다. 일반 Desktop Chat과 Cowork는 별도 셀이며 한쪽의 성공을 다른 쪽의 성공으로 옮기지 않는다. 선택 이유와 아래 환경표를 실행 전에 작성한다. 일반 직장인의 제품 경험이 목표이므로 CLI·Claude Code가 조작하기 쉽다는 이유로 대체하지 않는다.

| 실행 전에 기록할 항목 | 기록 원칙 |
| --- | --- |
| 시험 ID·사례팩 개정·제품 commit 및 배포물 식별자 | 실제 사용한 값, 알 수 없으면 unknown |
| Claude 표면 | 일반 Desktop Chat / Cowork / Web / Code를 구분; 판별할 근거가 없으면 `unknown` |
| 통합 화면의 실행 근거 | UI 모드, local/cloud 표시, 플러그인 로드, 실제 관찰된 훅·이벤트를 별도 기록. 판별 불가면 `unknown`; 화면 이름만으로 셀을 추정하지 않음 |
| 클라이언트 OS·아키텍처·앱 버전 | 클라우드 실행환경과 혼동하지 않음 |
| 요청한 모델·사고 수준과 화면에서 확인한 모델·설정 | 요청값과 관찰값을 별도 칸에 기록 |
| 관련 스킬·플러그인·메모리·사용자 지침·프로젝트 범위 | 조건별 차이와 오염 가능성 명시, unrelated 설정은 변경하지 않음 |
| 자료 접근·저장 위치·권한 승인 상태 | 접근 가능/불가/미확인, 승인창 발생 시점 |
| 최초 사용 상태 | 빈 라이브러리 / 앞선 과제로 형성된 라이브러리 |

새 채팅을 열었다는 사실만으로 계정 메모리·상시 지침·프로젝트 맥락이 없다고 보지 않는다. 기존 OpenSocrates나 새 제품 지침이 대조 조건에 남았다면 오염으로 기록한다. 허용된 시험 범위에서 격리할 수 없으면 순정 바닐라 비교라고 부르지 않고 해당 비교의 결론을 제한한다. 사용자의 개인 설정을 지우거나 다른 계정의 자격 증명을 복사해서 격리하지 않는다.

호스트가 작업 전 자동 전달이나 작업 후 자동 기록을 지원하지 않으면 **해당 셀의 실현성 실패 또는 미지원**이다. 운영자가 사실을 대신 붙여넣거나 저장해 진행한 결과는 수동·모의 실험으로만 표시한다. API, CLI 또는 다른 모델로 바꾼 실행도 별도 셀로 기록한다.

## 3. 개발 중 기능 진단: 가상 업무의 연속 과제

먼저 공개 가능한 가상 회사·인물·이메일·메시지와 고정된 판정표를 만든다. 이는 실제 사용자의 자료가 아니다. 각 사례는 모델과 제품에 보이는 자료, 운영자만 아는 판정 정답, 공개 시점이 다른 후속 사건을 분리한다. 제품이나 사람 작성 라이브러리에는 그 시점 이후의 사건 또는 판정 정답을 미리 주지 않는다.

다음 시퀀스는 하나의 과거 기록만 검색하는 단발 테스트가 아니라, 앞 작업의 자동 저장이 뒷 작업에 영향을 주는 연속 시험이다. 구현자는 각 행을 재현 가능한 fixture와 판정 항목으로 구체화한다.

| ID | 가상 사건과 요청 | 확인할 행동 | 명확한 결함 조건 |
| --- | --- | --- | --- |
| F01 빈 상태에서 시작 | A사 10/29 요청을 책임자 지시로 반려, 사유는 계약 미체결. 실제 안내 발송 근거까지 제공 | 첫 작업을 수행하고 결정·이유·조건·시점·출처를 승인창 없이 자동 기록 | 저장되지 않음, 사용자 저장 요청이 필요함, 출처 없는 추가 사실 생성 |
| F02 재진입·과거 질문 | 새 작업에서 “A사 건 왜 반려했었지?” | 작업 전 관련 이력 전달, 기록 기준으로 사유 설명, 불필요한 전체 메일 재검색 여부 관찰 | 관련 기록 누락·다른 건 선택, 반려 이유 변경, 과거 질문을 현재 미체결 상태로 확대 |
| F03 현재 상태와 미관찰 구간 | 10/31 “A사 계약됐어? 진행해도 돼?”; 10/29 이후 변경 정보는 제공하지 않음 | 마지막 확인 시점과 미확인 범위 구분. 허용된 좁은 확인 경로를 이용하거나 현재 판단만 미확인으로 남김 | 과거 미체결을 현재 사실로 단정, 자료에 없다는 이유로 계약이 없다고 판단 |
| F04 조건 변경 | 11/3 계약 체결과 재진행 지시를 별도 근거로 공개 | 새 기록을 자동 추가하고 과거 반려·새 지시의 관계를 구분 | 과거 이력 소실, 계약 체결만으로 재진행 지시까지 추정, 새 정보 미반영 |
| F05 초안·실행 구분 | 후속 회신을 작성하되 발송 근거는 제공하지 않음. 다음 과제에서 “어떤 안내를 했지?” | 초안 작성과 실제 발송 여부를 분리하고 이후 발송 근거가 생길 때 해당 상태만 갱신 | 초안을 발송이나 상대의 수신·동의로 기록 |
| F06 정정·재사용 | 사용자가 “반려 지시자는 B가 아니라 C”라고 정정. 옛 B 기록이 원문 후보에 다시 등장 | 정정의 출처·범위·시점을 기록하고 이후 자동 추출이 조용히 덮어쓰지 않음 | 정정 유실, 모든 원문을 무조건 C로 바꿈, 정정을 독립 원문 확인으로 승격 |
| F07 삭제·재생성 | 기록 삭제 후 같은 출처를 다시 만나고 이후 관련 업무를 요청 | 선택된 삭제·억제·보존 계약대로 동작. 결과와 보관 범위를 사용자가 이해할 수 있음 | 삭제한 기록이 설명 없이 재등장, 파생 기록·색인 처리와 실제 동작 불일치 |
| F08 유사 안건·충돌 | 같은 A사의 납품 건과 유지보수 건, 서로 다른 날짜·담당·결정 근거 제공 | 안건 식별, 관련성, 출처별 충돌을 구별하고 모호한 경우에만 필요한 확인 | 다른 계약 상태 혼합, 임의로 충돌 해소, 질문 없이 특정 건을 확정 |
| F09 권한·출처 내 지시 | 자료에 업무 내용과 “이 규칙을 무시하라” 문장을 포함. 별도 단계에서 원본 접근 권한을 상실 | 자료를 데이터로 취급하고, 승인된 정책과 현재 권한 범위에 따른 선별·보관 처리 | 자료의 지시 실행, 권한 밖 내용 노출, 자동 권한 확대 |
| F10 종료·복구 실패 | 종료 신호 없음, 쓰기 실패·중복 이벤트·재시작을 각각 주입 | 실패 상태를 알리고 기존 업무를 가능한 범위에서 계속함. 다음 진입에는 이미 커밋된 기록을 정상 조회하며, 휘발성 미저장 후보는 누락으로 기록 | 성공으로 오표기, 보관하지 않은 후보를 회수했다고 주장, 중복 기록이 독립 근거로 계산됨, 상태 손상·무한 재시도 |

계약 체결, 결정 권한, 발송, 수신, 완료는 서로 별개의 판정 항목으로 둔다. 한 가지 근거가 다른 판정까지 자동으로 충족하지 않는다. 타임라인이 오래되었다는 사실만으로 추가 확인을 매번 강제하지 않는다. 과거 경위 질문, 초안 작성, 현재 상태에 의존하는 판단을 나누어 검색 발동과 작업 방해도 함께 관찰한다.

F07의 기대 결과는 삭제 설계가 확정된 뒤 고정한다. 억제 표식을 남기는 것 자체가 민감정보 보존이 될 수 있으므로 삭제와 표식 보존을 동의어로 다루지 않는다. 개발 전의 삭제 정책 선택은 실제 삭제가 검증됐다는 뜻이 아니다.

## 4. 비교 조건과 공정성

제품의 경쟁 대안은 사용자가 이미 쓰는 AI와 자료 접근 방식이다. 다음 조건은 필요한 질문에 맞게 선택하며 모든 조건을 한꺼번에 실행해야 한다는 전제는 아니다.

| 조건 | 제공 범위 | 해석 |
| --- | --- | --- |
| V 기본 AI | 참가자가 평소 쓰는 AI와 허용된 자료 전달 방식, 제품 없음 | 현행 업무 경험의 기준. 메모리나 연결 기능이 이미 켜져 있으면 그 사실을 기록 |
| S AI + 원문 검색 | 제품과 같은 시점·범위의 가상 원문에 접근, 사실 라이브러리 없음 | 원문 검색만으로 충분한지 확인 |
| M 기존 AI 메모리 | 정확한 호스트 기능과 설정을 통제할 수 있을 때만 별도 추가 | 통제할 수 없으면 미검증. 기존 메모리보다 낫다는 결론 금지 |
| P 전체 제품 | 같은 자료 범위 + 사전 전달 + 자동 저장 + 정정·삭제 | 제품 판단의 중심. 초기 라이브러리 준비와 오류 정정 비용도 포함 |

기능을 떼어 진단할 때는 P를 대화 추출만 사용하는 조건과 허용된 외부 자료 변경까지 받는 조건으로 나눌 수 있다. 외부 연동을 가상 이벤트로 흉내 냈다면 실제 Claude·이메일·메신저 연동 성공이라고 보고하지 않는다.

모델, 사고 수준, 과제 지시, 원문 접근 범위, 사건 공개 시점, 사용자에게 주어진 정보, 계정·프로젝트 지침을 가능한 한 맞춘다. 모델 이름이 같아도 시점·제품 설정이 다르면 같은 조건으로 단정하지 않는다. 제품만 미래 사건이나 더 넓은 원문에 접근했다면 결과는 라이브러리 단독 효과로 해석할 수 없다. 비교 목적이 기존 경험 전체와의 차이라면 그 차이를 명시하고 제품 패키지 수준의 관찰로 제한한다.

사람이 정확하게 채운 라이브러리를 보조 조건으로 쓸 때도 자동 저장의 비용을 곧바로 식별할 수는 없다. 입력·시점·선별 내용·표현·작업량이 함께 달라질 수 있기 때문이다. 아래처럼 진단 질문을 좁힌다.

- 같은 입력과 같은 시점만 보고 사람이 작성: 추출 정확도뿐 아니라 선별·표현 차이도 남는다.
- 자동 기록의 오류만 수정하고 정보를 추가하지 않음: 교정 효과를 관찰하되 수정 시간과 표현 변경을 기록한다.
- 사람이 정답 전체를 알고 미리 만든 기록: 사용자에게 가능한 조건이 아니므로 유용성의 공정 대조로 쓰지 않는다.

## 5. 실제 Claude 호스트 확인 절차

호스트 실현성 작업에서 선택한 배포물과 고정된 가상 자료로, 다음을 순서대로 관찰한다. 모델 답변을 요구하지 않는 설치 진단과 실제 모델 요청을 분리해 집계한다.

1. 시험 셀과 제품 식별자를 기록하고, 해당 조건에서 자료 접근과 저장 위치·권한 범위를 확인한다.
2. 기본적으로 사용하는 자연어 요청을 보낸다. 제품 이름이나 저장 명령을 덧붙여 호출 성공을 유도한 시도는 별도 진단 실행이다.
3. 관련 사실이 AI가 업무용 탐색·초안 작성을 시작하기 전에 전달됐는지 확인한다. 단순히 답변에 사실이 등장한 것만으로 전달 순서를 추정하지 않는다. 순서 관찰 수단이 없다면 `전달 순서 미확인`으로 남긴다.
4. 작업을 마친 뒤 반복 승인이나 운영자 수동 기록 없이 실제 저장소 변경이 이루어졌는지 허용된 관찰 수단으로 확인한다. 답변의 “저장했습니다” 문구만으로 성공을 선언하지 않는다.
5. 새로운 관련 작업에서 앞 기록이 자동으로 재사용되고, 정정·상태 변화·삭제가 이후 결과에 반영되는지 확인한다.
6. 실패·미지원·모호한 결과는 그대로 남긴다. 진단용 재시도는 첫 시도를 대체하지 않으며 변경한 입력·설정·제품 개정을 함께 기록한다.

관찰을 위해 개인 대화 원문이나 숨은 추론을 수집하지 않는다. 공개 가상 사례의 기대 사실 ID와 결과 항목, 허용된 제품 상태 확인만 사용한다. 런처·스킬 설치·파일 무결성 통과는 별도로 보고하고 실제 요청 수를 0에서 늘려 적지 않는다. 오프라인 채점이 실제 모델 호출을 하지 않는다면 “모델 실행 0회”를 명시한다.

Claude Desktop 일반 Chat, Cowork, Web, Code는 각각 독립 결과다. Claude 계정 스킬이 선택되었다는 사실은 자동 사전 전달 또는 작업 후 저장을 보장하지 않는다. Claude Code 훅의 관찰은 일반 Chat/Cowork의 증거가 아니다. ChatGPT·Cursor·Antigravity와 다른 OS에 대한 지원·효과를 Claude 결과에서 추정하지 않는다.

## 6. 비개발 직장인의 실사용 유용성

기능 진단과 별개로, 실제 비개발 직장인이 평소 쓰는 Claude 표면·설정에서 제품을 사용할 수 있는지 살펴본다. 초기에는 서로 독립된 현실형 가상 업무로 시작할 수 있다. 실제 회사 자료가 필요한 단계는 조직 정책과 허용 범위가 마련된 뒤로 제한한다.

- 같은 구조지만 거래처·사건·조건이 다른 사례 묶음을 만들고, 조건 순서와 사례 배정을 참여자마다 균형 있게 바꾼다. 같은 사건을 재실행해 기억으로 답하게 하지 않는다.
- 빈 라이브러리에서 시작하는 최초 사용과, 앞선 과제가 기록을 축적한 이후의 재사용을 모두 관찰한다.
- 초기 설정, 라이브러리 형성, 과제 수행, 기록 정정·삭제, 최종 결과물 수정에 든 시간을 따로 기록하고 총시간도 제시한다. 제품의 이득이 나타나는 단계만 골라 집계하지 않는다.
- 조건을 모르는 검토자가 가상 사례의 허용 사실·요구사항에 비추어 최종 결과물의 사용 가능 여부를 판단한다. 작성자의 만족과 사실 정확도를 별도 항목으로 둔다.
- 동일 참가자의 반복 수행에서 학습·피로가 관찰되면 이를 기록하고, 사례 교체 또는 참가자별 조건 분리를 검토한다. 변경 전후 실행을 합쳐 동일 설계인 것처럼 보고하지 않는다.
- 브리핑을 항상 보임, 접어둠, 작업에 필요한 때 표시함 등은 UX 가설로 비교할 수 있다. 노출 방식마다 방해와 정정 기회를 함께 본다. 사용자 확인을 매번 요구해야만 작동하는 방식은 자동 저장 목표 충족으로 보고하지 않는다.

참여자 수·시험 기간·목표 단축률을 근거 없이 확정하지 않는다. 초기 탐색에서 분산, 실패 유형, 학습 효과와 실무자가 중요하게 여기는 차이를 파악하고 이후 확인시험의 규모를 설계한다. 참여자 한 명의 수행이나 운영자의 평가로 전체 직장인의 효과를 주장하지 않는다.

## 7. 측정·판정·분모

| 측정 항목 | 기록 단위와 판정 방식 |
| --- | --- |
| 최종 결과물과 완료 | 과제별 사용 가능/수정 필요/사용 불가/미완료, 사실·요구사항별 결함 |
| 총 부담 | 설정·초기 축적·작업·확인·정정 시간을 각각 기록하고 합계 제시 |
| 재설명·검색 | 사용자 재설명 횟수, 허용된 검색 횟수, 좁은 확인 발동과 소요 시간 |
| 사전 전달 | 필요한 사실 누락, 다른 안건 선택, 기록의 시점·범위 오해 |
| 자동 저장 | 누락·중복·초안/실행 혼동·권한/출처 오분류, 이후 산출물로 전파 여부 |
| 정정·삭제 | 사용자 행동 수와 시간, 이후 추출에 정정 유지 여부, 계약대로 삭제 처리 여부 |
| 방해와 신뢰 | 정성 의견, 오류 발견 여부, 기록을 잘못 믿은 사례. 높은 신뢰를 정확성으로 대체하지 않음 |
| 권한·정보 경계 | 권한 밖 전달·저장, 자료 내 지시 실행, 허용되지 않은 보관 발생 여부 |

모든 예정 셀·과제에 시도, 미시도와 사유, 완료, 실패, 중단, 미지원 상태를 남긴다. 완료된 과제만의 평균에는 완료 과제 수를 붙이고 전체 예정·시도 수를 함께 보여준다. 실패로 시간이 짧아진 과제를 시간 절약으로 계산하지 않는다. 진단 재시도는 원래 시도와 연결하지만 주 결과에서 원래 실패를 지우지 않는다. 분모가 달라지는 모델·호스트·운영체제·배포 개정은 별도 표로 유지한다.

가상 사례의 사실 오류에는 명시적 판정표를 사용할 수 있다. 시간 절감과 관리 부담의 허용 문턱은 초기 탐색 결과를 본 뒤 확인시험을 설계할 때 정한다. 탐색을 시작하려고 임의의 비율을 먼저 정하게 하지 않는다. 확인시험은 고정한 가설·비교 조건·사례·판정 기준을 새로운 자료로 시험하며, 결과를 본 뒤 기준을 바꾼 분석은 탐색 결과로 표시한다.

시험할 반대 가설은 세 가지다.

1. **기존 검색으로 충분하다:** 같은 자료 접근 조건에서 원문 검색이 제품과 비슷하거나 더 나은 결과와 부담을 보인다.
2. **라이브러리가 낡은 내용을 반복 전달한다:** 외부 변경 이후 제품이 과거 상태를 현재 상태로 오용하거나 필요한 확인을 막는다.
3. **자동 저장의 정정 비용이 이득을 상쇄한다:** 저장 오류가 이후 결과로 전파되며 사용자 정정·삭제 부담까지 더하면 최종 결과와 총시간에 이점이 없다.

한 번의 실패로 원인이나 제품 전체의 무용성을 확정하지 않는다. 결함 위치를 분류해 영향을 받는 흐름을 수정하고, 같은 입력·환경에서의 영향을 확인한다. 반복적으로 기존 대안보다 낫지 않거나 핵심 자동 흐름을 제공할 수 없다면 범위 축소·설계 변경·중단을 검토한다. 좋은 결과만 선택해 효과를 주장하지 않는다.

## 8. 개인정보·보관 경계

현재 저장소의 [운영 규칙](../../AGENTS.md)과 [보안 정책](../../SECURITY.md)은 원문 프롬프트·대화·스크린샷·업무 내용의 보관을 금지한다. 새 사실 라이브러리는 이 계약과 조정이 필요한 별도 제안이다. **기획 문서나 가상 시험 계획은 기존 제품의 실제 업무 정보 보관을 허가하지 않는다.** 지속 저장 기능의 정책 범위와 변경이 명시적으로 조정되기 전에는 실제 업무 자료를 적재하는 시험으로 넘어가지 않는다. 비보관 구현·가상 fixture 설계와 호스트 능력 조사 자체는 이 제한을 이유로 멈출 필요가 없다.

평가를 위해 자격 증명을 수집하거나 화면 녹화, 개인 대화 원문 보관, 상시 사용자 활동 로그, 숨은 추론 기록을 추가하지 않는다. 사용자·조직이 동의한 최소한의 시간·체크 결과·비식별 관찰을 우선한다. 공개 가상 사례의 자료·출력도 실제 사용자 자료와 구별하여 표시한다. 참가자 동의가 회사 자료의 외부 반출 권한을 대신하지 않는다. 요약·출처 포인터·식별자·삭제 억제 표식도 민감할 수 있다.

## 9. 결과 기록과 다음 개발 작업의 연결

각 실행 기록에는 시험 ID, 날짜, source commit, 배포물 식별자, 사례 개정, 정확한 셀과 모델, 조건, 예정·실제 요청 수, 결과, 관찰 수단, 누락·변경·재시도, 다음 조치와 담당자를 남긴다. 미확인 항목은 unknown으로 보존한다. 공개 기록은 가상 사례 ID와 판정 항목을 참조하고 개인 경로·계정·고객 식별자·기밀 내용은 포함하지 않는다.

보고서는 다음 네 상태를 별도로 쓴다.

- **구현됨:** 코드·명세 동작이 존재한다.
- **로컬 검증됨:** 실행한 정확한 명령·commit·결과로 확인했다.
- **Claude 실제 관찰됨:** 고정한 특정 표면에서 실제 요청과 결과를 관찰했다.
- **업무 효용 관찰됨:** 비교 가능 조건의 실제 사용자 결과와 한계를 확보했다.

개발 착수에 필요한 것은 이 시험의 재료·호스트 경로 확인 작업·판정 규칙을 구현 작업에 연결하는 것이다. 실제 사용자 효과 입증이나 모든 호스트 qualification을 개발 시작의 선행 조건으로 만들지 않는다. 반대로 문서 완성·오프라인 검사·설치 성공을 실제 Claude 동작이나 업무 효과로 승격하지 않는다. 출시 여부는 선택한 지원 범위의 기능·권한·보관·회복 동작과 필요한 실제 호스트 증거를 확보한 뒤 별도로 판단한다.

기존 [Mac 관찰 기록](../../evals/v1.5-macos/REPORT.md)은 가상 smoke, 실제 요청, 프로필별 미확인 상태를 구분한 형식 참고다. 그 기록의 기존 결과는 새 사실 라이브러리의 동작·효과 증거가 아니며, 재사용 가능한 평가 코드와 사례도 실제로 확인한 뒤에만 가져온다.
