# 업무 사실 라이브러리 기술 설계

상태: 개발 착수용 설계 제안. 작성 기준은 `origin/main`의
`d6b8ff1dc0dc7a51ebd5896a395ac39236e77d1c`이다. 이 문서는 새 런타임이나
영구 저장을 구현하지 않으며, 호스트 자동 동작이나 제품 효과를 검증했다는
뜻도 아니다. 첫 실제 사용 검증 환경은 사용자의 선택에 따라 **Claude**이다.

## 1. 구현 경계와 착수 순서

핵심 계약은 다음 두 동작의 연결이다.

1. 업무 요청을 받으면 관련 기록을 선별해 AI의 본 작업 전에 전달한다.
2. 작업에서 새로 확인된 보존 가치가 있는 사실을 분류해 매번 저장 승인을
   요구하지 않고 기록한다. 저장 이후 사용자는 열람·정정·철회·삭제할 수 있다.

현재 [AGENTS.md](../../AGENTS.md)는 `workspace-content retention`을 금지하고,
[SECURITY.md](../../SECURITY.md)는 대화·작업 자료를 보관하지 않는 기존 제품
계약과 Claude 어댑터의 transcript 미열람을 명시한다. 업무 내용을 지속
저장하려는 새 기능은 이 계약과 충돌한다. **이 설계 문서는 예외를 만들지
않는다.** 실제 업무 내용의 보관 구현을 보호된 `main`에 반영하기 전에, 새
제품 범위·최소 보관·사용자 통제·조직 정책·기존 사용자 영향이 명시된 별도
정책 변경과 코드·보안 검토가 필요하다. **현재 브랜치는 기획 문서만 담는다.**
정책 변경 전에도 이후 별도 개발 브랜치에서 실제 업무 내용을 일절 사용하지
않는 합성 fixture의 격리된 시험 저장·비보관 어댑터 실험을 진행할 수 있다.
시험 저장은 **독립 대화 사이에만 유지하고 시험 종료 시 정리**하는 방식으로,
실제 업무 정보의 지속 보관과 구분한다.
이것은 사용자·workspace 내용을 보관하지 않는 실험에 관한 해석이다. 실제 업무
내용을 지속 보관하는 기능을 현행 규칙에 반해 어느 브랜치에서든 추가하지 않으며,
정책 정합화 전에 실제 업무 보관·설치·출시를 허용한다는 뜻이 아니다. 최초
합성 시험 저장 전에 maintainer는 가상 자료의 출처·경로·정리 방식과 현재
정책의 정합성을 확인하고 판단을 기록한다.

착수 작업을 구분한다.

| 작업 | 지금 작성할 수 있는 산출물 | 다음 구현의 전제 |
| --- | --- | --- |
| 호스트 기능 확인 | Claude 표면별 공식 계약, 가상 입력의 호출·전달·쓰기 관찰 계획 | 실제 계정·호스트 권한 내에서 실험, 결과의 범위 기록 |
| 도메인·저장 계약 | 가상 기록 형식, 상태 전이, 오류와 수용 기준 | 영구 업무 보관 정책 정합화 후 별도 구현 PR |
| 실제 업무 시험 | 최소 수집과 데이터 접근 계획 | 사용자·조직이 허용한 자료·저장소·AI 전달 범위가 명확함 |
| 배포 | 설치·해제·복구 설계 | 해당 호스트와 플랫폼에서 구현 및 배포 검증 |

제품의 수요와 효과를 이미 입증하는 것은 개발 시작의 전제가 아니다. 다만
어떤 입력을 읽고 무엇을 저장할 수 있는지 모르는 상태에서 실제 업무 자료를
모으는 구현은 이 문서가 허용하지 않는다.

## 2. Claude 표면과 어댑터 계약

Claude 웹 Chat, Desktop 일반 Chat, Cowork, Claude Code는 같은 검증 셀이
아니다. 계정 스킬을 읽은 사실은 자동 선별이나 영구 쓰기를 입증하지 않고,
Claude Code의 hook 동작은 일반 Chat의 기능을 입증하지 않는다.

기존 소스의
[Claude native entry](../../src/opensocrates/hosts/claude/native.py),
[Claude hook CLI](../../src/opensocrates/cli/claude_hook.py),
[계정 스킬 템플릿](../../plugin-src/claude-chat/SKILL.md.tmpl)은 서로 다른
프로필의 입력이다. 이 경로의 존재만으로 새 사실 전달·저장을 재사용할 수
있다고 결론 내리지 않는다. 구체적인 재사용 판정은 실제 호출자·guard·응답
형식과 버전별 지원 계약을 함께 확인한다.

호스트 포트는 아래 능력을 각각 신고한다. `unknown`은 `false`나 성공이 아니다.

| 능력 | 필요한 관찰 | 미지원·미확인 시 처리 |
| --- | --- | --- |
| `before_task_delivery` | 사용자가 일반 업무를 요청한 뒤 본 작업 전에 관련 기록이 AI에 전달됨 | 그 표면에서 자동 사전 전달 지원을 주장하지 않음 |
| `structured_write` | 최초 권한 설정 이후 매번 저장 확인 없이 제한된 기록 쓰기가 수행됨 | 모델의 도구 호출 제안이나 파일 생성만으로 완료 처리하지 않음 |
| `task_boundary_signal` | 업무 종료·작업 전환 신호가 문서화되거나 실제 관찰됨 | 아래 사건 단위 저장·회수 대안을 별도로 측정 |
| `durable_store` | 독립된 새 대화에서 이전 기록이 접근 권한 안에서 재조회됨 | 같은 대화의 기억과 구분 |
| `source_access_check` | 현재 사용자·AI 전달 대상이 출처와 파생 기록을 쓸 권한이 있음 | 해당 기록을 제외하고 가능한 일반 작업은 계속 |
| `scoped_source_read` | 허용된 자료에서 필요한 안건·기간만 확인할 수 있음 | 현재 상태는 미확인으로 남기고 가능한 부분만 진행 |
| `record_management_surface` | 사용자가 기록·정정·삭제·저장 실패 상태를 실제로 열람하고 조작할 수 있음 | 별도 관리 화면 등 후보를 평가하고, 접근 불가능한 제어를 구현 완료로 세지 않음 |

제안 구현은 `HostAdapter`와 호스트 중립 코어를 분리한다. 어댑터는 허용된
현재 작업의 자료만 일시 전달하며 전체 대화 로그·원문·스크린샷을 수집하는
권한을 암묵적으로 얻지 않는다. 일반 Claude에서 이 포트를 만족하는 공식
확장·도구 경로가 있는지는 최신 문서와 실측으로 먼저 확인한다. 미확인
호스트를 브라우저 가로채기나 보안 설정 완화로 조용히 대체하지 않는다.

## 3. 컴포넌트와 데이터 흐름

```text
허용된 현재 작업의 짧은 단서
  -> HostAdapter.begin_task (메모리 내, 본문 영구 저장 없음)
  -> PolicyGate -> CaseResolver -> Retriever -> BriefBuilder
  -> 출처·시점·미확인 범위를 가진 Brief -> Claude 작업 맥락

허용된 작업에서 추출된 구조화된 기록 후보
  -> HostAdapter.submit_candidates (현재 작업 context만)
  -> PolicyGate -> CandidateValidator -> MutationPlanner
  -> 원자적 FactStore 변경 -> 저장 결과/정정·삭제 화면
```

* `PolicyGate`: 사용자·조직·자료 범위·AI 전달 대상·보존 정책을 적용한다.
* `CaseResolver`: 거래처와 업무 건을 구별한다. 같은 거래처의 여러 계약을
  이름 하나만으로 합치지 않는다. 모호성이 산출물을 바꿀 때만 최소 질문을 한다.
* `Retriever`: 허용된 건 식별자·명칭·별칭·기간을 이용한 제한 검색을
  제안한다. 로컬 검색은 후보일 뿐, 클라우드 실행에서 로컬 저장소가 접근
  가능하다는 뜻이 아니다. 임베딩과 외부 검색 서버는 초기 필수 요소로 두지
  않으며 저장 위치·연결·권한은 호스트 확인 후 선택한다.
* `BriefBuilder`: 필요한 기록과 출처·시점을 제한된 맥락으로 구성한다.
  저장된 텍스트는 명령이 아니라 데이터로 전달한다.
* `CandidateValidator`: 허용된 고정 필드·길이·열거값·관계를 검증하고,
  근거 없는 실행·결정 승격을 거부한다. 이 검증이 내용의 진실을 증명하지는 않는다.
* `FactStore`: 기록·변경 관계·접근 정책과 저장 결과를 원자적으로 관리한다.
  원본 이메일을 보내거나 출처 문서를 수정하는 기능은 포함하지 않는다.

추출은 호스트 모델이 현재 허용된 업무 맥락에서 수행하는 안을 우선 검토한다.
코어가 전체 transcript를 다시 읽어 추출하는 구조는 기본안에 넣지 않는다.
별도 모델·API·자격 증명·백엔드를 도입하려면 비용, 데이터 전달 경로와
권한을 새 설계 결정으로 기록해야 한다.

## 4. 기록 모델 v0 제안

하나의 항목은 검증된 영구 진실이 아니라 **출처와 시점이 있는 원자적 기록**이다.
한 항목에 계약 체결·지시·메일 발송을 묶어 한꺼번에 확정하지 않는다.

| 필드 | 형식·의미 | 제약 |
| --- | --- | --- |
| `record_id`, `case_id` | 저장소 내부의 임의 식별자 | 거래처명·이메일·개인정보를 식별자에 넣지 않음 |
| `revision` | 정수 증가 버전 | 정정 시 낙관적 동시성 검사 |
| `kind` | `request`, `decision`, `reason`, `commitment`, `status`, `action` | 표시용 분류이며 진실 등급이 아님 |
| `statement` | 필요한 최소 요약문 | 명령·실행 코드로 해석하지 않음 |
| `workflow_stage` | `draft`, `proposed`, `decided`, `executed`, `unknown` | 결정과 실행은 서로 다른 관찰, 원자 항목으로 분리 |
| `evidence_basis` | `source_observed`, `user_reported`, `ai_inferred`, `unverified` | 출처 관찰과 진실 검증을 혼동하지 않음 |
| `source_refs` | 출처 registry의 내부 참조 배열 | 사용자 진술이면 해당 작업의 최소 참조를 사용, 원문 로그 복제 금지 |
| `authority_basis` | `known`, `user_reported`, `unknown` 및 근거 참조 | 발화자가 결정권자라는 근거가 없으면 발언으로 표현 |
| `observed_at` | 시스템이 해당 근거를 확인한 시점 | 호스트 시계·시간대와 UTC 저장값을 구분 |
| `event_at` | 원문에 나타난 사건 시점 또는 `null` | 추측으로 채우지 않음 |
| `valid_from`, `valid_until` | 명시적으로 확인된 적용 구간 또는 `null` | `null`은 영구 유효가 아니라 모름 |
| `coverage` | 관찰한 경로·범위와 마지막 확인 경계 | ‘이후 변경 없음’과 ‘이후 관찰하지 못함’을 구분 |
| `relations` | `supersedes`, `corrects`, `contradicts`, `derived_from`의 `(record_id, revision)` 대상 | 동일 버전 자기참조·순환·다른 사용자 범위 참조를 거부. 같은 record의 이전 revision에 대한 정정은 허용 |
| `lifecycle` | `active`, `withdrawn`, `deleted_pending`, `purged` | 사용자가 볼 상태와 내부 보존 상태를 정책에 맞춰 구분 |
| `policy_ref` | 소유자·사용 범위·보존 정책 참조 | 권한 불명확한 항목은 전달 제외 |

`SourceRef`에는 공급자, 불투명한 locator, 자료 종류, 발화자 근거,
허용 범위와 마지막 접근 확인을 둔다. 메일 주소·문서 경로·locator도
기밀일 수 있어 공개 진단에 출력하지 않는다. 검증 수준을 올릴 때는 어떤
증거가 무엇을 확인했는지 적는다. 계약서 첨부를 봤다는 것만으로 계약 체결을
확정하지 않고, 메일 작성 완료만으로 발송을 확정하지 않는다.

## 5. 읽기·쓰기 API 의사 계약

아래는 구현할 경계를 보여주는 제안이며 현재 존재하는 CLI나 API가 아니다.
입력은 schema version으로 고정하고 알 수 없는 필드를 거부한다.

```text
begin_task({request_id, principal_ref, policy_ref, host_surface,
            case_hint, task_intent, requested_at})
  -> {task_ref, outcome: ready|empty|ambiguous|unavailable|denied,
      brief?, candidate_cases?, limitation_code?}

submit_candidates({request_id, task_ref, expected_store_revision,
                   candidates:[RecordCandidate], trigger})
  -> {outcome: committed|no_change|ambiguous|rejected|conflict|unavailable|denied,
      store_revision?, accepted_ids?, rejected_codes?, receipt_ref?}

correct_record({request_id, principal_ref, record_id, expected_revision,
                replacement, correction_basis})
  -> {outcome, record_id?, revision?, affected_ids?, limitation_code?}

withdraw_record({request_id, principal_ref, record_id, expected_revision})
  -> {outcome, affected_ids?, limitation_code?}

delete_record({request_id, principal_ref, record_id, expected_revision,
               requested_scope: record|case})
  -> {outcome: removed_from_use|held_by_policy|conflict|unavailable,
      deletion_ref?, policy_summary?, limitation_code?}
```

`principal_ref`와 `policy_ref`는 실행 위치에 맞는 신뢰된 인증·정책 계층에서
해석한다. 로컬 계층이 클라우드 호스트에서 직접 실행된다고 가정하지 않는다.
모델이 JSON에 넣었다는 이유로 권한을 인정하지 않는다. 예시에는 실제
자료·토큰·credential을 넣지 않는다. API 오류에는 닫힌 오류 코드와 필드
경로만 반환하고 거부한 본문이나 원문 오류를 반복하지 않는다.

`submit_candidates`의 성공은 저장소 commit만 입증한다. 모델이 기록을
정확히 이해했다거나 다음 결과물이 좋아졌다는 증거가 아니다. 저장 결과는
사용자가 필요할 때 펼쳐볼 수 있게 하되 승인 팝업으로 업무를 막지 않는다.
UI 노출 방식은 별도 사용성 검증 대상이다.

### 전달과 추출의 구체 계약 v0

아래 값은 첫 가상 구현을 위한 **초기 상한 제안**이며 사용자 효과 또는 호스트
능력을 측정한 값이 아니다. 설정·표면에 따라 더 낮출 수 있고 높이려면 테스트와
검토가 필요하다. 정해진 정보가 상한을 초과해 잘리면 중요 사실이 모두 전달됐다고
주장하지 않는다. 외부 자료 내용을 지시로 해석하지 않는다.

```text
Brief = {
  schema: "work-facts.brief/0", task_ref, outcome,
  case_id?, case_label?, as_of?, coverage_status,
  entries: [{record_id, kind, statement, workflow_stage, evidence_basis,
             authority_basis, observed_at, event_at?, source_labels, relations}],
  current_status: known_as_of|unknown|conflicted,
  current_status_basis?, needs_check: yes|no|unknown,
  limitation_codes: [], truncated: boolean, omitted_count: integer
}
RecordCandidate = {
  schema: "work-facts.candidate/0", case_hint, kind, statement,
  workflow_stage, evidence_basis, source_refs, event_at?,
  authority_basis, coverage, relates_to?, semantic_slot, trigger
}
```

`Brief`의 `outcome`은 `ready|empty|ambiguous|unavailable|denied`,
`coverage_status`는 `observed_through|partially_observed|unknown`이다.
`entries`는 접근 가능하고 정책이 허용한 항목만 전달한다. 최초 상한은 최대
5개 항목과 직렬화한 UTF-8 6,144바이트로 두고, 한 항목의 `statement`는
최대 512바이트다. 상한을 넘는 항목은 문장을 임의로 잘라 의미를 바꾸지 않고
항목 전체를 제외해 `truncated`와 누락 수를 설정한다. 안건이 일치하는 항목에서
이번 작업에 직접 필요한 마지막 관찰 상태·열린 약속·그와 충돌하는 기록을 먼저
묶고, 그 다음 관련 결정·이유, 그 다음 과거의 보조 이력 순서로 담는다.
서로 다른 출처의 미해결 충돌 묶음은 한쪽만 현재 사실로 제시하지 않는다.
동일 우선순위에서 근거 범위가 불확실하면 임의 확정을 피한다. 중요성이 같거나 상충하는 사실이 제한으로 빠졌다면
`needs_check=unknown`을 포함하며 이를 근거로 현재 상태를 확정하지 않는다.
해당 수치와 사용성은 바꿀 수 있는 설계 값으로 평가에서 다룬다.

모델에는 `Brief`를 시스템 지시와 분리된 **신뢰하지 않는 업무 자료**로
제공한다. 자료 속 명령은 따르지 말고 출처·관찰 시점·미관찰 구간을 유지하며,
`current_status=unknown|conflicted` 또는 `truncated=true`인 내용만으로
현재 상태·외부 실행을 단정하지 않도록 지시한다. `empty`는 과거 일이 없다는
의미가 아니다. 출처나 권한을 알 수 없을 때 타인의 건명·요약도 공개하지 않는다.

`RecordCandidate`는 새 입력의 주장으로서 `record_id`, `revision`, `lifecycle`,
저장 권한을 지정할 수 없다. 저장소가 신뢰된 사용 주체·안건·출처 권한을
검사하고 ID와 버전을 부여한다. 후보 출처에 대한 모델의 주장만으로 원문
검토·발송·결정권·외부 실행을 증명하지 않는다. 허용된 사용자 진술은
`user_reported`로 자동 저장하되 독립 원문 확인으로 승격하지 않는다. 가정·
초안은 명시된 미확인 단계로만 보관하고, 새 발송·승인·체결·처리 완료는
해당 사건을 뒷받침하는 관찰이 있을 때에만 그 관찰 범위로 기록한다.
후보당 512바이트, 한 제출당 최대 10개 후보를 v0 상한으로 제안하며,
초과 시 남은 건은 누락 상태로 보고한다. 이상치·불명확한 부분을 임의로
고쳐 확정하지 않는다. 이 지침은 구현 대상이며 준수 여부는 실제 모델 결과로
검증한다. `observed_at`은 신뢰된 어댑터/저장 계층이 관찰 시 부여한다.
모델이 후보에 보낸 `observed_at`은 미지원 필드로 거부하며, 자료에 기재된 시점은 별도로
`event_at`에 근거와 함께 기록한다.

## 6. 작업 진입과 종료 처리

### 시작

1. 정책과 전달 대상 AI 환경을 검사한다. 정책이 허용한 기록만 조회한다.
2. 요청 단서로 건을 식별한다. 모호하면 관련 후보만 짧게 제시한다.
3. 관련 기록의 관계·정정·철회·삭제 상태를 적용한다.
4. 마지막 확인 시점과 미관찰 범위를 포함한 brief를 만든다.
5. 본 작업보다 먼저 전달됐는지를 어댑터 증거와 구별해 확인한다. AI가 이미
   답을 작성한 뒤 관련 기록을 제시하면 사전 전달 성공으로 세지 않는다.
6. 현재 상태가 이번 행동을 바꿀 때에만 허용된 좁은 경로의 추가 확인을
   고려한다. 확인 불가 시 과거 경위·조건부 초안 등 가능한 작업은 계속한다.

### 저장

호스트의 종료 이벤트가 실제 업무 완료를 뜻한다고 가정하지 않는다. 다음
신호를 각각 측정한다: 명시적 작업 완료와 확인 가능한 업무 사건. 다음 작업
진입 시 이미 커밋된 기록은 정상 조회한다. 유휴 시간만으로 메일 발송이나
업무 완료를 추론하지 않는다.

원래 요구는 작업 후 자동 저장이다. 관찰된 사건에서 얻은 구조화 후보는 정책이
허용하는 경우 즉시 커밋하거나, 현재 프로세스의 휘발성 메모리에만 보류해 종료
신호에 커밋한다. 종료 신호 없이 프로세스가 사라지면 휘발성 후보는 회수할 수
없다. 다음 진입에는 이미 커밋된 기록을 정상 조회하며, 별도의 미커밋 후보를
회수하거나 변환했다고 표시하지 않는다. 미커밋
후보의 지속 대기열과 이전 대화 원문 재열람은 v0 기본안에 포함하지 않는다.
둘 다 불가능하면 `save_not_observed`/`unavailable`로 표시하고 누락을 보고한다.
사건 단위 저장은 업무 완료 감지와 같지 않으며 실제 지원 및 성공률을 별도
측정한다. 저장 후보가 없으면 `no_change`가 정상 결과다. 쓰기 불가나 거부는
저장됨으로 표시하지 않고 현재 업무를 가능한 범위에서 이어간다.

## 7. 정정·충돌·삭제의 상태 전이

* **정정:** 같은 `record_id`의 revision을 원자적으로 증가시키고, 그 새 버전이
  이전 revision을 `corrects`로 참조한다. 사용자 정정도 출처의 하나로 표시하며
  제3자의 접근 권한이나 과거 원문을 임의 변경하지 않는다.
* **상태 변경:** 10월 29일 반려와 11월 3일 재진행이 각각 확인됐다면
  `supersedes`로 현재 관찰 경계를 갱신한다. 이전의 반려를 틀린 기록으로
  지우지 않는다. 재진행 지시를 실제 착수나 완료로 승격하지 않는다.
* **충돌:** 같은 시점·안건에서 출처가 다르면 `contradicts`로 남긴다.
  최신 날짜 하나만으로 권한·정확성이 우선한다고 결정하지 않는다. 작업에
  영향을 주는 충돌만 사용자에게 짚고 관련 없는 부분은 진행한다.
* **철회:** 사용 대상에서 즉시 제외하고 파생 brief와 색인을 무효화한다.
* **삭제:** 먼저 조회·AI 전달에서 제외한다. 원본, 기록, 파생 정보, 색인,
  백업과 삭제 재생성 방지 정보가 각각 어떻게 처리되는지 정책으로 정한다.
  ‘휴지통으로 이동’과 ‘완전 삭제’를 같은 상태로 표시하지 않는다.

**재추출 대응:** `MutationPlanner`는 신뢰된 저장소 범위 안의 `case_id + kind +
origin_source_ref의 불투명 ID + semantic_slot`을 대응 후보 키로 사용한다.
`origin_source_ref`는 최초 기록을 뒷받침한 출처의 불투명 ID로서 정정이 새
`source_refs`를 추가하더라도 변경하지 않는다. `semantic_slot`은 모델이 자유롭게
명명하지 않고 도메인 담당자가 schema에서 관리하는 닫힌 v0 값이다:
`request.subject`, `decision.action`, `decision.actor`, `reason.cause`,
`commitment.terms`, `status.state`, `action.execution`. `kind`와 접두부가
일치하지 않거나 슬롯·원 출처·안건이 없으면 저장소가 `ambiguous`로
확정 변경을 보류한다. 하나의 슬롯에 여러 독립 사건이 가능한 경우에도
보조 사건 식별 근거가 없으면 별도 항목으로 조용히 생성하지 않는다.
문장 값이나 외부 고객명을 키에 직접 넣지 않는다.

같은 원 출처·안건·슬롯에 사용자 정정이 없는 기존 기록이 있을 때, 후보의
주장·단계·근거 구분이 기존 기록과 정확히 같으면 `no_change`를 반환한다.
문자열 동일성은 Unicode NFC 정규화와 양끝 공백 제거만 적용해 판정하며,
달라진 표현을 같은 의미로 추측하지 않는다. 동일 키의 내용·단계·근거가
달라졌는데 독립적인 새 사건이나 사용자 정정 근거가 없다면 `ambiguous`로
보류하고 기존 기록을 덮어쓰지 않는다.

새 후보가 같은 원 출처·안건·슬롯의 사용자 정정 이전 주장으로 판별되면
정정된 revision을 유지하고 `no_change`를 반환한다. 예: B의 반려 지시로
기록된 항목을 사용자가 C로 정정한 뒤 옛 B 원문이 같은 키로 재추출되면,
기록은 C 정정 상태로 남고 B를 새 항목이나 새 근거로 만들지 않는다. 새로운
독립 출처나 이후 사건이 같은 슬롯에 들어오면 새 사건 또는 충돌로 기록하되
자동으로 정정을 지우지 않는다. 여러 항목과 매칭되거나 안건·원 출처·슬롯을
신뢰성 있게 정할 수 없으면 `ambiguous`로 확정 변경을 보류하고 저장 상태를
알린다. `request_id`는 같은 호출의 재시도만 막으며 다른 호출의 의미상
재추출 판정 대신 사용하지 않는다. 출처 식별자와 슬롯 역시 민감할 수 있어
조직 정책과 삭제 범위를 따른다.

재생성 억제 표식도 locator·hash 등을 통해 민감정보나 재식별 단서가 될 수
있다. 최소 표식의 형식·보존기간·원본 변경 후 동작을 확정하기 전에는
‘삭제하면 절대로 다시 생성되지 않는다’는 보장을 하지 않는다. 정책이
완전 삭제와 억제 표식 보존을 동시에 허용하지 않으면 이 충돌을 공개하고
자동 재수집 제외 범위 등 대안을 정한다.

## 8. 저장소·권한·복구 제안

초기 구현 후보는 사용자 또는 조직이 지정한 단일 저장소를 사용하는
호스트 중립 코어이다. 로컬 SQLite 등 transactional 저장소와 OS 보안
저장소의 키 관리 조합은 **후보**이며, 암호화 backend·지원 플랫폼·조직
복구 정책이 정해지기 전 구현 기본값으로 확정하지 않는다. 평문 fallback은
만들지 않는다. 키가 잠기거나 접근이 거부되면 `unavailable`로 남긴다.

저장 데이터와 검색 색인은 같은 기밀 범위로 취급한다. 로컬 저장만으로
보안을 보장하거나 회사 정책 검토가 불필요해지는 것은 아니다. 원문 접근이
회수되거나 정책 확인이 불가능한 기록은 기본 전달 대상에서 제외하는 안을
검토한다. UI가 기록의 존재만 노출해도 누출일 수 있으므로 오류에 건명·내용을
넣지 않는다. 개인·팀 공유와 동기화는 초기 포트와 분리한다.

각 변경은 `request_id`를 사용해 같은 요청의 재시도를 한 번만 반영한다.
중복 판정 자료도 민감정보로 취급하며 공개 hash 로그를 만들지 않는다.
정정·삭제는 `expected_revision`과 store revision을 검사한다. 오래된
세션의 자동 저장이 새 정정을 덮어쓰지 못하게 충돌을 반환한다. 디스크 부족,
중단, 경합 시에는 전체 transaction을 rollback하고 일부 기록을 성공으로
보이지 않는다. commit 후 응답이 끊긴 재시도는 기존 결과를 돌려준다.

운영 진단은 버전·결과 코드·건수와 비식별 시간 정도로 제한하는 설계를
우선한다. raw prompt, transcript, screenshot, 원문·전체 경로, credential,
숨겨진 추론을 로그나 crash report에 넣지 않는다. 원격 telemetry는 초기
설계의 필수 요소가 아니며 별도 도입 결정 없이 추가하지 않는다.

## 9. 설치·해제·업데이트 제안

새 라이브러리 저장소는 기존 OpenSocrates 설치나 사용자 설정과 분리한다.
설치 과정이 과거 대화를 자동 수집하거나 기존 history를 가져오지 않는다.
최초 설정에서 저장 범위와 AI 전달 대상, 조직 정책과 사용자 통제를 설명하고
필요한 host trust flow를 따른다. **최초 기능 활성화와 매 작업의 저장 승인은
다르다.** 정상 활성화 이후의 각 기록 저장은 제품 목표대로 자동이어야 한다.

업데이트는 저장소 schema version과 어댑터 version을 별도 관리한다.
migration 전 정책상 허용된 보호 백업을 만들고 실패 시 복구한다. 백업이
삭제 요구와 충돌하지 않도록 위치·보존 상태를 노출한다. 이전 프로그램이
새 schema를 해석하지 못하면 쓰기를 멈추며, rollback했다고 새 데이터를
조용히 잃거나 평문 export하지 않는다.

연동 끄기, 프로그램 제거, 기록 삭제를 서로 다른 행동으로 정의한다.
연동을 끄면 더 이상 읽고 쓰지 않는다. 제거 시 라이브러리의 처리 방식을
명확히 보여 주고, 사용자 의도 없이 삭제나 과거 버전으로의 데이터 복제를
하지 않는다. 실제 설치 파일·서명·업데이트 자산과 배포 채널은 플랫폼 선택
후 별도 배포 명세로 확정한다.
