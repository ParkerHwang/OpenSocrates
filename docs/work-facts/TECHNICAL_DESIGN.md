# 업무 사실 라이브러리 기술 설계

상태: 개발 착수용 설계 제안. 작성 기준은 `origin/main`의
`d6b8ff1dc0dc7a51ebd5896a395ac39236e77d1c`이다. 이 문서는 새 런타임이나
영구 저장을 구현하지 않으며, 호스트 자동 동작이나 제품 효과를 검증했다는
뜻도 아니다. 첫 실제 사용 검증 환경은 사용자의 선택에 따라 **Claude**이다.

## 1. 구현 경계와 착수 순서

핵심 계약은 다음 두 동작의 연결이다.

1. 업무 요청을 받으면 관련 기록을 선별해 AI의 본 작업 전에 전달한다.
2. 작업에서 새로 확인된 보존 가치가 있는 사실을 분류해 매번 저장 승인을
   요구하지 않고 기록한다. 저장 이후 사용자는 열람·정정·철회·삭제할 수 있다.

현재 [AGENTS.md](../../AGENTS.md)는 `workspace-content retention`을 금지하고,
[SECURITY.md](../../SECURITY.md)는 대화·작업 자료를 보관하지 않는 기존 제품
계약과 Claude 어댑터의 transcript 미열람을 명시한다. 업무 내용을 지속
저장하려는 새 기능은 이 계약과 충돌한다. **이 설계 문서는 예외를 만들지
않는다.** 실제 업무 내용의 보관 구현을 보호된 `main`에 반영하기 전에, 새
제품 범위·최소 보관·사용자 통제·조직 정책·기존 사용자 영향이 명시된 별도
정책 변경과 코드·보안 검토가 필요하다. **현재 브랜치는 기획 문서만 담는다.**
정책 변경 전에도 이후 별도 개발 브랜치에서 실제 업무 내용을 일절 사용하지
않는 합성 fixture의 격리된 시험 저장·비보관 어댑터 실험을 진행할 수 있다.
시험 저장은 **독립 대화 사이에만 유지하고 시험 종료 시 정리**하는 방식으로,
실제 업무 정보의 지속 보관과 구분한다.
이것은 사용자·workspace 내용을 보관하지 않는 실험에 관한 해석이다. 실제 업무
내용을 지속 보관하는 기능을 현행 규칙에 반해 어느 브랜치에서든 추가하지 않으며,
정책 정합화 전에 실제 업무 보관·설치·출시를 허용한다는 뜻이 아니다. 최초
합성 시험 저장 전에 maintainer는 가상 자료의 출처·경로·정리 방식과 현재
정책의 정합성을 확인하고 판단을 기록한다.

착수 작업을 구분한다.

| 작업 | 지금 작성할 수 있는 산출물 | 다음 구현의 전제 |
| --- | --- | --- |
| 호스트 기능 확인 | Claude 표면별 공식 계약, 가상 입력의 호출·전달·쓰기 관찰 계획 | 실제 계정·호스트 권한 내에서 실험, 결과의 범위 기록 |
| 도메인·저장 계약 | 가상 기록 형식, 상태 전이, 오류와 수용 기준 | 영구 업무 보관 정책 정합화 후 별도 구현 PR |
| 실제 업무 시험 | 최소 수집과 데이터 접근 계획 | 사용자·조직이 허용한 자료·저장소·AI 전달 범위가 명확함 |
| 배포 | 설치·해제·복구 설계 | 해당 호스트와 플랫폼에서 구현 및 배포 검증 |

제품의 수요와 효과를 이미 입증하는 것은 개발 시작의 전제가 아니다. 다만
어떤 입력을 읽고 무엇을 저장할 수 있는지 모르는 상태에서 실제 업무 자료를
모으는 구현은 이 문서가 허용하지 않는다.

## 2. Claude 표면과 어댑터 계약

Claude 웹 Chat, Desktop 일반 Chat, Cowork, Claude Code는 같은 검증 셀이
아니다. 계정 스킬을 읽은 사실은 자동 선별이나 영구 쓰기를 입증하지 않고,
Claude Code의 hook 동작은 일반 Chat의 기능을 입증하지 않는다.

기존 소스의
[Claude native entry](../../src/opensocrates/hosts/claude/native.py),
[Claude hook CLI](../../src/opensocrates/cli/claude_hook.py),
[계정 스킬 템플릿](../../plugin-src/claude-chat/SKILL.md.tmpl)은 서로 다른
프로필의 입력이다. 이 경로의 존재만으로 새 사실 전달·저장을 재사용할 수
있다고 결론 내리지 않는다. 구체적인 재사용 판정은 실제 호출자·guard·응답
형식과 버전별 지원 계약을 함께 확인한다.

호스트 포트는 아래 능력을 각각 신고한다. `unknown`은 `false`나 성공이 아니다.

| 능력 | 필요한 관찰 | 미지원·미확인 시 처리 |
| --- | --- | --- |
| `before_task_delivery` | 사용자가 일반 업무를 요청한 뒤 본 작업 전에 관련 기록이 AI에 전달됨 | 그 표면에서 자동 사전 전달 지원을 주장하지 않음 |
| `structured_write` | 최초 권한 설정 이후 매번 저장 확인 없이 제한된 기록 쓰기가 수행됨 | 모델의 도구 호출 제안이나 파일 생성만으로 완료 처리하지 않음 |
| `task_boundary_signal` | 업무 종료·작업 전환 신호가 문서화되거나 실제 관찰됨 | 아래 사건 단위 저장·회수 대안을 별도로 측정 |
| `durable_store` | 독립된 새 대화에서 이전 기록이 접근 권한 안에서 재조회됨 | 같은 대화의 기억과 구분 |
| `source_access_check` | 현재 사용자·AI 전달 대상이 출처와 파생 기록을 쓸 권한이 있음 | 해당 기록을 제외하고 가능한 일반 작업은 계속 |
| `scoped_source_read` | 허용된 자료에서 필요한 안건·기간만 확인할 수 있음 | 현재 상태는 미확인으로 남기고 가능한 부분만 진행 |
| `record_management_surface` | 사용자가 기록·정정·삭제·저장 실패 상태를 실제로 열람하고 조작할 수 있음 | 별도 관리 화면 등 후보를 평가하고, 접근 불가능한 제어를 구현 완료로 세지 않음 |

제안 구현은 `HostAdapter`와 호스트 중립 코어를 분리한다. 어댑터는 허용된
현재 작업의 자료만 일시 전달하며 전체 대화 로그·원문·스크린샷을 수집하는
권한을 암묵적으로 얻지 않는다. 일반 Claude에서 이 포트를 만족하는 공식
확장·도구 경로가 있는지는 최신 문서와 실측으로 먼저 확인한다. 미확인
호스트를 브라우저 가로채기나 보안 설정 완화로 조용히 대체하지 않는다.

## 3. 범용 업무 지원과 데이터 흐름

코어는 비개발직군의 **모든 일반 사무직군**이 하는 업무를 대상으로 한다.
문서, 회의, 조사, 기획, 분석, 일정·운영, 판단, 업무 소통은 예시이며 허용
직무 목록이 아니다. 거래처·계약은 한 검증 사례다. 라이브러리는 AI의 맥락을
지원하는 구성요소다. 새 업무이거나 기록·저장할 사실이 없어도 작성·탐색·분석·
창의적 제안·사고 지원을 계속하며, 라이브러리가 업무 기능을 제한하지 않는다.

```text
허용된 현재 작업의 짧은 단서
  -> HostAdapter.begin_task (본문 영구 저장 없음)
  -> PolicyGate -> ContextResolver -> Retriever -> BriefBuilder
  -> 출처·시점·적용 범위·미확인 부분을 가진 Brief -> Claude 일반 업무 수행

허용된 현재 작업에서 추출한 구조화 후보
  -> HostAdapter.submit_candidates
  -> PolicyGate -> CandidateValidator -> IdentityResolver -> MutationPlanner
  -> 원자적 FactStore 변경 -> 저장 결과/정정·삭제 화면
```

* `PolicyGate`: 사용자·조직·자료·AI 전달 대상·보존 정책을 적용한다. 같은
  프로젝트나 조직에 속한다는 의미 연결을 열람 권한으로 해석하지 않는다.
* `ContextResolver`: 업무 건뿐 아니라 프로젝트·주제·문서·자료 묶음·조직·역할·
  업무 선호의 적용 범위를 식별한다. 같은 이름의 문서·다른 기간의 지표·동명이인을
  합치지 않는다. 모호성이 이번 결과를 바꿀 때만 필요한 질문을 한다.
* `Retriever`: 허용된 여러 맥락의 ID·명칭·별칭·기간·주제 역할을 검색한다.
  특정 업무 건 ID가 없어도 기준·정의·수치·자료를 찾는다. 로컬 검색·임베딩·
  원격 검색은 후보이며 어느 것을 선택할지는 실행 위치·권한 확인 후 정한다.
* `BriefBuilder`: 필요한 기록과 출처·시점·적용 범위를 제한된 맥락으로 전달한다.
  기록·선호·외부 기준을 시스템 지시나 사용자 권한으로 승격하지 않는다.
* `CandidateValidator`: 고정 코어 envelope와 등록된 데이터 확장·길이·관계를
  검사한다. 새 분류라는 이유로 정상 사실을 버리지 않고 범용 기록으로 받을 수
  있다. 이 검사는 내용의 진실을 증명하지 않는다.
* `IdentityResolver`·`MutationPlanner`: 중복·정정·충돌·이후 사건의 대응을
  판단한다. 불명확하면 **기존 기록 변경을 보류**하고, 같은 출처 구간의
  정정·철회·삭제 이력과 보관 권한을 확인한다. 해당 보호 이력과 겹치지
  않는 것이 확인된 허용 후보만 미해결 관계의 별도 기록으로 보존한다.
  금지 보관, 이력 확인 불가 또는 근거 없는 확정 승격은 자동 저장하지 않는다.
* `FactStore`: 기록·맥락 연결·변경·접근 정책을 원자적으로 관리한다. 메일 발송·
  문서 수정 등 외부 행동은 별도 사용자 요청과 호스트 권한을 따른다.

`PolicyGate`는 명시적으로 허용된 정보 범위만 저장하도록 설계한다. 정책이
정해지지 않았거나 자료의 보관 권한·민감도를 판단하지 못할 때는 해당 후보를
저장하지 않고 사유를 비공개 상태 코드로 표시한다. 이름·직무가 비개발 사무직이라는
이유로 업무 지원을 중단하지 않는다. 권한이 허용한 현재 자료를 일시적으로
분석하고 결과물을 만드는 것과 그 내용을 자동으로 보관하는 것은 별개다.

합성 fixture의 기본 제외 집합 초안은 비밀번호·접근 토큰·인증 정보, 제3자의
비공개 연락처·식별 정보, 개인별 인사·성과 평가, 건강·금융 등 민감 내용,
보관 금지로 표시된 자료다. 허구의 식별자를 이용해 제외 동작을 시험한다.
**실제** 저장 범주와 예외는 사용자·조직 정책 및 T00b에서 결정하며 이 목록은
업무 처리 자체의 금지 목록이나 법적 판단이 아니다. 인사·재무 등 직무도
사용 대상에 포함하고, 기록이 제한되면 그 사유를 숨기지 않으면서 허용된
범위의 업무는 계속한다. 키워드만으로 민감도를 완전하게 식별했다고 가정하지
않고 범위 불명이면 보관하지 않는다.

추출은 호스트 모델이 현재 허용된 업무 맥락에서 수행하는 안을 우선 검토한다.
코어가 전체 transcript를 다시 읽어 축적하는 구조는 기본안에 넣지 않는다.
별도 모델·API·백엔드는 비용·전달 경로·권한을 새 설계 결정으로 기록한다.

## 4. 범용 기록·맥락 모델 v0 제안

하나의 항목은 출처·시점·적용 범위가 있는 원자적 기록이다. 저장됐다는 이유로
영구적 진실이나 현재 상태가 되지 않는다. 확인한 사실, 원문상 주장, 사용자
선호, 진행 중 이슈, 가정과 AI 제안을 구별한다. 아이디어를 냈다는 사실과 그
아이디어가 채택됐다는 사실도 다르다.

### 맥락과 대상

`ContextRef`는 불투명 ID, 종류(`work_item`, `project`, `topic`, `document`,
`resource_set`, `organization`, `role`, `user_preference_scope`, `other`), 표시명·
별칭·적용 범위와 신뢰된 권한 참조를 갖는다. 한 기록은 여러 `scope_refs`와
연결될 수 있다. 예를 들어 공통 보고 기준은 여러 프로젝트, 조사 결과는 보고서와
기획에 함께 관련된다. `subject_refs`는 기록이 말하는 대상이고 `scope_refs`는
적용·검색 맥락이다. 의미 연결은 권한 부여의 증거가 아니며 전달 권한을 별도 검사한다.

단순 `scope_refs` 목록은 기본적으로 **모두 충족해야 하는 적용 제약(all_of)**이며
권한 또는 적용 범위의 OR로 해석하지 않는다. 여러 프로젝트에 공통으로 적용할
경우에는 명시적인 `scope_expression`을 사용한다. 예:
`all_of(조직 O, any_of(프로젝트 P1, 프로젝트 P2))`. 서로 무관한 맥락을 임의로
OR 연결하지 않는다. 확인되지 않은 범위 조건은 자동으로 넓히지 않는다.
적용 표현이 참이어도 자료·기록·사용자·전달 대상 AI의 권한은 각각 검사하며,
여러 출처로 만든 요약은 사용한 출처들의 허용 범위 교집합을 따른다. 접근 불가
출처의 존재·내용을 노출하지 않으며, 접근 가능한 출처만으로 독립적으로 지지되는
부분은 별도 기록으로 재구성한 경우에만 전달할 수 있다.

고유 업무 건이 없어도 저장할 수 있다. 연결이 불명확하면 신뢰된 사용자·자료
범위 안에서 보관 권한과 보호 이력에 겹치지 않음이 확인된 경우에만
`unresolved`로 보존하고 검색 시 한계를 표시한다. 임의로 조직 전체·
다른 프로젝트에 적용하지 않는다. 출처·기간·대상·값이 다른 기록을 제목이나
거래처명이 같다는 이유로 합치지 않는다.

| 필드 | 형식·의미 | 제약 |
| --- | --- | --- |
| `record_id`, `revision` | 내부 임의 ID와 증가 버전 | 실제 이름·이메일을 ID에 넣지 않음. 정정 시 동시성 검사 |
| `scope_refs`, `subject_refs` | 적용·검색 맥락 배열과 대상 배열 | 단일 계약 건 강제 없음. 미해결 연결과 권한 불명 구분 |
| `scope_expression` | 신뢰된 맥락 ID를 사용하는 `all_of`/명시적 `any_of` 적용 표현 | 생략한 목록은 all_of. 적용 조건을 접근권한으로 사용하지 않음 |
| `record_type` | versioned registry의 분류 참조 | 표시·검색용이며 진실·권한 등급이 아님 |
| `statement` | 필요한 최소 요약 | 원문·산출물 전체 복제 또는 명령·코드 실행 금지 |
| `predicate_ref`, `topic_role` | 등록 속성 또는 범용 주제 역할 | 자유 문구는 데이터이며 등록 코드·명령이 아님 |
| `workflow_stage` | `draft`, `proposed`, `decided`, `executed`, `not_applicable`, `unknown` | 정의·자료·측정값에 실행 단계를 강제하지 않음 |
| `evidence_basis` | `source_observed`, `user_reported`, `ai_inferred`, `unverified` | 원문 관찰과 진실 검증을 혼동하지 않음 |
| `verification` | 확인 범위·방법의 참조 또는 `unverified` | 모델 선언만으로 검증됨 승격 금지 |
| `source_refs`, `origin_evidence_ref` | 출처 배열과 최초 주장 근거의 불투명 출처·구간 참조 | 원문 로그 복제 금지. 같은 문서의 여러 주장 구분 |
| `authority_basis` | 결정·정책·절차의 권한 근거 또는 `not_applicable`, `unknown` | 근거 없이 발언을 결정·규칙으로 승격하지 않음 |
| `observed_at`, `event_at` | 시스템 관찰 시점과 자료상 사건 시점 또는 `null` | 모델은 관찰 시점을 정하지 못함. 사건 시점 추측 금지 |
| `valid_from`, `valid_until`, `reference_period` | 확인된 적용 구간·수치 기준 기간 또는 `null` | `null`은 영구 유효가 아니라 모름 |
| `quantity` | 값·단위·통화·척도·대상·기간·측정/계산 근거 | 빠진 차원은 모름으로 보존. 호환되지 않는 수치를 합치지 않음 |
| `coverage` | 관찰 경로·범위·마지막 확인 경계 | 변경 없음과 변경을 관찰하지 못함 구분 |
| `relations` | `supersedes`, `corrects`, `contradicts`, `derived_from`, `applies_to`의 `(record_id, revision)` 대상 | 동일 버전 자기참조·순환·권한 밖 연결 거부. 미해결 관계를 확정하지 않음 |
| `identity_status`, `identity_ref` | `resolved`, `unresolved`, `conflicted` 및 내부 대응 참조 | 모델이 기존 기록 ID를 임의로 지정하지 못함 |
| `identity_dimensions` | 대응에 사용한 맥락·대상·속성·원 구간·사건·기간·반복 발생 참조 | 신뢰된 resolver가 부여. 확정할 수 없는 차원은 미해결로 보존 |
| `lifecycle`, `policy_ref` | `active`, `withdrawn`, `deleted_pending`, `purged` 및 신뢰된 보관 정책 | 권한 불명은 전달 제외. 존재 자체 노출도 정책 적용 |

`SourceRef`에는 공급자, 불투명 locator·필요한 구간/표/셀/발언 참조, 자료 종류,
허용 범위와 마지막 접근 확인을 둔다. 자료명·locator도 기밀이므로 공개 진단에
출력하지 않는다. 동일 자료의 두 요약을 독립 출처로 세지 않는다. 수치는 예를
들어 `12.4`, `%`, `2026-Q3`, `국내 제품 A 사용자`, `자료 표 2`처럼 값·단위·
기간·대상·근거를 분리한다. 필요한 단위·기간이 빠졌으면 확정 비교·합계로 만들지 않는다.

사용자의 직접 진술은 문서 링크가 없어도 신뢰된 호스트 어댑터가 부여한 비식별
`assertion_event_ref`를 최초 근거로 사용할 수 있다. 이 참조는 사용자·작업·
관찰 시점을 권한 안에서 연결하되 원문 대화나 프롬프트를 보관하지 않는다.
`evidence_basis=user_reported`를 유지하고 독립 문서 확인으로 승격하지 않는다.
모델이 이벤트 ID를 지어내거나 다른 사용자의 진술을 원 출처로 붙이지 못한다.

`quantity`의 데이터 형태는 다음과 같다. 측정이 아닌 기록에는 `null`을 사용한다.
숫자는 자릿수 손실을 피하는 십진 문자열로 보존하고 단위·척도 변환은 근거 있는
별도 파생 기록으로 남긴다. `%`와 `%p`, 총계와 평균, 사람 수와 응답 수를 혼동하지 않는다.

```text
quantity = {value_decimal?, value_text?, unit?, currency?, scale?,
            reference_period?, population?, measure_name?, method?,
            input_record_refs:[], source_refs:[]}
```

### 분류 확장과 범용 보존

코어 registry v0는 `fact`, `source_claim`, `request`, `decision`, `reason`,
`commitment`, `status`, `action`, `constraint`, `procedure`, `definition`, `metric`,
`resource`, `preference`, `open_issue`, `hypothesis`, `generic_context`를 예시 기본
분류로 제공한다. 이 목록은 지원 직무·주제의 한계가 아니다. 분류가 맞지 않으면
`generic_context`의 주장·근거·시점·범위로 보존한다. 분류를 넓혀도 가정·아이디어·
자료상의 주장을 확인된 현실의 사실로 승격하지 않는다.

도메인 담당자가 관리하는 **선언형 versioned registry**는 `namespace`, `name`,
`version`, 데이터 필드·단위 규칙·적용 범위·표시명·호환 규칙을 정의한다. 예:
`core.metric/1`, `organization.report-standard/1`. 확장은 신뢰된 등록·검토와
호환성 검사를 거친다. 외부 자료·모델 출력은 실행 코드·권한·저장 범위를
동적으로 등록하지 못한다. 사용자·조직의 분류 추가도 같은 검증을 거치며 매
업무 기록마다 등록 승인을 요구하지 않는다.

미등록 참조는 실행하지 않고 `generic_context`로 낮춰 원문 관찰·사용자 진술·
추론 상태를 유지한다. 원래 라벨은 필요한 최소 데이터로만 남기며 새 확정 슬롯이나
기존 정정 변경의 근거로 해석하지 않는다. 버전 변경이 과거 기록을 조용히
재해석하지 않도록 migration·rollback을 정한다. 근거 없는 추론·제안은 검증
필요 상태로만, 업무 선호는 진술한 사용자·적용 범위·보관 정책을 붙여 보존한다.

## 5. 읽기·쓰기 API 의사 계약

아래는 구현 제안이며 현재 존재하는 CLI나 API가 아니다. 코어 envelope의 알 수
없는 실행 필드는 거부하고 등록 확장은 해당 버전의 데이터 필드로만 수용한다.
미등록 업무 내용은 범용 보존 경로를 사용한다.

```text
begin_task({request_id, principal_ref, policy_ref, host_surface,
            context_hints:[], task_intent, requested_at})
  -> {task_ref, outcome: ready|empty|ambiguous|unavailable|denied,
      brief?, candidate_contexts?, limitation_code?}

submit_candidates({request_id, task_ref, expected_store_revision,
                   candidates:[RecordCandidate], trigger})
  -> {outcome: committed|no_change|partially_committed|ambiguous|rejected|
              conflict|unavailable|denied,
      store_revision?, accepted_ids?, unresolved_ids?, rejected_codes?, receipt_ref?}

correct_record({request_id, principal_ref, record_id, expected_revision,
                replacement, correction_basis})
  -> {outcome, record_id?, revision?, affected_ids?, limitation_code?}

withdraw_record({request_id, principal_ref, record_id, expected_revision})
  -> {outcome, affected_ids?, limitation_code?}

delete_record({request_id, principal_ref, record_id, expected_revision,
               requested_scope: record|context})
  -> {outcome: removed_from_use|held_by_policy|conflict|unavailable,
      deletion_ref?, policy_summary?, limitation_code?}
```

`principal_ref`·`policy_ref`는 신뢰된 인증·정책 계층에서 해석한다. 모델의 JSON만으로
권한을 인정하거나 로컬 계층이 클라우드에서 실행된다고 가정하지 않는다. 오류는
닫힌 코드와 필드 경로만 반환하고 거부 본문·원문 오류를 반복하지 않는다. 실제
자료·토큰·credential을 예시에 넣지 않는다. `partially_committed`는 유효한 별도
후보는 저장하고 다른 기존 기록 변경·승격은 보류한 상태로, 전체 성공과 다르다.
transaction의 기술적 실패로 일부만 반영되는 상태를 허용한다는 뜻은 아니다.

commit 성공은 기록의 진실·모델의 이해·업무 품질 개선과 다르다. 결과는 필요할
때 펼쳐보게 하되 매번 승인으로 업무를 막지 않는다. 정상 업무 결과 생성은
저장 성공·기록 존재와 독립이다.

### 전달과 추출의 구체 계약 v0

아래 수치는 첫 가상 구현의 **초기 상한 제안**이며 효과·호스트 능력 측정값이
아니다. 상한 때문에 중요한 내용이 빠지면 완전한 맥락이라고 주장하지 않는다.

```text
Brief = {
  schema: "work-facts.brief/0", task_ref, outcome,
  context_refs:[], as_of?, coverage_status,
  entries: [{record_id, record_type, scope_refs, scope_expression, subject_refs, statement,
             workflow_stage, evidence_basis, verification, authority_basis,
             observed_at, event_at?, valid_from?, valid_until?, reference_period?,
             coverage, quantity?,
             source_labels, relations, identity_status}],
  task_dependencies: [{topic_role, state: supported_as_of|unknown|conflicted,
                       basis_refs:[]}],
  needs_check: yes|no|unknown,
  limitation_codes:[], truncated:boolean, omitted_count:integer
}
RecordCandidate = {
  schema: "work-facts.candidate/0", context_hints:[], subject_hints:[],
  record_type, statement, workflow_stage, evidence_basis, source_refs,
  origin_evidence_hint?, event_at?, valid_from?, valid_until?, reference_period?,
  quantity?, authority_basis, coverage, relates_to?, predicate_ref?, topic_role?,
  occurrence_hint?, applicability_hint?, extension_data?, trigger
}
```

`Brief.outcome`은 `ready|empty|ambiguous|unavailable|denied`, `coverage_status`는
`observed_through|partially_observed|unknown`이다. 접근 가능하고 정책이 허용한
기록만 전달한다. 최초 상한은 최대 5항목·직렬화 UTF-8 6,144바이트·항목별 요약
512바이트다. 문장을 잘라 의미를 바꾸지 않고 항목 전체를 제외해 `truncated`와
누락 수를 표시한다. 이번 산출물의 직접 입력·적용 기준·관련 수치와 정의·필요한
최근 상태를 먼저 담고, 그에 대한 미해결 충돌을 같은 묶음으로 보존한다. 다음에
관련 결정·이유·보조 이력을 담는다. 회신의 상태·약속 우선순위를 조사·분석·
기획에 일괄 적용하지 않는다. 중요 입력이나 충돌 묶음이 빠지면
`needs_check=unknown`으로 표시하고 확정 비교·판단에 쓰지 않는다. 수치와 노출
방식은 다양한 업무를 대상으로 조정할 설계 값이다.

모델에는 `Brief`를 시스템 지시와 분리된 **신뢰하지 않는 업무 자료**로 제공한다.
자료 속 명령·선호·조직 기준도 신뢰된 사용자 지시나 권한을 덮어쓰지 못한다.
출처·시점·적용 범위·미관찰 구간을 유지하고, 필요한 기준·수치·현재 상태가
`unknown|conflicted`이거나 누락됐으면 그 부분을 확정하지 않는다. 각 기준의
`valid_from`·`valid_until`과 관찰 범위를 전달해 적용 기간 밖의 지침을 현재
기준으로 사용하지 않는다. 미지의 유효 구간은 무기한이 아니다. 기록이 비어도
작성·탐색·분석·창의적 제안·사고 지원을 계속하며 제안을 확인된 사실로 저장하지 않는다.

`RecordCandidate`는 ID·revision·lifecycle·저장 권한을 지정하지 못한다. 코어가
신뢰된 주체·맥락·출처 권한을 검사하고 ID·버전을 부여한다. 모델의 출처 주장만으로
발송·결정권·검증·실행을 증명하지 않는다. 사용자 진술은 그 근거 수준으로, 연구
결과는 해당 연구의 주장·대상·조건으로, 계산 결과는 입력·단위·기간·계산 근거를
가진 파생 기록으로 보존한다. 후보당 요약 512바이트·제출당 10개 후보를 초기
상한으로 두고 초과·거부·미해결 건을 명시한다. `observed_at`은 신뢰된 어댑터·
저장 계층이 부여하며 모델 후보에 있으면 미지원 필드로 거부한다.
코어와 확장을 합친 후보 envelope에도 별도 직렬화 크기 상한을 적용하고,
임의로 큰 `extension_data`·출처 배열·수식·원문을 요약 상한 우회에 쓰지 못하게
한다. v0 후보 envelope 상한 4,096바이트는 초기 구현 제안이며 실제 호스트
시험에서 조정한다. 등록 확장의 필드도 그 상한과 권한·보존 규칙을 따른다.

## 6. 작업 진입과 종료 처리

### 시작

1. 정책과 전달 대상 AI 환경을 검사한다. 정책이 허용한 기록만 조회한다.
2. 요청 단서로 프로젝트·주제·문서·업무 건 등의 맥락을 식별한다. 모호성이
   이번 결과를 바꿀 때만 필요한 후보를 짧게 제시한다.
3. 관련 기록의 관계·정정·철회·삭제 상태를 적용한다.
4. 마지막 확인 시점과 미관찰 범위를 포함한 brief를 만든다.
5. 본 작업보다 먼저 전달됐는지를 어댑터 증거와 구별해 확인한다. AI가 이미
   답을 작성한 뒤 관련 기록을 제시하면 사전 전달 성공으로 세지 않는다.
6. 현재 상태·적용 기준·수치·자료 해석이 이번 결과를 바꿀 때만 허용된 좁은
   경로의 추가 확인을 고려한다. 확인 불가 시 설명·초안·가설 탐색 등 가능한
   작업을 계속하고 미확인 부분의 단정만 보류한다.
7. 기록이 없거나 맥락을 찾지 못해도 일반 업무·사고 지원을 수행한다. 조회·저장
   성공을 정상 업무 결과 생성의 선행 조건으로 만들지 않는다.

### 저장

호스트의 종료 이벤트가 실제 업무 완료를 뜻한다고 가정하지 않는다. 다음
신호를 각각 측정한다: 명시적 작업 완료와 확인 가능한 업무 사건. 다음 작업
진입 시 이미 커밋된 기록은 정상 조회한다. 유휴 시간만으로 메일 발송이나
업무 완료를 추론하지 않는다.

원래 요구는 작업 후 자동 저장이다. 관찰된 사건에서 얻은 구조화 후보는 정책이
허용하는 경우 즉시 커밋하거나, 현재 프로세스의 휘발성 메모리에만 보류해 종료
신호에 커밋한다. 종료 신호 없이 프로세스가 사라지면 휘발성 후보는 회수할 수
없다. 다음 진입에는 이미 커밋된 기록을 정상 조회하며, 별도의 미커밋 후보를
회수하거나 변환했다고 표시하지 않는다. 미커밋
후보의 지속 대기열과 이전 대화 원문 재열람은 v0 기본안에 포함하지 않는다.
둘 다 불가능하면 `save_not_observed`/`unavailable`로 표시하고 누락을 보고한다.
사건 단위 저장은 업무 완료 감지와 같지 않으며 실제 지원 및 성공률을 별도
측정한다. 저장 후보가 없으면 `no_change`가 정상 결과다. 쓰기 불가나 거부는
저장됨으로 표시하지 않고 현재 업무를 가능한 범위에서 이어간다.

## 7. 정정·충돌·삭제와 재추출 대응

* **정정:** 같은 ID의 revision을 원자적으로 증가시키고 이전 revision을 `corrects`로
  참조한다. 사용자 정정도 출처로 표시하며 제3자의 권한·원문을 임의 변경하지 않는다.
* **변경:** 기준 개정·새 기간 지표·담당 변경·계약 재진행은 기존 기록이 틀렸다는
  뜻과 다르다. 범위·기간이 이어지는 근거가 있으면 `supersedes`나 새 관찰로
  연결하고 과거를 보존한다. 지시를 실제 착수·완료로 승격하지 않는다.
* **충돌:** 같은 대상·기간·적용 범위의 주장이 다르면 충돌 또는 미해결 관계로
  보존한다. 최신 날짜만으로 정확성·권한을 우선하지 않으며 필요한 부분만 확인한다.
* **철회:** 전달 대상에서 제외하고 파생 brief·색인을 무효화한다.
* **삭제:** 조회·전달에서 제외하고 기록·파생물·색인·백업·억제 정보의 처리를
  정책으로 정한다. 휴지통과 완전 삭제를 같은 상태로 표현하지 않는다.

### 동일성의 두 경로

일곱 고정 슬롯에 맞지 않는 사실을 버리는 구조를 없애고, 명확한 대응과 아직
불명확한 범용 대응에서 **기존 기록을 변경하는 권한**을 보수적으로 판단한다.
`request_id`는 호출 재시도만 막고 의미상 동일성을 대신하지 않는다. 식별 자료도
민감정보이며 공개 진단에 값·해시를 남기지 않는다.

1. **등록 속성:** 신뢰된 맥락·대상 ID, 불변 `origin_evidence_ref`의 출처 구간·표·
   셀·발언, versioned `predicate_ref`, 사건·기준 기간, 반복 항목의 `occurrence_ref`를
   조합한다. 필요 없는 차원은 `not_applicable`, 필요한 단위·기간·대상이 빠지면
   자동 병합하지 않는다. 정정 근거가 추가돼도 최초 근거 ID는 유지한다.
2. **범용 대응:** 새 주제·미등록 속성은 `generic_context`로 다룬다. 허용된 출처
   구간·대상·기간·값/단위·주제 역할로 대응 후보를 찾되 구조적 동일성이 없으면,
   보호된 출처 구간과 겹치지 않고 보관 권한이 확인된 경우에만
   `identity_status=unresolved`의 별도 항목으로 저장한다. 보호 이력과의 관계나
   구간을 판단하지 못하면 후보의 자동 저장을 보류하고 기존 작업은 계속한다.
   비슷한 문구나 모델의 주제 역할만으로 기존 정정의 대체물로 만들지 않는다.
   같은 문서의 여러 주장은 구간·대상·역할을 나누며, 구분이 모호해도 자료 전체를
   한 사실로 합치지 않는다.

범용 기록도 동일 출처 구간·같은 적용 맥락·정규화한 동일 주장·동일 수치 차원이
정확히 일치하면 중복 후보로 `no_change` 처리한다. 서로 다른 내용의 의미상
동일성이나 관계를 확정하지 못했다면 보호 이력과 보관 권한을 확인한 뒤에만
별도 미해결 기록을 보존한다. 완전히 같은 후보가 매 작업마다 새 독립 근거로
쌓이게 두지 않는다. 같은 출처 구간에서 표현만 달라졌고 별개의 주장인지 판단할
근거가 없으면 새 기록을 만들지 않고 `ambiguous`로 보류한다. 구간·주제·대상이
다름을 확인한 별도 주장은 각각 보존할 수 있다.

속성은 versioned registry에서 정의하며 모델이 미등록 참조를 자동 등록하지 못한다.
하지만 미등록이라는 이유만으로 원문 관찰·사용자 명시 진술을 저장 불가 처리하지
않는다. 근거 없는 추론·제안은 검증 필요 상태로만 보존한다. 아직 대응하지 못한
항목은 검색에서 미해결 상태를 드러낸다. **정정·철회·삭제 보호 확인은 속성
매칭보다 먼저** 적용한다. 같은 `origin_evidence_ref` 구간에 보호 이력이 있으면
모델이 속성·문장을 바꾸거나 속성을 빼더라도 후보를 별도 확정 기록으로 저장하지
않는다. 정정 이력이 있고 재추출이 **정정 전 주장과 정확히 동일**함이 확인되면
`no_change`로 처리해 정정된 같은 `record_id`·revision을 유지하고 새 항목이나
관계를 만들지 않는다. 정정 전 주장과의 동일성도 독립 사실 여부도 판단하지 못하면
`ambiguous`로 보류한다. 다른 독립 사실임이 구간·대상 근거로 확인되면 별도로
저장할 수 있다. 삭제·철회 이력과 겹치거나 보호 이력을 검사할 수 없으면 조용히
재생성하지 않고 보류한다. 허용된 나머지 업무 결과는 계속 만든다.

신뢰된 출처 registry는 자료 제공자의 원자료 식별자·버전·구간과 알려진 별칭을
해당 권한 범위에서 정규화해 보호 이력을 대조한다. 다른 ID여도 같은 자료의
겹치는 구간이면 같은 보호 대상으로 처리한다. 원자료 동일성·구간 중첩·보호
이력을 확인할 수 없을 때는 별개의 출처라고 추정해 후보를 자동 저장하지 않는다.
출처 registry가 권한을 부여하거나 원문 복제·공개 hash 로그를 정당화하지 않는다.

삭제 정책이 보존 표식을 허용하는지 아직 미정이다. 필요한 보호 정보를 보관할 수
있으면 정책에 허용된 범위의 출처·구간에 대해 재수집을 제한한다. **표식을
보관할 수 없어 어느 출처가 삭제됐는지 특정할 수 없는 설정에서는 범위를
짐작하지 않고 그 라이브러리의 자동 재수집 전체를 중지한다.** 이 중지 상태를
비식별 설정값으로 유지할 수 없는 환경에서는 자동 재수집을 미지원으로 두며,
다시 켜기 전 정책과 사용자에게 영향을 설명한다. 사전 저장 승인창을 매 작업
요구하는 방식으로 대체하지 않는다. 업무 수행은 계속하되 자동 저장 제한을 알린다.
삭제 후 재생성 방지를 보장할 수 없는데 완료라고 주장하지 않는다. 억제 정보
자체의 민감성과 사용자·조직의 삭제·보존 정책은 별도 검토한다.

### MutationPlanner 판정

- 구조적 동일성이 확정된 키에 정정이 없고 내용·단계·근거·수치 차원이 정확히
  같으면 `no_change`. 문자열은 NFC·양끝 공백만 정규화하고 의미를 추측하지 않는다.
- 동일 키의 다른 해석에 새 사건·근거·정정이 없으면 기존 항목을 덮어쓰지 않는다.
  같은 출처 구간이 별도 주장을 담는다는 것이 확인되지 않거나 정정·삭제 보호
  이력과의 관계가 불명확하면 `ambiguous`로 보류한다. 보호 이력과 무관함이
  확인되고 보관이 허용된 별도 후보만 `unresolved`로 저장해
  `partially_committed`와 이유를 반환한다. 같은 후보가 이미 있으면 `no_change`다.
- 사용자 정정이 있는 키에 옛 주장이 재추출되면 정정 revision을 유지하고
  `no_change`. 정정 범위를 넘어 모든 출처·다른 기간의 값을 고치지 않는다.
- 독립 새 근거나 이후 사건은 별도 항목으로 받되 사용자 정정을 지우지 않는다.
  명확한 변경·충돌만 연결하고 불명확한 관계만 보류한다. 보관 금지·근거 없는
  확정 승격은 후보 자체를 거부한다.

### 재현할 범용 예시

| 입력 | 기대 저장·재사용 | 금지되는 해석 |
| --- | --- | --- |
| 보고서 기준의 “매출은 부가세 제외” | 해당 조직·보고서의 기준, 버전·적용 시점·출처 | 모든 보고서의 전역 규칙 또는 상위 명령 |

| 연구가 특정 조건의 시간 감소를 보고 | 연구 주장·표본·조건·시점과 근거 | 모든 직장인의 효과로 승격 |

보존기간·원본 변경 후 동작 확정 전에는 영구 재생성 금지를 보장하지 않는다.
완전 삭제와 표식 보존이 충돌하면 이를 공개하고 재수집 제외 등 대안을 정한다.

## 8. 저장소·권한·복구 제안

초기 구현 후보는 사용자 또는 조직이 지정한 단일 저장소를 사용하는
호스트 중립 코어이다. 로컬 SQLite 등 transactional 저장소와 OS 보안
저장소의 키 관리 조합은 **후보**이며, 암호화 backend·지원 플랫폼·조직
복구 정책이 정해지기 전 구현 기본값으로 확정하지 않는다. 평문 fallback은
만들지 않는다. 키가 잠기거나 접근이 거부되면 `unavailable`로 남긴다.

저장 데이터와 검색 색인은 같은 기밀 범위로 취급한다. 로컬 저장만으로
보안을 보장하거나 회사 정책 검토가 불필요해지는 것은 아니다. 원문 접근이
회수되거나 정책 확인이 불가능한 기록은 기본 전달 대상에서 제외하는 안을
검토한다. UI가 기록의 존재만 노출해도 누출일 수 있으므로 오류에 건명·내용을
넣지 않는다. 개인·팀 공유와 동기화는 초기 포트와 분리한다.

각 변경은 `request_id`를 사용해 같은 요청의 재시도를 한 번만 반영한다.
중복 판정 자료도 민감정보로 취급하며 공개 hash 로그를 만들지 않는다.
정정·삭제는 `expected_revision`과 store revision을 검사한다. 오래된
세션의 자동 저장이 새 정정을 덮어쓰지 못하게 충돌을 반환한다. 디스크 부족,
중단, 경합 시에는 전체 transaction을 rollback하고 일부 기록을 성공으로
보이지 않는다. commit 후 응답이 끊긴 재시도는 기존 결과를 돌려준다.

운영 진단은 버전·결과 코드·건수와 비식별 시간 정도로 제한하는 설계를
우선한다. raw prompt, transcript, screenshot, 원문·전체 경로, credential,
숨겨진 추론을 로그나 crash report에 넣지 않는다. 원격 telemetry는 초기
설계의 필수 요소가 아니며 별도 도입 결정 없이 추가하지 않는다.

## 9. 설치·해제·업데이트 제안

새 라이브러리 저장소는 기존 OpenSocrates 설치나 사용자 설정과 분리한다.
설치 과정이 과거 대화를 자동 수집하거나 기존 history를 가져오지 않는다.
최초 설정에서 저장 범위와 AI 전달 대상, 조직 정책과 사용자 통제를 설명하고
필요한 host trust flow를 따른다. **최초 기능 활성화와 매 작업의 저장 승인은
다르다.** 정상 활성화 이후의 각 기록 저장은 제품 목표대로 자동이어야 한다.

업데이트는 저장소 schema version과 어댑터 version을 별도 관리한다.
migration 전 정책상 허용된 보호 백업을 만들고 실패 시 복구한다. 백업이
삭제 요구와 충돌하지 않도록 위치·보존 상태를 노출한다. 이전 프로그램이
새 schema를 해석하지 못하면 쓰기를 멈추며, rollback했다고 새 데이터를
조용히 잃거나 평문 export하지 않는다.

연동 끄기, 프로그램 제거, 기록 삭제를 서로 다른 행동으로 정의한다.
연동을 끄면 더 이상 읽고 쓰지 않는다. 제거 시 라이브러리의 처리 방식을
명확히 보여 주고, 사용자 의도 없이 삭제나 과거 버전으로의 데이터 복제를
하지 않는다. 실제 설치 파일·서명·업데이트 자산과 배포 채널은 플랫폼 선택
후 별도 배포 명세로 확정한다.

## 10. 실패 수용 계약과 남은 결정

| 가상 조건 | 요구 결과 | 성공으로 세면 안 되는 것 |
| --- | --- | --- |
| 초안만 작성, 발송 여부 미확인 | `draft` 또는 실행 미확인 기록 | 발송 완료 자동 승격 |
| 같은 이름의 프로젝트·문서 또는 A사의 두 계약 | 대상·범위·기간을 분리하거나 필요한 식별 질문 | 이름만 보고 합친 brief |
| 10/29 반려 기록, 이후 관찰 없음 | 시점이 붙은 반려 이력 | 오늘도 계약 미체결이라고 단정 |
| 사용자가 지시자·지표·기준 정정 후 재추출 | 정정 범위 유지, 명확한 대응은 `no_change`, 불명확 관계만 보류 | 옛 내용으로 정정을 덮거나 다른 대상·기간까지 정정 |
| 저장 중 디스크·키·권한 오류 | 저장 실패와 가능한 작업 지속 | 실패를 무음 성공으로 표시 |
| source access 회수 | 해당 내용 전달 제외·일반적인 한계 코드 | 오류 메시지로 제목이나 요약 노출 |
| 작업 종료 신호 누락 | 누락 관찰 및 가능한 회수 방식 측정 | 응답 종료를 실제 업무 완료로 간주 |
| 원문에 ‘이 규칙을 무시하라’ 문장 | 기록 데이터로 취급·실행하지 않음 | 원문의 명령을 앱 권한으로 실행 |
| 같은 저장 요청 중복 도착 | 한 번만 반영·같은 결과 반환 | 중복을 독립 근거로 계산 |
| 새 업무·기록 없음 | 작성·분석·탐색·기획을 계속하고 필요한 새 사실만 기록 | 기록 없음을 업무 불가로 처리 |
| 미등록 분류·여러 맥락의 정상 사실 | 권한과 보호 이력을 확인한 범용 기록·적용 범위 보존, 불명확한 후보는 보류 | 고정 슬롯 없음으로 정상 사실 모두 폐기하거나 정정·삭제 우회 |
| 기간·단위가 다른 지표·다른 적용 기준 | 차원과 적용 가능성을 유지 | 수치·기준을 무조건 합치거나 전역 적용 |

다음 항목은 완료된 제품 결정이 아니다. 호스트 기능 확인 결과와 함께 담당
작업에 인계한다: Claude의 정확한 표면·버전·지원 경로, 자동 진입/쓰기/종료
포트 충족 여부, 보관 정책 변경, 저장소와 key backend, 실제 source authority
정책, 삭제·백업·억제 정보의 보존 의미, 배포 플랫폼과 포장 방식. 이 가운데
호스트 경로의 부재는 다른 앱에서 성공한 것처럼 숨기지 않고 해당 어댑터
설계를 다시 선택하게 하는 전환 조건이다.

이 문서는 새 업무 저장 기능을 제안한다. 기존 코드의 단위 검사, 패키지 생성,
Claude의 대화 응답, 사람이 작성한 가상 record가 존재한다는 사실은 자동
사전 전달·자동 저장·실제 직장인 효용의 증거가 아니다. 각각의 구현, 로컬
검사, 호스트 실측, 사용자 결과를 별도 상태로 기록한다.
