# OpenSocrates 2.0 검증·평가 계획

상태: 2026-11-02 개발 계획. 이 문서는 실행 결과, 지원 인증, 성능 개선의 증거가 아니다. [제품 요구사항](VISION_2.0.ko.md)과 [시스템 설계](SYSTEM_2.0.ko.md)를 실제로 확인할 수 있는 사례로 바꾼다. [English](VALIDATION_2.0.md)

## 1. 검증할 제품과 판단 기준

첫 범위는 한 사용자의 한 컴퓨터에서 실행하는 OpenSocrates 프로그램과 가벼운 데이터베이스, ChatGPT 데스크톱 앱 및 Claude 데스크톱 앱의 연결이다. macOS와 Windows를 각각 확인한다. ChatGPT의 Chat·Work·Codex, Claude의 일반/통합 대화·Cowork·데스크톱 Code는 실제로 노출되는 기능과 경계에 따라 별도로 기록한다. 앱 안의 Codex를 다른 데스크톱 제품으로 취급하지 않는다. 독립 CLI·웹·모바일, Cursor, Grok Bot, 여러 컴퓨터 간 동기화는 첫 출시의 지원 근거가 아니다.

사용자가 요청한 대화는 상담과 작업 준비·조율을 수행한다. 실제 조사·분석·제작·결과물 통합은 새 앱 대화 세션에서 이루어진다. 모든 에이전트 간 의뢰·질문·응답·인계는 OpenSocrates 레이어를 거쳐야 한다. 그 레이어가 각 업무에 맞는 프롬프트, 맥락, 추론 가이드를 전달한다. 모델 제공자 API를 직접 호출하는 구현을 이 제품의 실행 경로로 대신 시험하지 않는다.

제품의 효과를 평가할 때는 관찰 가능한 사용자 결과를 먼저 정한다. 의도 이해, 결과물의 품질·사용성, 재작업, 불필요한 질문과 사용자 개입, 맥락 전환, 권한 준수, 소요 시간·비용을 평가한다. 특정 파일 구조나 알고리즘이 있다는 사실은 좋은 사용자 경험의 충분조건이 아니다. ‘token alignment’, MoE, RL, Git 트리는 구상의 설명 또는 설계 가설이며, 내부 토큰이나 숨은 추론의 변화를 관측했다고 주장하지 않는다.

## 2. 증거 상태와 호스트 매트릭스

각 주장에는 다음 상태 중 실제로 확보한 상태를 붙인다. 상태는 자동 승격되지 않는다.

| 상태 | 의미 |
| --- | --- |
| 계획 | 구현 또는 시험이 아직 필요함 |
| 문서 근거 | 해당 버전의 공식 안내에서 기능을 확인함 |
| 로컬 구현 | 특정 소스·패키지에 구현되어 있음 |
| 오프라인 검증 | 합성 입력·격리 환경의 검사에서 관찰함 |
| 실제 호스트 관찰 | 명시한 앱·모드·운영체제·계정에서 직접 관찰함 |
| 비교 평가 | 사전 고정한 조건과 평가로 상대 결과를 확인함 |
| 도구 정책 차단 | 조작 도구의 정책이 그 시도를 막음. 호스트 자체의 지원 여부와 구별하고 같은 행동을 우회하지 않음 |
| 불가/미확인 | 접근·권한·기능·측정 수단의 부족을 명시함 |

| 필수 앱/운영체제 | 별도 확인할 표면 | 현재 2.0 검증 상태 |
| --- | --- | --- |
| ChatGPT 데스크톱 / macOS | 노출된 Chat·Work·Codex, 로컬/클라우드 작업 경계 | 계획; 2.0 통합 시험 미실행 |
| ChatGPT 데스크톱 / Windows | 노출된 Chat·Work·Codex, Windows 기본 실행/허용된 별도 환경 | 계획; 2.0 통합 시험 미실행 |
| Claude 데스크톱 / macOS | 일반 또는 통합 대화·Cowork·데스크톱 Code, 실제 로컬/클라우드 경계 | 계획; 2.0 통합 시험 미실행 |
| Claude 데스크톱 / Windows | 일반 또는 통합 대화·Cowork·데스크톱 Code, 실제 로컬/클라우드 경계 | 계획; 2.0 통합 시험 미실행 |

앱 설치 여부, 계정 요금제, 지역·배포 상태, 관리자의 정책에 따라 기능이 달라질 수 있다. 문서상 기능을 이 사용자 계정의 가용성으로 간주하지 않는다. 표면의 차이가 없다면 관찰 근거를 남기고 중복 셀을 합칠 수 있지만, 미확인 표면을 성공한 셀에 묶어 통과시키지 않는다. CPU 아키텍처와 지원 운영체제 버전의 정확한 범위는 실제 시험 후 정한다.

현재 회의에서 `claude://` 딥링크의 공개 합성 시험은 인앱 브라우저의 URL 정책에 의해 실행 전에 차단됐다. 이는 도구의 경로 제한이며 Claude 앱 자체의 성공이나 실패를 뜻하지 않는다. 이 시도에서 HOST-09는 미실행이고, 차단된 동작을 다른 실행 경로로 우회하지 않았다.

기능별로 등록·활성화, 세션 생성, 전달된 프롬프트/가이드/맥락의 식별, 에이전트의 수신 또는 읽기, 실제 업무 결과를 구별한다. 에이전트의 자기 보고만으로 읽기나 적용을 독립 검증했다고 쓰지 않는다. 개인정보를 남기지 않는 수신 식별자를 호스트가 제공하지 않으면 해당 단계는 미확인으로 두고 최종 결과의 관찰은 별도로 보고한다. 제공되지 않는 영수증을 찾는 일을 제품 완료의 추가 조건으로 만들지 않는다.

### 먼저 가를 호스트 관찰

각 앱·OS·모드의 허용된 시험 환경에서 공개 합성 자료로 다음 세 가지를 별도로 살핀다. 최초 설치에서 호스트가 요구하는 권한과 일상 업무마다 요구되는 확인의 빈도도 구분한다.

1. **새 실행 대화:** 실제로 새 대화를 열고 첫 의뢰를 보내며 결과를 레이어로 회수할 수 있는가. 각 단계를 관찰하면 해당 단계의 가능성을 알 수 있고, 하나라도 안 되면 해당 자동 경로는 미완료다. 화면이나 입력창만 열린 결과를 완료로 세지 않는다.
2. **수신자와 권한:** 두 대화가 연결·프로세스를 공유하는지, 호스트가 모델이 임의로 바꿀 수 없는 대화 식별·권한 정보를 제공하는지, 재시작·오인 수신에서 어떻게 되는지 관찰한다. 한 번의 프로세스 분리나 식별자 일치는 격리·인증 보증이 아니다. 검증된 바인딩이 없으면 영향받는 민감한 전달과 귀속만 대기하고 독립 업무를 계속한다.
3. **진행 중 교환:** 실행 중 조건 변경을 알리고 재조회해 적용과 결과 반환까지 되는지, 사용자의 개입과 지연이 어느 정도인지 관찰한다. 전달·읽기·적용·산출은 따로 기록하며 지원하지 않는 경로는 대안 후보를 별도로 평가한다.

이 관찰은 설계 단계의 시험 계획이며 실행 결과가 아니다. 도구 정책이 차단한 조작을 다른 경로로 재시도하거나 우회하지 않는다. 이 세 가지가 일부 성공해도 네 조합 전체의 지원, 보안성, 결과 품질이나 개인화 효과가 입증되는 것은 아니다.

## 3. 시험 준비와 자료 경계

시험 전에 사례 버전, 합성 입력, 기대 결과, 모델·노력 수준·도구 접근, 앱·운영체제 버전, 사용자 권한, 반복 수·순서, 시간 제한, 실패와 중도 중단의 처리, 평가자를 고정한다. 실제 입력이나 사용자 파일을 보관하지 않아도 재현 가능한 시험은 공개 가능한 합성 자료와 버전으로 만든다.

실사용 평가는 사용자가 범위를 알고 동의한 과업에서 진행한다. 사용자가 원래 할 일을 수행하는 동안 최소한의 결과 판정과 부담을 측정하며, 매 수정마다 이유를 설명하거나 장기간 수동 기록을 작성하도록 제품 사용의 전제로 요구하지 않는다. 별도 연구용 인터뷰나 평정은 선택적인 평가 절차로 구분한다. 평정을 얻지 못한 결과는 미평가로 남긴다.

[AGENTS.md](../../AGENTS.md)와 [CONTRIBUTING.md](../../CONTRIBUTING.md)의 현재 정책을 따른다. 원문 프롬프트·대화록, 작업 공간 내용의 복사본, 자격 증명, 스크린샷, 숨은 추론을 수집·보관하지 않고 텔레메트리를 추가하지 않는다. 사용자 소유의 최종 결과물은 원래 전달 위치에 두며 평가 저장소에 복제하지 않는다. 공개 가능한 합성 자료, 내용 없는 상태·버전·결과 수치와 허용된 참조만 시험 기록에 남긴다. 가이드나 요약에도 원문·비밀이 재현되지 않는지 확인한다.

파일 이전 내용의 상시 보관이나 비공개 실제 프롬프트 재현이 필요한 평가안은 이 문서만으로 허용되지 않는다. 먼저 정책 변경을 별도로 검토하고 명시적으로 결정하거나, 기존에 허용된 원본 버전 참조와 합성 자료를 사용하도록 시험을 바꾼다. 데이터가 없다는 이유로 실제 변화의 원인이나 의도를 꾸며내지 않는다.

## 4. 비교 평가 설계

| 비교 조건 | 확인할 질문 |
| --- | --- |
| A: 같은 호스트, OpenSocrates 없음 | 일반적인 앱 사용의 결과와 부담은 어떠한가? |
| B: 정확히 고정한 v1.5.3 | 기존 48개 가이드 배포·선택 경로와 비교해 무엇이 달라지는가? |
| C: 2.0, 기본 가이드와 프로그램 연결 | 세션 분리·통신·맥락 전달 자체의 영향은 무엇인가? |
| D: 2.0, 개인 가이드 선택·재조립 | 관련 개인 가이드가 추가로 기여하는가? |
| E: 2.0, 경험으로 가이드를 생성·조정 | 미리 작성한 개인 가이드와 달리 실제 학습 과정이 다음 업무를 개선하는가? |

모든 비교를 무조건 한 번에 실행하지 않는다. 주장에 필요한 대조 조건을 선택한다. 예를 들어 위임의 효과는 동일한 자료·도구·예산에서 하나의 실행 세션과 OpenSocrates를 통한 동적 위임을 비교한다. 가이드의 효과는 프로그램과 실행 조건을 고정하고 관련 가이드만 바꾼다. 사실 메모만 전달하는 조건과 비교하면 개인 사실 회상과 사고 가이드의 기여를 더 잘 구분할 수 있다. 실험마다 변경한 요인과 함께 변경된 요인을 명시한다.

v1.5.3은 [릴리스 기준선 목록](RELEASE_BASELINE_1.5.3.md)에 연결된 정확한 배포본과 해당 호스트의 실제 동작을 확인한다. 특정 호스트의 B와 비교하려면 그 호스트의 B 조건이 필요하다. 다른 운영체제나 앱의 기준선 측정이 끝나지 않았다는 이유로 이미 근거가 있는 개별 호스트의 정적 비교·기능 관찰·별도 비교를 막지 않는다. 해당 표면에서 v1.5.3이 지원되지 않으면 B를 ‘적용 불가’로 적고 A 등 적절한 대조군을 쓴다.

학습을 평가할 때는 가이드 생성에 쓴 경험과 평가 업무를 구분한다. 동일 프로젝트의 후속 업무, 다른 프로젝트의 유사 업무, 관련 없는 업무, 시간이 지나 선호나 사실이 바뀐 업무를 포함한다. 후보 조건 사이의 사용자 학습·피로·순서 효과를 기록하며, 각 조건의 개인 데이터베이스와 가이드 상태를 격리한다. 현재 상태를 다른 조건에 흘려보내고 독립 비교라고 하지 않는다.

모델·도구·접근 권한·가용 기능을 최대한 맞춘다. 앱 간 비교에서 이를 맞출 수 없으면 차이를 보고하고 제품이나 모델 하나의 인과 효과로 해석하지 않는다. 모든 시도, 재시도, 시간 초과, 실패, 동률과 중단을 포함한다. 표본 수와 반복 단위를 공개하며, 하나의 출력에 대한 여러 평가를 독립적인 여러 업무로 세지 않는다.

### 개인 가이드의 추가 기여를 가르는 시험 설계

다음은 실행 전 실험 설계이며 결과가 아니다. 합성 사례에서 외부 의사결정용 분석 보고서를 Word로 의뢰한 사람이 진행 중 “원인보다 다음 행동을 먼저 보고 싶다”고 수정한다. 그 신호를 바탕으로 가이드 후보가 만들어지는 경험과, 이후 새 작업을 분리한다. 후속 사례는 유사한 의사결정 문서, 절차 순서가 필수인 지원서, 관련 없는 팀 회고, 선호가 바뀐 업무를 포함한다. ‘한 투자자의 요구’와 ‘사용자의 범용 선호’를 다르게 설정한 사례도 준비한다. 모든 내용은 공개 가능한 합성 자료다.

- 같은 호스트·모델·도구·권한과 예산에서 **기본 가이드**, 같은 신호를 담은 **사실 메모**, 그 신호를 바탕으로 생성한 **개인 가이드**를 비교한다. 기본 가이드와 사실 메모가 맞지 않는 상황도 포함한다. 관련 세션·프로그램·맥락은 비교할 요인 외에는 맞춘다. 필요하면 OpenSocrates 없는 기본 앱과 해당 호스트의 v1.5.3을 별도로 비교한다.
- 호스트 자체 메모리가 가이드를 보강하거나 반대로 누출할 수 있다. 가능한 셀에서는 호스트 메모리 상태와 조건별 데이터 격리를 확인하고, 켜짐·꺼짐 비교를 별도로 한다. 통제할 수 없거나 사용 여부를 관찰할 수 없으면 미확인·교란 요인으로 기록한다. 호스트 메모리 비활성화가 모든 표면에서 가능하다고 가정하지 않는다.
- 경험 생성용 업무와 평가용 업무를 분리하고 조건의 순서, 모델·앱 버전, 반복 단위와 평가 기준을 사전에 기록한다. 같은 사용자·대화에서 여러 조건을 번갈아 실행해 기억이 섞이면 독립 비교로 처리하지 않는다. 합성 테스트와 동의받은 실제 업무의 평가를 구별한다.
- 산출물의 정확성과 목적·형식 적합성뿐 아니라, 의뢰 단계에서 무엇을 물었는지, 위임한 그래프가 어떤 판단을 돕는지, 불필요한 정정과 중요한 확인 누락, 무관 업무로의 부정적 전이, 변경된 선호에 대한 회복, 대기·비용을 평가한다. 질문이나 위임 내용의 차이는 별도 관찰이며, 모델의 자기 보고는 실제 품질을 증명하지 않는다.
- 가능하면 조건을 가린 평가와 사용자 판단을 분리하고 불일치·실패·동률·미평가를 보존한다. 시험할 수 없는 형식이나 호스트는 제외 이유를 명시한다. 개인정보 정책에 허용되지 않는 실제 작업물의 복사본이나 대화록을 평가 기록에 만들지 않는다.

사실 메모와 개인 가이드가 같은 효과를 내면 **이 사례에서는** 개인 가이드 표현의 추가 기여가 입증되지 않은 것이다. 그 결과는 통신이나 파일 관리 등 다른 기능의 가치를 자동으로 부정하지 않는다. 반대로 한 사례의 좋은 결과만으로 다른 사용자·업무에서의 개선을 주장하지 않는다.

앞의 [두 업무 합성 가이드 사례](SYSTEM_2.0.ko.md)는 다음처럼 평가용 작업을 따로 준비할 수 있다. 이는 **시험 계획**이며 이 회의의 모델 답변이나 2.0 효과를 평가한 결과가 아니다. 가이드를 만드는 발주·감사 경험과 겹치지 않는 합성 과제를 미리 정하고, 같은 기본 가이드·자료·호스트·모델 조건 아래 기본 가이드만, 같은 경험을 요약한 사실 메모 추가, 경험에서 만든 개인 가이드 추가를 비교한다. 메모와 가이드의 정보량·범위가 완벽히 같다고 가정하지 않고 비교 전 차이를 점검한다. 각 평가 과제의 현재 사용자 지시는 모든 비교군에 동일하게 제공한다. 이번 업무 지시를 한 조건에서만 현재 지시로, 다른 조건에서는 과거 메모로 넣으면 개인 가이드 표현만의 비교가 아니다.

| 후속 과제 | 살필 결과 |
| --- | --- |
| 관련 발주: 선택지와 근거가 충분 | 목적과 현재 지시에 맞는 판단을 제공하면서 결정을 바꿀 가정을 필요한 깊이로 다루는가. |
| 급한 발주: 선택지·수치 없음 | 안 하나를 지어내지 않고, 이미 이용 가능한 자료를 먼저 찾으며 결정에 필요한 빈칸을 짧고 구체적으로 다루는가. |
| 결론부터 필요한 감사 또는 절차가 중요한 다른 검토 | 업무명만으로 순서를 강제하지 않고 현재 사용자·독자의 목적을 따르는가. |
| 다른 프로젝트와 제3자의 수정 | 가이드의 관련성을 새로 판단하고 제3자의 선택을 원래 사용자의 선호로 오인하지 않는가. |

가능한 경우 과제와 조건의 배정·평가 기준을 사전에 정하고 평가자는 조건을 모르게 한다. 조건별 상태와 호스트 메모리의 실제 격리 여부를 기록한다. 통제하지 못한 기억이 있다면 조건별 관찰은 보고하되 그 차이를 가이드 표현만의 효과라고 단정하지 않는다. 작은 표본에서 차이가 검출되지 않았다는 사실도 동등성의 증거가 아니다.

자기강화의 반증은 별도로 설계한다. 공개 합성 경험의 실제 사용자 지시·고객 요구·선호 변화와 작성자를 평가용으로 미리 정한 뒤, 원래 가이드가 적합한 경우와 잘못된 경우 모두에서 수정·부분 수정·침묵·동일 신호의 다중 전언을 준비한다. 같은 초기 상태의 학습 정책을 비교하고 가이드 전달, 실제 읽기·사용의 관찰 가능성, 호스트 메모리의 상태를 분리한다. 후속 평가 업무에는 관련·무관·바뀐 선호를 포함한다. 평가자는 허용된 자료에서 현재 업무 지시 준수, 거짓 일반화·중복 강화, 필요한 적응의 누락, 부정적 전이와 사용자 부담을 각각 판단한다. 조건당 여러 채점은 서로 다른 업무 수가 아니며, 결과 누락·중단·평가 불가와 호스트 메모리의 통제 불가는 그대로 보고한다. 독립적인 지지로 보이는 지표만이 아니라 유용한 수정 신호를 과도하게 버리는 비용도 본다. 이 실험은 평가를 위해 실제 사용자의 유효한 지시나 적합한 가이드를 임의로 숨기라는 뜻이 아니다.

[추천 시스템의 피드백 순환 연구](https://onlinelibrary.wiley.com/doi/10.1002/aaai.12055)는 시스템이 제시한 선택이 나중의 사용자 평가에 영향을 주어 선호 자료가 대표성을 잃을 수 있음을 논의한다. 이는 이 제품의 효과를 입증하지 않지만, 2.0에서도 이미 제시한 출력에 대한 반응을 해석할 때 노출과 교란을 확인할 이유가 된다. 호스트 상태나 관찰이 부족한 경우 결과의 인과 귀속은 미확인으로 남는다. 가능하면 합성 사례와 조건 순서를 사전에 배정하고 동등한 과제·예산에서 짝지어 비교한다. 비교 단위와 불확실성을 보고하며, 적은 표본에서 차이를 발견하지 못한 것만으로 두 방식의 효과가 같다고 주장하지 않는다.

**이번 회의에서 관찰한 근거 없는 수치:** 의장은 발주량·판매 이력과 선택지를 제공하지 않은 합성 요청에서 수치를 만들지 말라고 했다. Claude는 첫 제안에서 주어지지 않은 발주량과 판매 이력·결과를 넣어 권장안을 제시했고, 의장의 반론 뒤 이를 철회했다. 이는 이 회의의 한 답변에 대한 관찰이며 독립 비교, 실제 2.0의 동작이나 일반적인 모델 오류율의 증거가 아니다. `GUIDE-12`는 필요한 근거가 없는 경우를 이후 평가하도록 만든 계획이다.

## 6. 품질·학습·부담 측정

평가자는 가능하면 비교 조건을 모른 채 결과물을 먼저 판단한다. 숫자·사실·논리, 의도와 독자 적합성, 요청한 형식의 사용성, 필요한 수정과 추가 지시를 평가한다. 파일 열기·수정 가능 여부, 그래프의 단위·축·원자료와의 일치도 포함한다. 설명이 매끄럽다는 이유로 잘못된 결과를 통과시키지 않는다. 사용자 평가와 분야별 독립 평가를 구분하고 이견·동률을 보존한다.

학습은 과거 업무의 수정량뿐 아니라 이후 평가 업무에서의 정확성·적합성, 불필요한 일반화, 이전에 잘하던 업무의 회귀, 관련 없는 프로젝트로의 잘못된 전이로 평가한다. 무응답·미사용·수정 없음은 만족과 동치가 아니다. 학습 신호의 확실성, 확인하지 못한 원인, 개입된 모델·도구·가이드 변경을 기록하고, 관측만으로 특정 가이드의 인과 기여를 확정하지 않는다.

사용자 부담은 설명·정정의 반복, 필요한 상담과 불필요한 질문, 중요한 결정의 누락, 사용자가 직접 에이전트 사이를 중계한 횟수·시간으로 본다. 평소 조정은 조용히 하되 요청 시 현재 적용 상태와 허용된 변경 근거를 확인하고 고칠 수 있는지 시험한다.

시간과 비용은 첫 응답, 사용자 결정에 필요한 준비, 사용 가능한 최종 결과까지의 경과 시간, 가이드 검색·조립, 통신·화면 조작·모델 대기, 백그라운드 학습, 재시도·복구를 나눈다. 사용자 전면 작업과 백그라운드 작업의 자원 경쟁을 포함한다. 호스트가 제공한 실제 사용량과 추정치를 구분하고 미제공 수치는 미확인으로 둔다. 병렬 구간의 시간을 중복 합산하거나 캐시 토큰을 총 입력에 다시 더하지 않는다.

가볍고 빠르다는 요구는 별도로 측정한다. 같은 기기·전원 조건에서 미설치 기준과 비교해 유휴·작업 중 CPU와 메모리, 디스크와 색인 크기, 시작·검색·학습 재개 지연의 분포, 백그라운드 작업으로 인한 전면 작업의 지연, 배터리 영향을 확인한다. 큰 가이드 집합과 작은 집합, 동시 업데이트·앱 종료·절전 이후를 포함한다. 모델 대기 시간과 로컬 프로그램의 시간을 분리하며, 관찰할 수 없는 사용량은 미확인으로 둔다. 이는 개발 환경의 동의된 측정이며 제품에 상시 텔레메트리를 넣는 지시가 아니다.

성능·품질 목표치는 제품 책임자와 평가 담당자가 기준선, 사용 목적, 허용 가능한 실패·사용자 부담을 보고 후보 결과를 보기 전에 정한다. 근거 없는 비율·횟수·시간을 보편적 합격선으로 쓰지 않는다. 권한 침해·비밀 유출·사용자 의사 변경 같은 실패는 해당 기능의 배포 판단을 다시 열며 평균 점수로 상쇄하지 않는다. 한 비교가 실패해도 원인을 가리지 않고 전체 제품의 불가능성을 단정하거나 다른 독립 작업을 중단시키지 않는다.

참조와 식별자 자체가 민감할 수 있으므로 필요 최소 범위와 접근 제어를 적용한다. 이 형식은 원문을 숨겨 담는 필드를 허용하지 않는다. 합성 시험 자료의 저장과 실제 사용자의 자료 참조를 구별한다. 성공한 시도만 보존하거나 실패 후 조건을 바꾼 재시도를 같은 입력의 최초 성공처럼 보고하지 않는다.

문서 작성 완료와 제품 검증 완료는 별도다. 최종 인계에는 실제 확인한 커밋, 정확한 명령과 결과, 실행하지 못한 검사와 이유, 앱/운영체제별 미확인 근거, 다음 행동을 적는다. 모든 계획 사례가 아직 미실행이면 그대로 보고한다.

## 8. 회의에서 구체화한 첫 시연과 반증 실험

아래는 **기획 사례**이지 실제 데모나 평가 결과가 아니다. 가상의 사용자가 투자자용 이탈 분석을 대략적으로 의뢰하고 Word를 고른다. 의뢰 세션은 목적·형식·결정사항을 정리한다. OpenSocrates가 적합한 초기 가이드와 맥락을 준비해 실제 작업 세션에 전달하고, 그 세션이 그래프가 필요하다고 요청하면 계층을 통해 다른 실제 세션에 위임한다. 사용자가 “결정과 다음 행동을 앞에 두자”고 수정하면, 그 신호에서 범위와 불확실성을 가진 가이드 후보를 조용히 만들고 관련 진행 중 작업에 반영할 수 있는지 시도한다. 다음의 유사 업무와 관련 없는 업무에서 각각 적용의 적절성을 확인한다. 실제 입력과 결과를 창작해 성공처럼 제시하지 않는다.

구현 전에 독립적으로 착수할 수 있는 실험은 다음과 같다.

1. **중단과 입력 유실:** 합성 입력·호스트 대역으로 해석 도중 중단한다. 재독 가능/불가와 전달 전/후 중단을 각각 시험해 복구, `input_unavailable`, `payload_unrecoverable`, `effect_unknown`, 중복 방지를 구분한다. 호스트 대역의 성공은 실제 앱의 재독 가능성을 증명하지 않는다.
2. **실제 한 셀 왕복:** 이용 가능한 앱·OS 하나에서 공개 가능한 합성 작업으로 새 대화 생성, 작업 식별, 가이드와 맥락 전달, 결과의 계층 경유를 관찰한다. 각 단계가 불가능하거나 미확인이면 그대로 기록한다. 한 셀의 결과를 네 셀의 지원으로 일반화하지 않는다.
3. **개인화의 기여:** 같은 정보와 조건을 가진 기본 가이드, 사실 메모, 개인 가이드를 가능한 범위에서 비교하고, 학습에 쓰지 않은 후속 업무·무관 업무·달라진 선호를 본다. 결과를 모르는 평가자와 실제 사용자 평가를 가능한 범위에서 분리하고, 실패·동률·비용·지연도 보존한다. 사실 메모보다 낫다는 결과가 없더라도 팀 통신이나 맥락 관리의 가치를 자동으로 부정하지 않는다.
4. **맥락 복귀 단서:** 공개 합성 업무를 단서 없음, 허용된 근거에서 자동 준비한 단서, 의도적으로 오래되거나 충돌하는 단서로 비교한다. 공통 원천에 대한 접근과 모델·도구 조건을 가능한 한 맞추되, 추가로 제시되는 단서의 내용은 실험 조건에 따라 다르다고 명시한다. 호스트 기억의 통제 가능 여부와 모델의 비결정성도 기록한다. 참가자와 과제 간 배정·순서를 균형 있게 하고 학습·순서 효과를 기록한다. 가능한 범위에서 결과 평가자를 조건에 눈가림하고, 실제 사용자 평가도 별도로 설계한다. 올바른 방향의 과제 완료와 결과 품질, 과거 사실·권한의 오인, 잘못된 파일 수정, 필요한 확인 누락과 불필요한 질문, 사용자 수정·부담, 총 소요 시간·비용을 함께 본다. 첫 클릭까지의 시간만으로 복귀 성공을 판단하지 않는다. 실패·미확인·지원되지 않는 조건을 보고하고, 평가를 위해 실제 사용자의 원문·스크린샷·작업 공간 내용을 보관하거나 메모 작성을 강요하지 않는다. 이는 미실행 계획이며 특정 단서의 효과를 가정하지 않는다.

단서를 **사람에게 보여 주는 효과**와 **작업 세션에 전달하는 효과**는 구분한다. 에이전트만 실행한 결과로 사람의 복귀 경험이나 부담을 주장하지 않는다. 세션 간 조정이 필요한 사례에서는 실제 세션을 계층으로 연결할 수 있는지와 이 비교 자체의 효과를 각각 기록한다. 단서가 없다는 조건도 현재 지시와 허용된 맥락을 모두 제거한다는 뜻은 아니다.

모델의 자체 보고, 가이드 ID 전달, 파일 존재는 각기 다른 관찰이다. 어느 하나도 실제 사고 방식 변화나 품질 향상의 단독 증거로 바꾸지 않는다. 목표는 멋진 시연 영상만이 아니라 사용자가 실제로 덜 설명하고도 유용한 결과와 통제감을 얻는 경험이며, 검증 전에는 이를 달성했다고 쓰지 않는다.

### 실제 연결의 첫 왕복: 구별해야 할 관찰

이 실험은 **미실행 계획**이다. 해당 호스트의 지원·권한을 먼저 확인하고 공개 합성 업무를 사용한다. 새 실행 대화 A와 B를 만들고, 의뢰 대화가 제작하지 않은 상태에서 A → 계층 → B → 계층 → A로 합성 질문과 답을 교환한 다음 계층을 통해 결과를 사용자에게 돌려주는 것이 목표다. 앱·모드·OS·계정 조합과 사용한 진입점을 기록하고, 해당 대화가 실제로 모델 턴을 시작했는지와 각 대화의 귀속 근거를 별도로 살핀다. 사용자의 붙여넣기나 이번 회의처럼 의장 세션이 계층 없이 옮기는 대조는 자동 통신의 성공이 아니다. 반대로 **계층이 허용된 호스트 에이전트의 화면 조작을 실제로 호출하고 요청·결과가 계층을 거친 경우**, 조작 주체가 에이전트라는 이유만으로 수동 중계라 단정하지 않는다. 어느 경로가 실제로 제공되고 허용되는지는 별도로 입증해야 한다.

공개 합성 표지를 각 방향의 본문에 따로 두고 상대 세션이 그 본문을 어떤 경로로 받았는지 확인한다. 표지 반향·시간·공유 연결만으로 수신 세션의 신원, 개인 자료를 받을 권한이나 가이드 전체 사용을 증명하지 않는다. 입력창 채움에서 멈춤, 발송 뒤 수신 미확인, 턴 종료 뒤 재개 경로 부재, 잘못된 창, 이미 외부 효과가 생겼을 수 있는 재시작을 각각 시험한다. 열린 연결이나 일회용 값의 소지만으로 본문 접근을 허용하는 설계를 안전하다고 간주하지 않는다. 민감하지 않은 합성 시험의 가능성과 실제 업무 내용의 전달 권한은 별개다.

기기 잠금·앱 종료·사용자 입력과 재개를 각 표면에서 확인하고, 새 승인 여부는 실제 호스트와 사용자 지시를 따른다. 전송 또는 효과가 미확인일 때 성공·미발송으로 단정하거나 같은 외부 동작을 무작정 재시도하지 않는다. 필요한 원문을 현행 정책 아래 재확보할 수 없다면 본문 유실과 외부 효과 미확인을 구분한다. 최초 관찰은 한 셀의 근거이며, 다른 앱·모드·OS의 지원이나 사용자 효용을 대변하지 않는다.

### 위임과 개인화의 효과를 각각 비교하는 실험 설계

다음은 **실행 전 설계**다. 같은 가상 코호트 보고서라도 사용자별 교집합 없이 월별 합계만 있으면 전월 관측자 중 다음 달에도 관측된 동일 고객의 유지율을 알 수 없다. 최초 코호트에 속한 각 월의 인원이라는 정의가 확인된다면 최초 인원 대비 비율은 계산할 수 있다. 별도 합성 ID가 있는 두 경우는 아래 산술 관찰처럼 교집합이 달라진다. 산출물은 사용자가 선택한 Word와 실제 편집 가능한 차트를 요구하고, 수치의 의미·원자료·차트·문서의 일치를 각각 살핀다. 사용자가 이전에 한 차례 수정한 내용은 범위와 불확실성이 있는 신호이며, 그것만으로 후속 업무의 선호를 확정하지 않는다.

| 비교 | 바꾸는 조건 | 무엇을 구별하는가 |
|---|---|---|
| 위임 | 같은 가이드·맥락을 가능한 한 제공한 단일 실행 세션과 동적 위임 경로 | 세션 분리와 조정이 가져온 결과·부담·비용. 위임 여부는 실제 관찰하며, 필요 없는 위임을 강제한 진단 실험은 제품의 자율 선택 평가와 따로 표시한다. |
| 개인화 | 공통 기본 48개 선택 경로 위에서 개인 자료 없음, 같은 정보를 담은 사실 메모, 개인 가이드를 각각 적용 | 개인 정보의 전달과 사고 방향을 제시하는 방식의 차이. 한 조건만 유리하게 범위·불확실성·정보를 추가하지 않는다. |
| 실제 앱 경험 | 기존 앱만 이용하는 경로와 2.0 경로 | 제품 전체의 사용자 경험 차이. 호스트 자체 메모리와 세션 구조가 함께 달라질 수 있으므로 위 두 비교의 순수한 효과로 섞지 않는다. |

각 비교는 동일한 직접 지시·합성 입력·목표 형식·허용 권한과 가능한 범위의 모델·앱·도구를 사용한다. 위임 측 비교는 준비된 가이드와 초기 맥락을 맞추되, 각 작업에 필요한 전달은 동적이며 실제로 받은 내용과 지연이 다를 수 있다. 동등한 시간이나 비용으로 모두 통제했다고 가정하지 않는다. 사용량을 확인할 수 있다면 비슷한 예산의 단일 세션 자기 검토를 추가 대조로 살핀다. 사용량이 보이지 않으면 관찰 가능한 대리 지표와 실제 사용량 미상을 구분한다. 가능하면 비교 순서를 섞고 반복하며, 예산이나 시간 제한과 호스트 메모리·계정·세션 상태의 확인 가능 여부를 기록한다. 사용자 설정은 무단 변경하지 않는다. 한 사용자가 여러 조건을 직접 경험하면 학습·피로·순서 효과가 생기므로 비교 가능성을 따로 판단한다. 숨겨진 호스트 상태를 통제할 수 없다면 미확인으로 남긴다.

첫 업무에서 생긴 신호로만 메모와 가이드 후보를 구성하고 해당 평가에 쓰는 버전을 고정한다. 학습 사례와 다른 자료·목적의 관련 후속 업무, 목적이 다른 업무, 명시적으로 현재 선호가 바뀐 업무를 사용한다. 관련 업무의 선호는 사례에 별도로 정해진 의도나 실제 사용자의 별도 평가로 판정하고, 불충분하면 미확인으로 둔다. 합성 사례에는 이전 수정이 일회성이었던 반대 의도도 포함해 무조건 결론 우선으로 점수를 얻지 못하게 한다. 감사라는 이름만으로 개인 가이드를 금지하지 않으며 현재 지시는 과거 후보보다 우선한다. 실제 사용자를 매번 기록자로 만들지 않는다. 필요할 때 독립 평가자와 사용자 평가를 구분하고, 평가자가 조건을 모르게 할 수 있는 범위와 불가능한 이유도 밝힌다. 결과물의 구조로 조건이 드러나면 맹검 실패를 보고한다. 한 가이드의 결과를 가이드 생성·학습 체계 전체의 효과로 일반화하지 않는다.

**시도별 결과표**에는 가능한 범위에서 앱·OS·모드와 모델, 업무·자료 변형, 비교 조건, 가이드/맥락 전달·실제 사용의 관찰 수준, 완료·부분·실패·시간초과, 수치 정의와 계산, Word에서 차트 편집 여부, 현재 지시 존중, 질문·사용자 결정·실제 정정 및 필요했던 질문 누락, 소요 시간·조정 지연·노출된 비용·재시도를 각각 둔다. 평가 불가와 미노출은 0이 아니다. 사용자에게 선택권을 주는 필요한 질문과 불필요한 반복 질문을 구분한다. 파일 구조에 차트 객체가 존재한다는 점과 실제 Word에서 차트를 편집할 수 있다는 점도 분리해 확인한다. 동일 사례의 동률, 위임으로 악화된 결과, 중단과 실패도 빠짐없이 보고한다. 사전에 평가 기준과 반례를 정하되 임의의 성공률을 제품 요건으로 만들지 않는다. 표본·불확실성·비교의 한계가 충분치 않으면 차이를 발견하지 못한 것을 동등성의 증거로 바꾸지 않는다.

특히 같은 오류를 여러 세션이 물려받아 자신 있게 확산시키는 경우, 단일 세션이 더 빠르고 정확한 경우, 새 명시 지시가 과거 가이드와 충돌하는 경우가 드러나도록 한다. 현재 가능한 것은 공개 합성 자료·검사 설계와 대역을 통한 제한적 실험이다. 자동 계층 전달·실제 세션 작업·가이드 사용·사용자 효용은 각각 구현과 해당 호스트에서의 관찰이 필요하다. 사람이 수동 중계한 시연은 그렇게 밝히며 자동 채널의 성공으로 세지 않는다. 실제 사용자 원문 대화·작업 파일·화면·숨은 추론을 평가 저장소에 복사하지 않고, 참조·메타데이터도 항목별 보관 허용을 확인한다.

### 가이드 검색과 적용을 나눠 시험하기

합성 요청·가이드·권한의 묶음을 만들고 평가 전에 작업별 허용 범위, 적합한 후보의 집합, 적용하면 안 되는 사례, 가이드 없이 진행해도 되는 사례를 검토한다. 복수 가이드가 맞을 수 있고 정답 후보가 없을 수도 있으므로 한 ID만 정답으로 고정하지 않는다. 같은 의도를 표현한 거친 말·맞춤법·어미·두 글자·동의어와, 단어는 비슷하지만 긴급성이나 의도가 반대인 경우를 포함한다. 평가자 이견과 사례의 모호성도 보존한다.

검색 후보에서 적합한 허용 가이드를 놓친 비율과 부적합 후보의 포함을 먼저 살피고, 별도로 실제 선택에서 금기·현재 지시를 어긴 경우와 적합한 개인 가이드를 놓쳐 불필요하게 fallback한 경우를 본다. 비인가 가이드가 후보 내용·참조·결과·진단으로 노출되는지는 정확도 점수와 별도의 경계로 시험한다. 검색에 실패한 상태와 충분히 검토해 적합한 후보가 없는 상태, 전달과 읽기·사용의 미확인을 나눈다. 표본, 언어, 허용 범위, 시도·실패·평가 불가와 사용자 부담을 함께 보고하며 후보 일치만으로 품질 개선을 주장하지 않는다.

기본 정본 48개와 여러 규모의 공개 합성 개인 가이드를 별도로 시험하고, 예를 들어 10개와 10만 개는 **측정 규모 후보**이지 개인 가이드의 개수 제한이 아니다. 동일 기기·색인 상태·작업 부하에서 정확도와 함께 검색·재검색·의미 판단·전달의 지연과 사용량을 구분한다. 비교 대상이 1.x라면 실제 해당 호스트의 선택 경로와 증거를 사용한다. 단순 FTS 실험을 1.x 또는 미구현 2.0 자체의 성능으로 바꾸어 적지 않는다. 개인정보 정책상 허용되지 않는 실제 요청·가이드 원문은 시험 기록이나 색인에 보관하지 않는다.

**이번 회의의 제한된 검색 관찰:** 2026-11-03 macOS의 Python 3.14.8·SQLite 3.53.4에서 `python3 docs/v2.0/examples/canonical_search_probe.py`를 실행했다. 이 스크립트는 로컬 정본 48개의 한국어 이름과 전체 절차를 메모리 DB에 넣고 직접 고른 일곱 문자열을 각각 하나의 인용 구절로 검색한다. `실패`는 unicode61에서 8개·trigram에서 0개, `근본원인`은 각각 0개·1개, `뭐가 망할지`는 둘 다 0개였다. 첫 번째의 unicode61 결과에 사전부검이, 두 번째의 trigram 결과에 근본원인분석이 포함됐다. 관찰 당시 `git diff --stat v1.5.3 HEAD -- content/methods`는 변경을 보이지 않았다. 이것은 검색 순위·가이드의 의미상 적합성·호스트 전달·실제 사용이나 2.0 효과를 측정한 시험이 아니다. 공개 정본을 대상으로 한 한 환경의 정확 구절 탐색이며, 제품의 선택기 또는 개인정보가 포함된 개인 색인의 성능으로 일반화하지 않는다.

별도로 같은 macOS에서 저장소의 잠긴 Python 3.12.15 환경을 사용해 1.x in-turn `decision`에 사람이 만든 합성 구조화 특성(`judgment`, `risk_assessment`, `diagnose=3`, `failure_risk=3`)을 전달했다. `uv run --locked --no-sync python docs/v2.0/examples/canonical_routing_probe.py`의 출력은 `weighted_primary`, 후보 `premortem-analysis`, `applied: unverified`, `selector_model_calls: 0`이었다. 이 절차의 정본 본문에는 긴급 억제를 지연시키는 경우의 중단 조건이 있지만 선택 메타데이터의 `contraindications`는 비어 있다. 후보가 반환된 뒤 본문을 확인하고 적용 가능성을 판단하는 계약이 있으므로, 이 차이나 합성 후보 반환만으로 실제 호스트가 금기를 어겼다고 단정하지 않는다. 특성은 사람이 지정한 것이며 실제 사용자 발화가 그렇게 분류되었거나 세션에서 이 절차가 읽히고 적용됐다는 증거가 아니다. 선택기 내부의 모델 호출 수 0도 이 시험에 앞선 호스트의 분류 비용이나 행동에 관한 관찰이 아니다.

### 위임 검수에 관한 이번 회의의 관찰

2026-11-03 회의에서 의장은 시스템 설계의 합성 코호트 사례를 논의하며 `78/89`를 동일인 전월 유지율이라고 잘못 제시했다. Claude와 Grok은 초기 답변에서 그 의미를 받아들였고, Claude는 산술도 재계산했다고 보고했다. 이후 의장이 가능한 동일인 교집합의 반례를 제시하자 두 모델 모두 기존 해석을 정정했다. 같은 잘못된 설명을 두 모델에 제공했으므로 이는 독립적인 모델 정확도 평가가 아니다. 합의와 산술 검증이 공유 가정의 의미까지 보장하지 않는다는 **이 회의의 관찰**이다.

의장은 공개 합성 ID 집합으로 두 시나리오를 만들고 macOS의 Python 3.14.8에서 `python3 docs/v2.0/examples/cohort_overlap.py`를 실행했다. 두 시나리오 모두 최초 110명, 1개월 89명, 2개월 78명이고, 두 달 교집합은 각각 78명·57명이었다. 출력은 동일인 유지율 각각 87.64%·64.04%와 동일한 인원비 87.64%를 보였다. 이는 합성 집합에서의 산술 관찰이지 실제 사용자 데이터, 2.0의 자동 위임·검수 또는 품질 개선의 증거가 아니다. 재현 코드의 입력과 관측은 공개 합성이며 실제 프롬프트·화면·업무 파일을 보관하지 않는다.

### 공개 시연을 설득력 있게 만드는 근거

사용자가 제시한 높은 공개 기준은 특정 인물이 공유할지를 예측하거나 약속하는 지표가 아니다. 그 기준을 개발에서 시험할 수 있는 형태로 바꾸면 다음과 같다. 아래는 시연 계획이며 실행·게시 결정이 아니다.

- **한눈에 보이는 첫 업무:** 공개 가능한 합성 자료로 의뢰 상담, 사용자가 선택한 결과물 형식, 기존 앱의 새 실행 대화, 계층을 통한 추가 위임, 실제 열리고 수정 가능한 결과물을 보여준다. 파일이 만들어진 사실과 가이드 전달·각 세션의 실제 작업은 따로 확인한다.
- **학습의 후속 효과:** 첫 업무에서 나타난 수정의 적용 범위와 불확실성을 가진 가이드 후보가 관련된 별도 후속 업무에서 어떻게 선택되는지, 무관한 업무에서는 어떻게 취급되는지와 선호가 바뀌었을 때의 교정을 보여준다. 호스트 자체 메모리·기본 가이드·동등 정보 메모 비교와 실제 사용 평가를 함께 제시한다. 예쁜 한 번의 결과를 일반적 개선으로 부르지 않는다.
- **실패를 숨기지 않는 팀:** 진행 중 수정, 세션을 열 수 없음, 입력·결과 미확인 중 적어도 시연에서 주장하는 경로의 실패와 복구를 확인한다. 화면을 잇는 사람이 중계했다면 시스템의 자율 통신처럼 편집하거나 묘사하지 않는다. 이 회의에서 Codex가 Claude와 Grok의 발언을 전달한 것은 수동 중계된 기획 회의이지 2.0 프로그램이 작동했다는 증거가 아니다.
- **검토 가능한 근거:** 합성 입력과 평가 조건, 실제 앱·OS·모드, 버전, 각 단계의 관찰 수준, 실패와 비용을 정책상 허용된 범위에서 제공한다. 실제 원문 대화·화면·사용자 작업물의 보관이나 녹화가 필요하다는 가정은 하지 않는다. 새로운 보관 범위를 제안하려면 현행 정책과 별도로 검토한다.

사용자의 실제 업무에서의 효용, 호스트별 지원, 구현의 개인정보 경계는 각각의 근거가 필요하다. 위 예시가 되는 한 가지 셀의 성공은 네 가지 앱·OS 지원이나 효과의 일반성을 뜻하지 않는다.

## 9. 소스 검사와 출시 판단

구현을 모두 통합하고 검토할 파일이 안정된 뒤 [CONTRIBUTING.md](../../CONTRIBUTING.md)의 전체 소스 검사를 해당 커밋에 실행한다.

```sh
make bootstrap
make format-check
make lint
make generated-check
make content-check
make adjudication-check
make docs-check
make governance-check
make package-check
make security-scan
make smoke
make installer-check
```

정본 생성 입력을 바꿨다면 `make generate`로 정본·생성 결과를 함께 갱신한다. 새 DB·채널·가이드 생성·호스트 어댑터의 동작은 그 구현에 맞는 테스트를 추가하며, 명령 이름을 이 문서에서 먼저 만들어 통과했다고 보고하지 않는다. macOS 네이티브 패키지·릴리스 주장은 문서화된 Apple-silicon 환경의 `make release-check`와 해당 설치·업데이트·복구 근거가 필요하다. Windows 네이티브 주장은 실제 Windows 환경에서 시험한다. 기존 `npm run test:windows`와 패키지 검사는 유지하되 그것만으로 새 2.0 앱 연결·UI 동작·학습을 증명하지 않는다.

출시는 요청한 두 앱×두 운영체제의 명시한 기능 범위에 대해 실제 호스트 근거를 갖추고, 사용자 요구·데이터 정책·복구와 업데이트·정본 일치·필수 검사·독립 리뷰가 해당 주장에 맞게 충족될 때 검토한다. 미확인 셀이 있으면 그 셀을 지원한다고 발표하지 않는다. 범위를 줄이는 결정은 사용자에게서 받아야 하며, 시험 환경이 없다는 이유로 필수 범위를 조용히 삭제하지 않는다. 다른 셀의 부족한 근거는 이미 확인된 한 셀의 관찰을 무효로 만들지 않는다.
