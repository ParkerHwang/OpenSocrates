# OpenSocrates 2.0 제품 방향과 요구사항

상태: 2026-11-02 사용자 인터뷰를 반영한 개발 기준 문서. 제품 방향을 정리한 것이며 구현, 설치 지원, 학습 효과 또는 출시 완료의 증거는 아니다. [English](VISION_2.0.md).

## 제품이 제공할 경험

사용자는 평소 쓰는 데스크톱 AI 앱의 대화에서 일을 의뢰한다. OpenSocrates는 불완전한 요청을 이해하고, 필요한 질문과 결과물 상담을 거쳐 업무 프롬프트를 정리한다. 현재 작업에 맞는 추론 가이드와 맥락을 준비하고 새로운 실제 대화 세션들에 작업을 전달한다. 각 작업 세션은 OpenSocrates 레이어를 통해 협의하고 결과를 돌려준다. 사용자는 그 팀을 직접 조직하거나 매번 같은 설명을 반복할 필요 없이 결과와 중요한 결정에 집중한다.

각 사용자의 OpenSocrates는 실제 업무 경험에서 추론 가이드를 만들어 발전시킨다. 추론 가이드는 단순한 사실 메모나 금지 목록에 머무르지 않고, 어떤 맥락과 관점에서 생각할지 돕는다. 동시에 OpenSocrates는 가볍고 빠른 데이터베이스와 통신·상태 관리 기능을 포함하는 실제 프로그램으로 발전한다.

사용자가 원하는 것은 서로 다른 앱에서 사용자에게 보이는 실제 대화 세션이 한 팀으로 일하는 경험이다. 이는 어떤 subagent도 이와 비슷한 일을 할 수 없다는 보편적 기술 주장과 다르다. 또한 사용자는 고정 역할 정의가 강력한 모델의 가능성을 제한할 수 있다고 보아 사전 정의된 역할표 없이 업무·기대 결과와 추론 가이드를 전달하는 방향을 선택했다. 역할 프롬프트의 일반적인 효과나 이 방식의 품질 우위는 별도 검증이 필요하며, 업무에 필요한 구체적 능력·도구·결과를 설명하는 것까지 금지하지 않는다.

## 한눈에 보는 작동과 남은 검증

다음은 **목표 경험**이다. 각 연결과 품질이 지금 동작한다는 뜻은 아니다.

| 사용자가 겪는 일 | OpenSocrates가 맡을 일 | 개발에서 확인할 핵심 |
| --- | --- | --- |
| 평소 쓰는 앱에서 거칠게 의뢰하고, 필요하면 결과물 형식을 상담한다. | 의뢰 대화에서 목적·선택·권한을 정리하고, 적합한 가이드와 맥락을 준비한다. | 이미 정한 선택을 다시 묻지 않는가? 의뢰 대화가 실제 산출을 대신하지 않는가? |
| 맡긴 일의 결과와 중요한 결정에 집중한다. | 별도 실제 대화에 작업을 맡긴다. 유용할 때 추가 대화를 열고 업무 요청·응답을 계층으로 연결한다. | 앱·모드·OS마다 실제 대화 생성, 대상 식별, 가이드·맥락 전달과 왕복이 가능한가? |
| 같은 설명을 반복하지 않으면서도 현재 선택을 바꾸고, 이전 방향으로 돌아갈 수 있다. | 허용된 경험에서 개인 가이드를 발전시키고, 적합하면 조합·재조립한다. 기본 48개도 상황에 맞게 쓴다. | 개인화가 실제로 도움이 되는가? 진행 중 적용과 학습의 중단·재개가 사용자 선택을 존중하는가? |
| 결과물이 원하는 형식으로 쓰이고, 필요한 경우 기존 파일도 이어서 다뤄진다. | 작업 세션의 결과를 전달하고 관련 파일·맥락 상태를 다룬다. 다음 관련 작업에서 외부 변경을 살핀다. | 파일을 실제로 열고 원하는 방식으로 편집할 수 있는가? 외부 변경·경합과 사용자 접근을 확인할 수 있는가? |

연결이 막히면 가능한 상담과 무관한 작업은 계속하되, 확인하지 못한 작업 시작·수신·완료를 성공으로 표시하지 않는다. 원문 대화나 작업 내용을 프로그램의 영구 저장소에 복제하지 않는 현재 정책도 유지한다. 작업 흐름과 실패 경계는 [시스템 구조](SYSTEM_2.0.ko.md), 착수·통합은 [개발 로드맵](ROADMAP_2.0.ko.md), 증거와 비교 실험은 [검증 계획](VALIDATION_2.0.ko.md)에서 이어진다.

## 확정된 범위와 범위 밖의 일

| 항목 | 첫 2.0 개발 범위 |
| --- | --- |
| 앱 | ChatGPT 데스크톱 앱과 Claude 데스크톱 앱 |
| 운영체제 | macOS와 Windows. 앱과 운영체제의 네 조합을 각각 검증한다. |
| ChatGPT 내부 경험 | Chat·Work·Codex를 같은 데스크톱 앱 안의 경험으로 취급한다. 각 경험의 연결 능력은 별도로 확인한다. |
| 실행 방식 | 사용자가 이미 사용하는 앱의 실제 대화 세션을 활용한다. 모델 제공자 API를 직접 호출해 별도 에이전트 앱을 만드는 방식은 현재 범위에서 제외한다. |
| 컴퓨터 조작 | 필요할 때 앱이 제공하는 computer use 또는 기존 오픈소스 도구를 활용하는 방향이다. 구체적인 도구는 호스트 조사 후 결정한다. |
| 기기 | 우선 한 컴퓨터 안에서 동작한다. 여러 컴퓨터의 동기화와 개인 데이터 이전은 후속 업데이트 범위다. |
| 연기한 호스트 | Grok Bot, Cursor, Antigravity 및 기타 앱 연결은 첫 버전의 지원 대상이 아니다. 기존 릴리스의 지원 기록을 변경하지 않는다. |

사용자가 원하는 macOS·Windows 지원은 제품 요구다. 문서, 스킬 파일 또는 한 운영체제의 성공만으로 다른 조합의 실제 지원을 주장하지 않는다. 접근 불가능한 조합은 미검증으로 남기며, 필수 범위 축소는 제품 소유자의 별도 결정이 필요하다.

## 세 종류의 가이드

| 종류 | 출발점과 변화 주체 | 사용 방식 |
| --- | --- | --- |
| 기본 48개 추론 가이드 | 설치 시 제공되는 기본 콘텐츠. 제품 버전 관리 대상이다. | 개인 가이드가 아직 없거나 적합한 개인 가이드가 없을 때 사용한다. 개인 가이드가 일부만 맞으면 적합한 기본 가이드와 보완·재조립할 수도 있다. |
| 공통 가이드 생성 지침 | 모든 사용자에게 공통으로 제공한다. OpenSocrates 버전업으로 발전시킨다. | 개인별 학습 로직이 경험을 추론 가이드로 바꾸고 평가하는 기준으로 활용한다. 사용자별 학습이 이 공통 지침을 임의로 다시 쓰지는 않는다. |
| 개인별 생성 추론 가이드 | 각 사용자의 실제 작업·선택·수정·관련 경험을 바탕으로 생성하고 발전시킨다. | 적합한 개인 가이드를 우선 사용한다. 여러 가이드를 선택·조합·재조립할 수 있다. |

개인별 생성 가이드의 개수에는 48개 같은 고정된 제품 상한을 두지 않는다. 이는 디스크·컨텍스트·계정 사용량이 무한하다는 뜻은 아니다. 검색, 전달량, 중복과 오래된 가이드 처리, 저장 예산은 측정 가능한 설계 과제로 남긴다.

재조립은 문서를 나란히 붙이는 것보다 넓은 작업이다. 현재 업무에 필요한 부분을 선택하고 연결해 적합한 사고의 흐름을 만들 수 있다. 필요하면 OpenSocrates를 통해 별도 에이전트 세션에 재조립 업무를 의뢰한다. 재조립 결과를 이번 작업에서만 쓸지 개인 가이드로 남길지도 관련 경험과 맥락을 보고 판단하는 방향이다. 이 판단의 구체적인 기준과 검증 방법은 구현 전에 명세한다.

## 요구사항과 확인 가능한 결과

이 표의 `REQ-01`–`REQ-16`은 제품 요구사항이다. 로드맵의 `P01`–`P15` 작업과 구분한다. 이전 초안의 비전 `P01`–`P16`은 같은 번호의 `REQ-01`–`REQ-16`에 대응한다.

| ID | 요구사항 | 수용 사례 |
| --- | --- | --- |
| REQ-01 | 불완전한 요청에서 목적·제약·원하는 결과를 파악한다. 결정에 영향을 주는 빈칸만 구체적으로 묻는다. | 사용자가 두서없이 보고서를 의뢰했을 때 이미 말한 내용을 다시 묻지 않고, 결과가 갈리는 핵심을 짚어 질문한다. |
| REQ-02 | 결과물의 내용·형식·사용 방식을 대략 보여주며 필요한 상담을 한다. 사용자의 이해 수준을 상황별로 살핀다. | Word와 HTML의 차이를 모르는 사용자에게 수정·공유·사용 경험의 차이를 설명한다. 이미 형식을 선택한 사용자에게 불필요하게 선택을 되돌리도록 유도하지 않는다. 모든 사소한 일에 상담을 반복하지 않는다. |
| REQ-03 | 사용자가 의뢰한 대화 세션에서는 실제 산출물 제작을 수행하지 않는다. | 의뢰 세션은 요청 해석, 업무 프롬프트 준비, 가이드·맥락 준비, 상태 전달과 중요한 결정 상담을 담당한다. 조사·분석·그래프·문서 제작과 실제 결과물 통합은 새 작업 세션에서 수행한다. 완성 결과의 전달·표시는 의뢰 세션에서 가능하다. |
| REQ-04 | 실제 앱 대화 세션을 열어 일을 수행한다. | 사용자는 평소 의뢰 세션만 사용해도 된다. 필요하면 앱의 대화 목록에서 작업 세션을 열어 확인하거나 참여할 수 있다. 세션 생성과 접근은 앱이 허용하는 기능으로 각각 검증한다. |
| REQ-05 | 모든 에이전트 간 통신·위임은 OpenSocrates 레이어를 거친다. | 조사 세션이 그래프가 필요하다고 판단하면 OpenSocrates에 의뢰를 전달한다. 레이어가 작업 연결과 가이드·맥락 전달을 처리하며 결과와 협의도 같은 경로로 전달한다. 직접 우회 통신은 이 요구를 충족하지 않는다. 호스트 내부의 모든 동작을 관찰하거나 통제할 수 있다고 가정하지 않는다. |
| REQ-06 | 업무와 기대 결과가 명확한 단일 의뢰 프롬프트로 동적으로 일을 맡긴다. | 사전 역할 목록이나 역할별 AGENTS.md 없이 현재 과업에 맞는 세션을 구성한다. 요청 내용, 결과물과 관련 제약은 그 의뢰에 맞게 명확히 한다. |
| REQ-07 | 앱·모델 선택과 위임 필요성을 맥락에 맞게 판단한다. | OpenSocrates가 해당 컴퓨터에서 사용 가능한 앱·모델·도구·권한을 고려해 맡길 곳을 선택한다. 추정한 능력과 실제 결과의 품질을 구분해 확인한다. |
| REQ-08 | 의뢰·실행·재조립·학습 등 판단에 참여하는 각 세션에 적합한 추론 가이드와 맥락을 전달한다. | 의뢰 세션에도 요청 해석과 상담에 유용한 가이드가 필요하다. 학습용 세션에는 제품 버전의 공통 생성 지침 전체 또는 제품이 완결된 단위로 정의한 모듈과 그 필수 의존·보호 조건을 전달한다. 해당되는 가이드가 없으면 억지로 적용하지 않으며, 전송·읽기·사용·품질은 구분한다. |
| REQ-09 | 적합한 개인 가이드를 우선 선택하고 필요하면 기본 48개로 보완하거나 적합한 개인 가이드가 없을 때 기본 가이드를 활용한다. | 초기 사용자와 충분한 개인 경험이 쌓인 사용자의 동일 과업을 각각 시험한다. 부분적으로 맞는 개인 가이드와 기본 가이드의 조합·재조립도 평가한다. 관련 없는 개인 가이드를 억지로 쓰지 않으며, 사용자가 지정한 조건이 우선한다. |
| REQ-10 | 맥락을 사용자·프로젝트·업무·시점에 맞게 선택하고 우선순위와 버전을 관리한다. | 같은 사용자의 다른 프로젝트 경험을 무차별 적용하지 않는다. 사용자가 이전 방향으로 돌아가려 할 때 해당 흐름을 가져오며, 당시 가정과 현재 확인된 사실을 구분한다. Git 트리는 기능을 설명하는 비유이며 Git 구현 선택은 미정이다. |
| REQ-11 | 사용자 확인이 필요한 중요한 결정을 상황별로 판단한다. | 각자 사소해 보이는 결정이 합쳐져 중요한 변경이 되는 경우도 평가한다. 사용자의 확인, 위임받은 권한과 이미 확정한 선택을 보존한다. 학습된 선호가 새 권한을 만들지 않는다. |
| REQ-12 | 실제 작업에서 조용히 배우고 관련 진행 중 작업에도 반영할 수 있다. | 사용자가 '배워'라고 말하지 않아도 관련 경험을 학습 후보로 다룬다. 허용된 상태로 변경의 관련성을 추적하고 개인 선호·프로젝트 제약·일회성 상황을 구분한다. 요청 시 확인 가능한 가이드 적용 상태와 허용된 근거를 설명하고 범위 조정·사용 중지·삭제 요청을 다룬다. 실제 사용이나 근거를 확인할 수 없으면 미확인으로 밝힌다. |
| REQ-13 | 백그라운드 학습 자체의 진행을 기록하고 중단 후 재개한다. | 관찰한 경험, 아직 다루는 문제, 적용해 본 가이드와 미확인 결과를 구분한다. 재개 시 그사이 바뀐 맥락을 확인하며 중복 반영과 완료 오인을 시험한다. 개인적인 비공개 추론 과정을 저장하지 않는다. |
| REQ-14 | 파일·폴더·버전 관리도 맥락에 맞게 수행한다. | 기존 파일을 수정할지, 새 버전을 남길지, 관련 폴더를 정리할지를 일의 의미와 기존 방식에 맞게 판단한다. 관련 없는 파일을 임의로 변경할 권한이 생기는 것은 아니다. |
| REQ-15 | 관련 작업 재개 시 외부 파일 변경을 발견하고 해석한다. | 모든 폴더를 계속 감시하지 않는다. 이전에 남긴 허용된 상태 기록과 현재 파일을 비교한다. 비교할 이전 내용이 없으면 구체적인 차이를 안다고 주장하지 않는다. 수정자나 의도도 별도 근거 없이 단정하지 않는다. |
| REQ-16 | 한 팀이 자율적으로 일하되 사용자가 중간 전달자나 팀 관리자가 될 필요를 줄인다. | 에이전트가 필요한 업무를 발견하고 OpenSocrates를 통해 협의할 수 있다. 중요한 결정은 의뢰 대화에 전달한다. 백그라운드 동작이 중단되거나 호스트가 제한되면 그 상태를 분명히 한다. |

## 필요조건과 충분조건을 적용할 대상

**무엇의 조건인지 먼저 구분한다.** 사용자가 정한 전체 2.0 범위의 충족, 특정 환경에서 한 건의 협업을 관찰한 것, 실제 사용자에게 유용하고 계속 쓰이는 제품은 서로 다른 주장이다. 아래는 사용자 결정과 검증 계획을 정리한 것이며 현재 이 조건들이 충족됐다는 뜻이 아니다.

| 판단 대상 | 필요한 것과 확인 방법 | 그것만으로 충분하지 않은 이유 |
| --- | --- | --- |
| **전체 2.0 범위** | 위 `REQ-01`–`REQ-16`과 확정된 앱·OS 범위를 각 요구의 적용 조건에 맞게 충족해야 한다. 초기 48개와 개인 가이드의 진화, 의뢰·실제 작업 대화의 분리, 계층을 통한 협업, 사용자 선택과 권한, 맥락·파일·학습의 연속성이 모두 요구된다. | 가이드 파일의 존재, 합성 검사 통과 또는 한 앱의 성공만으로 다른 기능·환경까지 충족되지는 않는다. 특정 DB나 고정 역할, 모든 경험에서 새 가이드를 만드는 일은 사용자가 정한 필수조건이 아니다. |
| **지정한 한 건의 협업 관찰** | 예를 들어 그래프 분담이 필요한 합성 보고서 한 건이라면, 실제 작업 대화와 적합한 가이드 전달, 계층을 통한 실제 요청·반환, 선택한 결과물의 확인이 해당 앱·OS에서 관찰돼야 한다. | 전송 시도나 가이드 ID만으로 수신·사용이 확인되는 것은 아니다. 한 건의 관찰은 다른 환경이나 개인화의 장기 효과를 입증하지 않는다. |
| **실제 사용자에게 유용하고 계속 쓰이는 제품** | 실제 사용자에게 도움이 되고 이용되는 것이 필요하다. 이를 주장할 때는 실제 업무의 결과 품질·부담·신뢰와 사용에 관한 근거를 별도로 살핀다. 무엇을 누구에게 어떤 기간 동안 성공으로 볼지는 평가에서 분명히 한다. | 기능 목록이나 문서·시연만으로 사용자의 만족이나 채택을 보장할 수 없다. 비교 평가가 아직 없다는 사실도 실제로 유용하지 않다는 증거는 아니다. |

**필요충분조건은 좁게 정의한 판정에 한정한다.** 예를 들어 어떤 합성 보고서 시험의 `PASS`를 “미리 정한 환경에서 실제 별도 대화, 해당 시험이 요구하는 가이드 전달, 한 번 이상의 계층 경유 요청·반환 및 결과물 확인이 모두 관찰됨”으로 정의했다면, 이 항목들이 모두 관찰되는 것은 *그 시험의 PASS*에 대해 정의상 필요하고 충분하다. 이 동치는 시험 정의에서 나온다. 시험이 통과돼도 관찰 범위 밖의 동작, 전체 `REQ-01`–`REQ-16`, 다른 앱·OS 또는 실제 사용자에게 도움이 된다는 주장이 자동으로 참이 되지는 않는다. 각 단계의 관찰이 불가능하면 **미확인**으로 기록하고, 실제 실패와 구분한다. [검증 계획](VALIDATION_2.0.ko.md)은 더 구체적인 조건·근거·한계를 정한다.

조건부 요구는 그 뜻대로 시험한다. 추가 위임이 필요하지 않은 업무에서 실행 대화 하나만 쓰는 것은 허용되지만, 통신이 한 번도 없었다면 “모든 통신이 계층을 거쳤다”는 문장만으로 **왕복 성공**을 주장할 수 없다. 왕복 능력은 실제 교환이 필요한 별도 과제로 확인한다. 사용자가 학습이나 가이드 사용을 멈춘 범위에서는 그 선택을 따르는 것이 올바른 동작이다. 동시에 기능 자체는 허용된 조건과 적합한 근거가 있는 별도 사례에서 시험해야 한다. 개인 가이드를 만들지 않은 한 번의 경험만으로 실패나 성공을 단정하지 않는다.

확인된 경로의 미지원과 다른 경로의 미확인은 다르며, 한 호스트의 제약만으로 다른 경로 전체를 불가능하다고 단정하지 않는다. 반대로 한 셀의 성공이나 미확인 상태를 전체 지원으로 바꾸지 않는다. 목표 앱·OS 범위의 축소는 사용자 결정이 필요하다. 제품의 실제 성공이나 특정인의 반응을 보장하는 충분조건은 이 계획에서 확립되지 않았다.

## 학습에서 확정한 것과 열린 것

확정한 방향은 개인별 학습, 실제 작업을 통한 적용과 조정, 일반적인 조정의 조용한 실행, 진행 중 관련 작업에의 적용 가능성, 학습 진행 상태의 추적이다. 에이전트 협업에서 생긴 수정이나 검토 경험도 각 사용자의 OpenSocrates 안에서 다뤄볼 학습 문제가 될 수 있다. 여기서 문제를 '이슈로 다룬다'는 것은 시스템 내부의 학습 대상으로 다룬다는 뜻이며 GitHub 이슈를 생성한다는 뜻이 아니다.

RL은 현재 지향하는 피드백 순환을 가리킨다. 보상 신호, 학습 단위, 가이드 표현과 채택·보류·폐기 기준은 명세와 실험이 필요하다. 특정 강화학습 알고리즘, 모델 가중치 갱신 또는 내부 token alignment의 개선을 이미 결정하거나 입증한 것으로 쓰지 않는다. 사용자의 수정이 없었다는 사실만으로 만족이나 성공을 확정하지 않는다.

조용한 학습을 매번 승인받는 경험으로 바꾸지 않는다. 한편 잘못된 학습을 알아보고 수정할 방법, 가이드의 관련 범위와 버전을 다루는 방법은 아래 열린 결정에서 구체화한다. 이 문서는 아직 채택하지 않은 제안을 사용자 확정 요구로 승격하지 않는다.

## 사용자가 겪는 세 가지 장면 — 기획 예시

아래 대화는 제품 동작을 설명하기 위한 가상 예시이며, 고정된 대화 대본이나 실제 앱 실행 기록이 아니다.

의뢰 맥락 없이 결과물 형식의 장단점만 묻는다면 그 질문에 상담으로 답한다. 그 질문 자체를 새 결과물 제작 의뢰나 특정 형식의 선택으로 간주하지 않는다. 이미 별도로 맡긴 업무나 상담에 필요한 허용된 준비까지 일괄 중단하라는 뜻은 아니다. 반대로 제작을 맡긴 뜻이 맥락상 분명하면 별도의 착수 승인을 매번 요구하지 않는다. 필요한 중요한 선택이 남아 있다면 그 부분을 구체적으로 상담하면서 이미 허용된 독립 업무는 진행한다.

### 1. 결과물 형식부터 상담이 필요한 경우

사용자가 “투자자한테 보여줄 이탈 자료 좀 정리해줘”라고 의뢰한다. 의뢰 세션은 이미 제공된 맥락을 살펴 필요한 자료와 접근 범위를 확인하고 대략적인 결과물의 그림을 설명한다. 예를 들어 “이탈 추이와 원인, 다음 선택을 살펴볼 수 있는 자료로 이해했어요. 편집해 주고받을 문서라면 Word가 편하고, 링크로 열어 볼 자료라면 HTML도 가능해요. 어떤 방식으로 쓰실 계획인가요?”라고 설명할 수 있다. 실제 공유 환경과 접근 권한에 따라 차이는 달라지며 어느 형식도 미리 밀어붙이지 않는다.

사용자가 Word를 선택하면 그 선택과 목적을 해당 업무의 결정으로 보존한다. 의뢰 세션은 적합한 가이드·관련 자료·허용 범위를 준비하고 실제 작업을 새 앱 세션에 맡긴다. 그래프가 필요하고 별도 위임이 유용하면 해당 작업도 OpenSocrates를 통해 다른 실제 세션에 맡긴다. 의뢰 세션은 내용·상태를 조율하고 완성된 파일의 확인 결과를 전달한다.

### 2. 숙련자가 이미 선택을 명확히 한 경우

사용자가 “기존 보고서에 최신 지표를 반영해 Word 세 쪽으로 고쳐줘”라고 요청하고, 필요한 파일·독자·목적과 허용 범위가 맥락에서 분명하다면 이미 정한 형식을 다시 고르게 하지 않는다. 사용자가 해당 파일의 수정을 맡긴 경우 덮어쓰기라는 이유만으로 반복 확인하지 않는다. 실행 세션이 자료와 허용된 파일 상태를 확인해 작업하고, 필요한 결과와 실질적으로 중요한 불확실성만 전달한다.

반면 같은 지표와 분량을 정했더라도, 독자가 투자를 **권유받는 문서**인지 찬반 근거를 보는 **판단 문서**인지에 따라 내용이 달라지고 기존 맥락으로 판단할 수 없다면 그 선택을 구체적으로 설명하고 물을 수 있다. ‘지표 중심’과 ‘결정 중심’은 양립 가능하므로 둘 중 하나를 고르라고 거짓 충돌을 만들지 않는다.

### 3. 실제 작업 도중 방향이 바뀐 경우

사용자가 실행 세션 A를 열어 “원인보다 다음 행동부터 보여줘”라고 직접 전송한다. A는 이미 받은 지시를 현재 업무에서 처리할 수 있다. OpenSocrates가 변경을 적법하게 관찰할 수 있다면 현재 업무의 선택을 갱신하고, 관련된 다른 세션 B에 필요한 내용을 계층을 통해 전달하며 가이드 후보도 검토할 수 있다. 계층이 직접 지시를 관찰하지 못한다면 그 내용을 안다고 가장하지 않는다. A가 변경을 보고한 경우에는 확인된 사용자 지시가 아닌 출처가 표시된 잠정 단서로 다룰 수 있다. A의 직접 수신과 실제 반영, 계층의 관찰, B로의 전달·수신은 각각 별개다. 관련 전달이 불가능하거나 그 효과를 볼 수 없다면 해당 부분을 대기·미확인으로 두고, 옛 결과를 새 결정이 반영된 결과로 소개하지 않는다. 이 수정이 모든 업무의 선호라고 단정하지 않는다.

예를 들어 나중에 다른 독자를 위한 유사한 문서를 맡기면, 이전 경험에서 유용한 개인 가이드 후보가 있더라도 새 목적·현재 지시와의 관련성을 다시 판단한다. 맞는 개인 가이드가 없으면 기본 48개 중 적합한 가이드를 고려하고, 어떤 가이드도 적합하지 않으면 억지로 적용하지 않는다. 사용자가 적용 이유를 물으면 확인 가능한 근거와 미확인을 설명하고 교정할 수 있도록 한다. 이전 수정을 모든 업무에 강제하거나 새 업무라는 이유만으로 무조건 배제하지 않는다.

학습은 별도 “배워” 지시를 요구하지 않는다. 실제 앱이 제공하는 관찰 경로, 실행 가능 시점, 보관 정책과 결과의 검증 수준은 표면별로 확인해야 한다. 사용자에게 보여 주는 질문과 보고의 양은 상황과 필요에 따라 판단하며, 위 예시의 대화 횟수를 보편 규칙으로 만들지 않는다.

## 데이터와 권한의 경계

현행 [AGENTS.md](../../AGENTS.md)는 텔레메트리, 자격증명 수집, 원문 프롬프트·대화 기록, 스크린샷 보관, 작업 공간 콘텐츠 보관과 숨겨진 추론 수집을 금지한다. [CONTRIBUTING.md](../../CONTRIBUTING.md)에도 관련 개인정보 제한이 있다. 이 계획은 그 정책을 변경하지 않는다.

사용자는 개인 가이드의 생성·보관·조용한 사용을 이미 요청했다. 현행 정책이 금지한 원문이나 작업 공간 콘텐츠를 복제하지 않는 가이드 문장을 일률적으로 금지하거나 별도 사용자 승인을 매번 요구하지 않는다. 저장 전 프로그램의 자동 점검을 설계하고 그 탐지 범위와 한계를 시험한다. 자동 점검만으로 모든 유출을 막았다고 보장하지 않으며 매번 사람의 승인 대기를 만들지 않는다. 현재 정책 안에서 먼저 설계할 수 있는 것은 범위가 정해진 작업·가이드 식별자, 버전, 상태, 허용된 출처 참조와 파일 상태 지문 같은 최소 기록이다. 개인 가이드는 원문 대화나 문서를 복사하는 저장소로 사용하지 않는다. 프로젝트 내용을 다른 앱에 전달하는 권한, 저장할 개인화 상태와 삭제 범위를 명세해야 한다.

구체적인 파일 차이를 비교하려면 사용 가능한 기존 버전 또는 동등한 변경 자료가 필요하다. OpenSocrates가 학습용으로 작업 공간 원본·스냅샷을 새로 보관해야 하는 제안은 현재 정책과 충돌할 수 있다. 해당 기능을 구현하기 전에 제품 소유자의 명시적 정책 결정과 별도 검토를 거친다. 그 결정 전에는 변경 감지와 상세 비교의 가능 범위를 구분하며, 전체 파일 감시나 원문 보관을 추가하지 않는다.

## 개발 과정에서 구체화할 설계 항목

| 결정 | 결정 책임 | 결정에 필요한 자료 |
| --- | --- | --- |
| 공통 생성 지침의 형식·버전과 생성 가이드의 표현 | 콘텐츠·학습 구현 담당 제안, 제품 소유자 검토 | 합성된 학습 사례, 범위가 다른 수정·반례, 재조립 결과 비교 |
| 가이드·맥락의 관련성 판단, 복합 적용과 기본 가이드 복귀 | 학습·맥락 담당 제안 | 초기·성숙 사용자, 여러 프로젝트, 상충하는 가이드 사례 |
| 각 앱 경험의 세션 생성·가이드 전달·상태 회수 경로 | 호스트 담당 | 앱/운영체제/버전/계정/권한별 실제 능력 확인. 한 셀의 결과를 다른 셀에 전용하지 않는다. |
| 진행 중 가이드 변경의 적용 시점·범위와 재개 의미 | 학습·조정 담당 제안 | 동시에 진행되는 다른 목적의 과업, 중단과 최신 맥락 변경 사례 |
| 학습 개선·퇴행·원인 귀속과 정정 수단 | 평가 담당 제안, 제품 소유자 검토 | 블라인드 산출물 평가, 잘못 일반화한 사례, 사용자가 설명 없이 수정한 경우 |
| 저장·권한·삭제·복구와 파일 비교에 필요한 정책 변경 | 구현·보안 담당 제안, 제품 소유자 명시 결정 | 최소 데이터 설계, 기존 정책과의 차이, 실제 호스트 권한 범위 |
| 기술 스택·DB·실행 수명·사용량 예산 | 구현 담당 제안 | 기기별 운영 비용과 지연 측정, 고장·복구 시험. 가볍고 빠르다는 목표를 수치로 검증한다. |

요구사항과 기술 선택을 구분한다. 사용자 중심 팀, 개인 가이드의 진화와 중개 레이어는 확정된 제품 방향이다. MoE·Git·RL의 비유만으로 특정 자료구조나 알고리즘의 필요충분성을 주장하지 않는다. 제품의 성공은 이 구성 요소의 존재만으로 성립하지 않으며, 실제 사용자 경험·품질·권한·연속성의 관찰 결과로 평가한다.
