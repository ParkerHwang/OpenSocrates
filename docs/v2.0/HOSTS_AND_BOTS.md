# Host integration and Bot research for OpenSocrates 2.0

Research snapshot: 2026-10-29. This document sets implementation and qualification targets; it does not claim OpenSocrates 2.0 is implemented, installed, or verified on any host. Vendor documentation is capability evidence, not evidence of this product's actual delivery or usefulness. Recheck host versions and linked contracts before implementation.

## Scope and integration contract

Cursor is a required new host. Preserve and requalify Codex, Claude Code, the Claude account skill, and Antigravity. Dot, Grok Bot, and Claude Duet require research and a distinct lightweight profile; their precise release claims depend on demonstrated access and host support. Desktop, CLI, cloud, account skill, workspace, user, team, and Bot surfaces are separate qualification cells. Do not extend a passing result from one cell to another.

Separate five outcomes in every cell: discoverable, installed/enabled, instruction delivered, canonical content read, and applied/useful. No source or agent's own report alone proves all five. Preserve a legitimate empty method selection, the user's explicit instructions and permissions, and ordinary task continuation if the integration is missing or fails. A lifecycle hook signals only the event documented by that host; it is not a guaranteed semantic task boundary.

## Cursor: required integration

### Evidence and implementation consequences

- Cursor [Plugins](https://cursor.com/docs/plugins) supports both portable Agent Plugins (skills and MCP) and the Cursor-specific package (rules, agents, commands, and hooks). A portable package alone does not establish that Cursor-specific hooks are configured. The documented Cursor plugin manifest and plugin-root conventions require their own adapter and validation.
- [Rules](https://cursor.com/docs/rules) include an always-applied option. A compact entry rule can be considered for local/project use, while [skills](https://cursor.com/docs/skills) are discovered and selected by the agent. A referenced file is not implicitly inlined. Verify actual delivery and agent use instead of claiming automatic application from a rule or installed skill.
- [Hooks](https://cursor.com/docs/hooks) document `beforeSubmitPrompt` as allowing or blocking submission, with a user-facing message; its documented response does not include model-facing additional context. `sessionStart` can add context, but is fire-and-forget and cannot gate session creation. `postToolUse` can add context after a tool result, `afterAgentResponse` observes an already completed message, and `stop` can request a follow-up. Do not rely on a submission hook to inject a prompt or on a post-response event as a pre-draft event. Do not collect `afterAgentThought` content or raw transcripts.
- Cursor's managed cloud agents load repository command hooks but lack local user-level hooks and `sessionStart`/`sessionEnd`; prompt-based hooks are not supported there. Self-hosted worker behavior has separate documented boundaries. Personal skills can be synced for user-started cloud agents, but not automation runs; project skills are a separate route. See [hooks](https://cursor.com/docs/hooks) and [skills](https://cursor.com/docs/skills).
- GitHub-imported **team** marketplaces can enable auto refresh with the Cursor GitHub App; running cloud agents retain their starting plugin version. That mechanism is not proof of automatic updates for individual installations. See [plugin update documentation](https://cursor.com/docs/plugins).
- Cursor supports independent background [subagents](https://cursor.com/docs/subagents), but their availability and parallelism do not establish quality or a speed win.

### Cursor implementation work and acceptance

1. Prototype a short always-applied entry with on-demand localized references and a Cursor-specific plugin adapter. Establish documented local/user and project ownership, disabled state, and rollback without replacing unrelated rules.
2. Map lifecycle opportunities separately: entry, decision during work, post-tool, compaction, and completion. A missing prompt injection or cloud session-start event requires a documented fallback, not a synthetic receipt.
3. In disposable local and separately authorized cloud test environments, submit synthetic ordinary prompts without naming OpenSocrates: one mechanical task, one ambiguous planning task, one changed-constraint continuation, and one reader-facing artifact. Record actual entry/selection/read/delivery evidence independently. Test Korean conversation with English or Japanese output.
4. Test explicit skill invocation, activation, rule/skill discovery, hook payload shape and failures, a tool-free task, compaction, new session, plugin disable, update, removal, and unrelated-settings preservation. Verify what happens when the user rejects a hook or the host cannot write to the intended scope.
5. Test local and cloud scopes independently, including cloud without user hooks, synced personal skills versus automation, and an in-flight agent after a plugin update. Capture a content-free event receipt only where supported; absence of a receipt is unknown, not a model-compliance diagnosis.
6. For each claimed OS/architecture, test clean first install by a normal user, disconnected network, upgrade, failed/partial upgrade, rollback and removal. Verify whether updating the OpenSocrates package, as opposed to Cursor itself or a marketplace index, is actually automatic. Record availability or an actionable manual fallback, not an unsupported automation guarantee.

## Codex

The published [hook contract](https://learn.chatgpt.com/docs/hooks) supports session, prompt submission, tool, compaction, subagent and completion events. `UserPromptSubmit` can add developer context. Asynchronous hooks provide supported output at a later safe point; they cannot govern the triggering operation, may finish out of order, and unfinished output is discarded when the session ends. Matching hooks require the host's trust and event-specific output schemas. Do not describe a `Stop` event as the instant before final writing or assume all host events are wired by an installed OpenSocrates version.

The [v1.5.3 release](https://github.com/ParkerHwang/OpenSocrates/releases/tag/v1.5.3) retains the existing package and compatibility boundaries. [Issue 124](https://github.com/ParkerHwang/OpenSocrates/issues/124) records one observed omitted application despite installed/approved hooks; the cause and frequency are unresolved. The 2.0 adapter must distinguish event execution, emitted context, method selection, full read, claimed application, and practical outcome. Synthetic ordinary prompts should cover a relevant judgment, mechanical bypass, empty selection, changed facts, compaction, and unavailable runtime. Test foreground/background paths, trust, update, and migration under separate local and cloud conditions.

## Claude Code and account-based Claude

[Claude Code hooks](https://code.claude.com/docs/en/hooks) expose prompt, session, tool, compaction, completion, and subagent events with event-specific contracts. The completion event can request continuation; it is not a universal prewriting trigger. A subagent stop can also come from host-internal agents, so do not treat every event as OpenSocrates' independent reviewer. Avoid reading raw prompts or transcripts for diagnostics unless specifically authorized; never capture hidden reasoning. Verify actual host consent and delivery in CLI and Desktop local Code separately.

Claude account skills are a separate content-based transport: the published [setup](https://github.com/ParkerHwang/OpenSocrates/blob/v1.5.3/README.ko.md) requires account-side upload and activation. Skill availability does not prove the host automatically selected it or ran native hooks. Probe a fresh account session, activation, relevant and mechanical prompts, complete reference reads, change of output language, and replacement/update while preserving existing user instructions. Claude Chat, Cowork and local Code are independent surfaces, as are their account/OS settings. Do not imply a local CLI install has updated an account-uploaded ZIP.

## Antigravity

The documented [rules](https://antigravity.google/docs/rules) and [skills](https://antigravity.google/docs/skills) support modular guidance. [Hooks](https://antigravity.google/docs/hooks) describe session start, tool events, model pre/post invocation, and stop for app, CLI, and IDE. Invocation hooks can inject steps, but a model invocation is not necessarily the final answer-writing phase. Their documented input supplies counters and common metadata, not an automatic guarantee of the complete user request. The documented post-tool output is an empty object; do not assume it accepts Cursor-style extra context. Avoid transcript access and prompt retention.

The v1.5.3 distribution's Antigravity path uses scoped rules and skills; any new hooks are 2.0 implementation proposals, not existing behavior. Test workspace and global scope individually, preserve non-owned settings, and observe actual guidance without calling it out in the prompt. Verify initial invocation, repeated model calls without duplicate injection, changed judgment, failure fallback, locale selection, stop behavior and update/remove. Test app, IDE, and CLI only when claimed; do not transfer an app observation to the other surfaces.

## Bot profile: capability research

| Host | Documented entry point | Required proof before a product claim |
| --- | --- | --- |
| ChatGPT Dot | [Dot guide](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot): an approved connected local computer can run local skills and create Work or Codex tasks. | Determine separately whether the Dot's direct cloud conversation discovers, invokes, installs, and updates the Bot profile; local delegated execution does not establish those capabilities. Test access revoked/offline and account/plan availability. |
| Grok Bot | [Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations): skills can be saved, discovered, and enabled for a Bot; private skills use a shared library. | Verify import of the actual OpenSocrates package, per-Bot enablement, automatic relevance-based activation, updates, permissions and repeatable runs. Do not substitute Grok Build CLI plugin compatibility for Grok Bot proof. |
| Claude Duet | [Duet guide](https://support.claude.com/en/articles/17631495-get-started-with-claude-duet): account skills/connectors are available and plugins are supported. | Verify the actual existing Claude account skill and proposed Bot profile, invocation, updates and privacy; the research preview is currently restricted to invited US Pro/Max users. No access means unavailable, not a pass. |

Grok Bot distinguishes desktop app updates from updates of its cloud computer; the latter can rebuild the computer and remove installed apps/packages while retaining files and logins. A skill or plugin update is a separate question. Test reinstatement and scope boundaries without inferring product persistence from app update behavior. See [settings](https://docs.x.ai/grok-bot/settings-and-notifications).

For each accessible Bot, evaluate brief conversation and substantial background work separately. The lightweight guidance must retain relevant evidence, stopping, and user-authority constraints. Compare no intervention, lightweight guidance, and full guidance using the same scripted, synthetic cases; record time to first response, task completion, quality, unwarranted follow-up, and actual context delivery. Test input/output language distinction, durable project memory versus host memory, app disconnect, new conversation, user-requested deletion, update, and inability to install or enable the profile. Never infer always-on coverage from one successful invocation. Unsupported or unobserved capabilities remain unknown and need a clear supported fallback.

## Cross-host release checks

Build a matrix containing host version, surface, OS/architecture, profile, scope, installation origin and version, consent/trust, activation, entry event, content delivery/read, task outcome, update/restart behavior, deletion, and evidence status. Use disposable profiles, synthetic data, and minimal receipts; do not record raw prompts, private transcripts, credentials or hidden reasoning. The v1.5.3 installed package inventory and existing settings are preserved; test new-install, upgrade, interrupted upgrade, retry, rollback and removal without assuming all hosts share an updater. Account-upload and local updates are separate. Establish native auto-update capability and boundaries for each claimed cell before reporting it as supported.
