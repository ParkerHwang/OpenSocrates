# OpenSocrates 2.0 validation and evaluation plan

Status: development plan, 2026-11-02. This document is not an execution result, support qualification, or evidence of improvement. It turns the [product requirements](VISION_2.0.md) and [system design](SYSTEM_2.0.md) into observable cases. [한국어](VALIDATION_2.0.ko.md)

## 1. Product under test and judgment criteria

The first scope is the OpenSocrates program and lightweight database on one user's computer, connected to the ChatGPT desktop app and Claude desktop app. Qualify macOS and Windows independently. Record ChatGPT Chat, Work and Codex, and Claude ordinary/unified chat, Cowork and desktop Code separately where their actual capabilities and boundaries differ. Do not treat Codex inside ChatGPT as a separate desktop product. Standalone CLI, web, mobile, Cursor, Grok Bot and synchronization across computers do not establish first-release support.

The conversation receiving the user's request performs consultation, preparation and coordination. Actual research, analysis, production and artifact integration occur in new, real app conversations. Every inter-agent request, question, response and handoff goes through the OpenSocrates layer, which delivers a suitable task prompt, context and reasoning guides to each task. Do not replace this execution path with direct model-provider API calls in the evaluation.

Define observable user outcomes before measuring effectiveness: intent understanding, artifact quality and usability, rework, unnecessary questions and user intervention, context switching, authority compliance, elapsed time and cost. The existence of a file structure or algorithm is not sufficient for a good user experience. Token alignment, MoE, RL and Git trees describe the concept or design hypotheses; do not claim to observe internal token changes or hidden reasoning.

### Host observations to distinguish first

In an authorized test environment for each app, OS and mode, examine these three independently with public synthetic material. Distinguish permissions required by the host during initial installation from confirmations required during ordinary work.

1. **New execution conversation:** Can the product actually open a new conversation, send the first request and retrieve the result through the layer? Observation establishes each completed step only; if any step fails, that automatic route remains incomplete. An open screen or prefilled composer is not completion.
2. **Recipient and authority:** Observe whether two conversations share connections or processes; whether the host supplies conversation identity and authority information the model cannot arbitrarily alter; and what happens after restart or misdelivery. A single observation of process separation or a matching identifier is not a guarantee of isolation or authentication. Without verified binding, hold only the affected sensitive delivery and attribution while independent work continues.
3. **In-flight exchange:** Observe whether an execution conversation can be informed of, retrieve and apply changed conditions and return its result, including user intervention and delay. Record delivery, reading, application and output separately; assess alternatives independently when a route is unsupported.

These are planned design probes, not results. Do not retry or bypass an action blocked by the operator tool's policy through another route. Even partial success does not establish support for all four combinations, security, output quality or the effect of personalization.

## 3. Preparation and data boundaries

Before running, freeze case version, synthetic stimuli, expected criteria, model/effort/tool access, app/OS versions, user authority, repetitions/order, timeouts, failure/censoring treatment and assessors. Reproducible tests that cannot retain actual inputs or user files use publishable synthetic materials and version identities.

Conduct real-use evaluation on tasks whose scope the user understands and authorizes. Collect minimal outcome ratings and burden measures during work the user would otherwise do; do not make explaining every edit or maintaining a lengthy manual diary a prerequisite for using the product. Separate optional research interviews or ratings from normal operation. If no rating is obtained, the outcome remains unassessed.

Follow the current policies in [AGENTS.md](../../AGENTS.md) and [CONTRIBUTING.md](../../CONTRIBUTING.md). Do not collect or retain raw prompts/transcripts, copies of workspace content, credentials, screenshots or hidden reasoning, or add telemetry. Leave user-owned final artifacts at their intended delivery location rather than copying them into the evaluation store. Retain publishable synthetic materials, content-free states/versions/outcome measures and permitted references. Check that guides and summaries do not reproduce private source text or secrets.

This document does not authorize always retaining prior file contents or private actual prompts to reproduce a test. First obtain an explicit, separately reviewed policy decision, or change the test to use already permitted original-version references and synthetic materials. Missing data does not justify inventing the cause or intention behind a change.

## 4. Comparative evaluation design

| Condition | Question |
| --- | --- |
| A: same host without OpenSocrates | What outcomes and burden occur in ordinary app use? |
| B: exactly pinned v1.5.3 | What differs from the released 48-guide delivery and selection path? |
| C: 2.0 with baseline guides and program integration | What does session separation, communication and context delivery contribute? |
| D: 2.0 with personal-guide selection/recomposition | Do relevant personal guides add benefit? |
| E: 2.0 generating/adapting guides from experience | Does the learning process improve subsequent work beyond a prewritten personal guide? |

Do not require every comparison at once. Choose controls needed for the claim. To test delegation, compare one execution conversation with dynamic delegation through OpenSocrates using equivalent materials, tools and budgets. To test guides, keep the program and execution conditions fixed while varying relevant guidance. A factual-memory-only condition can help distinguish personal fact recall from reasoning guidance. Identify the deliberately changed factor and any factors that changed with it.

For v1.5.3, use the exact distribution linked in the [release baseline inventory](RELEASE_BASELINE_1.5.3.md) and observe its behavior on the host being compared. A comparison against B on one host needs B evidence on that host. Missing baseline measurements for another app or OS do not block a supported static comparison, feature observation or independent comparison elsewhere. If v1.5.3 does not support a surface, mark B not applicable and use appropriate controls such as A.

Separate experiences used to generate guides from evaluation tasks. Include subsequent work in the same project, similar work in another project, unrelated work, and later work after preferences or facts change. Record user learning, fatigue and order effects; isolate each condition's personal database and guide state. Do not leak current state between conditions and call them independent.

Match model, tools, permissions and available capabilities where possible. If cross-app conditions cannot be matched, report the differences rather than attributing the outcome to the product or model alone. Include every attempt, retry, timeout, failure, tie and interruption. Report sample size and repetition unit; multiple ratings of one output are not multiple independent tasks.

### Test design to isolate the added contribution of personal guides

This is a pre-execution experiment design, not a result. In a synthetic scenario a user requests a Word analysis for an external decision-maker and, during work, changes it to lead with next actions rather than causes. Separate the experience from which a candidate is generated from later evaluation tasks. Include a similar decision document, an application requiring a prescribed process order, an unrelated team retrospective, and work after a preference change. Include distinct cases where the signal belongs to one investor versus a general user preference. All content is public synthetic material.

- Under the same host, model, tools, authority and budget, compare **baseline guides**, a **fact note** containing the same signal, and a **personal guide** generated from that signal. Include cases where baseline guidance or the fact note is inappropriate. Hold sessions, program and context constant apart from the factor being compared. Where appropriate, compare the unaugmented app and host-specific v1.5.3 separately.
- Native host memory may reinforce or leak an out-of-scope preference. Where supported, inspect native-memory state and condition isolation and compare memory enabled and disabled separately. If it cannot be controlled or observed, record it as an unknown or confound. Do not assume all surfaces can turn it off.
- Separate experience-generating tasks from evaluation tasks and prerecord condition order, model/app versions, repetition units and rating criteria. Alternating conditions in a shared user conversation where memory carries over does not constitute an independent comparison. Distinguish synthetic tests from consenting real-work evaluation.
- Evaluate accuracy and fitness for purpose/format, what the intake session asks, what decision a delegated chart supports, unnecessary corrections and missed important confirmation, negative transfer to unrelated work, recovery after preference change, waiting and cost. Different questions or delegated specifications are observations, not proof of quality. Model self-report does not prove quality.
- Where feasible, separate blinded assessment from the user's judgment and preserve disagreement, failures, ties and unrated outcomes. Explain unavailable formats or hosts. Do not create evaluation copies of actual workspace contents or transcripts prohibited by policy.

Equivalent effects from a fact note and a personal guide mean that the guide's additional contribution is not established **for that case**. This does not automatically invalidate communication, file management or other independent features. Conversely, one good result does not establish improvement for other users or tasks.

The earlier [two-task synthetic guide example](SYSTEM_2.0.md) can be evaluated with separately prepared follow-up tasks as below. This is a **test plan**, not an evaluation result for the models' meeting responses or 2.0. Prespecify synthetic evaluation tasks distinct from the ordering and audit experience used for guide generation. Under the same baseline guide, materials, host and model conditions, compare baseline only, baseline plus a factual note summarizing the same experiences, and baseline plus personal guidance generated from them. Inspect differences in informational content and scope rather than assuming the note and guide are perfectly equivalent. Provide each evaluation task's current user instruction identically to all conditions. Treating the same instruction as current in one arm and only as a past note in another is not a comparison of personal-guide wording alone.

| Follow-up task | What to assess |
| --- | --- |
| Related order: options and evidence are sufficient | Does the response make a purpose-appropriate decision within current instructions while considering decision-changing assumptions at the needed depth? |
| Urgent order: options and figures are absent | Does it avoid inventing an option, first seek already available materials, and address decision-relevant gaps briefly and specifically? |
| Audit needing the conclusion first, or a different review where procedure matters | Does it follow the current user and reader's purpose rather than forcing an order from the task name? |
| Another project and a third party's correction | Does it reassess guide relevance without attributing a third party's choice to the original user? |

Where feasible, preregister task and condition assignment and assessment criteria and blind raters to condition. Record whether condition state and host memory were actually isolated. If memory is uncontrolled, report observed condition outcomes without attributing their difference solely to guide wording. A failure to detect a difference in a small sample is not evidence of equivalence.

Design a separate falsification of self-reinforcement. In public synthetic experience, prespecify the user's actual task instruction, customer demand, changed preference and author, and prepare corrections, partial corrections, silence and repeated relay of one signal both when the original guide fits and when it does not. Compare learning policies from the same initial state, distinguishing guide delivery from observability of actual reading/use and from host-memory state. Include related, unrelated and changed-preference follow-up tasks. Using permitted material, evaluators separately judge current-task compliance, false generalization or duplicated reinforcement, missed useful adaptation, negative transfer and user burden. Several ratings of one condition are not several independent tasks. Report missing outcomes, interruptions, unavailable assessments and inability to control host memory as such. Measure the cost of discarding useful corrections too, not only apparent independent support. This experiment does not instruct the product to arbitrarily withhold a real user's valid instruction or an applicable guide for evaluation.

[Research on recommender-system feedback loops](https://onlinelibrary.wiley.com/doi/10.1002/aaai.12055) discusses how presented choices can influence later user ratings and make preference data unrepresentative. It does not establish this product's effects; it motivates checking exposure and confounders when interpreting reactions to 2.0's already-presented outputs. When host state or observations are insufficient, causal attribution remains unknown. Where possible, assign synthetic cases and condition order in advance and use paired comparisons with equivalent tasks and budgets. Report the unit of comparison and uncertainty; failure to detect a difference in a small sample does not establish equivalent effects.

**Unsupported figures observed in this meeting:** The chair requested a synthetic ordering example without supplying order quantities, sales history or options and asked the model not to invent numbers. Claude's initial proposal introduced an order quantity, sales history and outcome not supplied in that scenario and recommended a choice; it withdrew that answer after the chair's challenge. This is an observation about one response in this meeting, not an independent comparison, evidence of 2.0 behavior or a general model error rate. `GUIDE-12` is a plan to assess cases where necessary evidence is missing.

## 6. Quality, learning and burden measures

Where possible, assessors judge the artifact before knowing its condition. Evaluate numerical/factual/logical correctness, intent and audience fit, usability in the requested format, necessary edits and follow-up instructions. Include opening/editing files and checking chart units, axes and agreement with underlying data. Fluent explanation does not excuse an incorrect result. Distinguish user ratings from independent domain assessment and preserve disagreement/ties.

Evaluate learning through subsequent-task correctness and suitability, inappropriate generalization, regressions in previously successful work and incorrect transfer to unrelated projects, not only fewer edits to past tasks. Silence, non-use and no edits are not equivalent to satisfaction. Record signal confidence, unresolved causes and intervening model/tool/guide changes; observation alone does not establish one guide's causal contribution.

User burden includes repeated explanations/corrections, necessary consultation versus unnecessary questions, missed consequential decisions and the count/time of manual routing between agents. Ordinary adaptation should be quiet, while the user can request inspection and correction of current applicability and permitted change grounds.

Measure first response, preparation needed for user decisions, usable completion time, guide retrieval/assembly, communication/UI/model waiting, background learning and retry/recovery separately. Include competition between foreground work and background resources. Distinguish host-reported actual usage from estimates; unavailable numbers remain unknown. Do not double-count overlapping wall time or add cached tokens to total input twice.

Measure the lightweight and responsive requirement separately. Under matched device and power conditions, compare against an uninstalled baseline: idle and active CPU and memory, disk and index size, distributions of startup/retrieval/learning-resume delay, foreground delay caused by background work, and battery impact. Include small and large guide collections, concurrent updates, app exit and sleep. Separate model wait from local program time and leave unobservable usage unknown. These are consented development-environment measurements, not an instruction to add always-on product telemetry.

The product owner and evaluation owner set quality/performance targets from baseline, intended use and tolerable failure/user burden before observing candidate outcomes. Do not use unsupported percentages, counts or times as universal pass thresholds. Authority violations, secret leakage or overriding user decisions reopen the affected deployment decision and are not cancelled by a high mean score. A failed comparison does not by itself prove the entire product impossible or stop unrelated independent work without diagnosing its cause.

## 8. First demonstration and falsification experiments from the meeting

This is a **planning scenario**, not a completed demo or evaluation. A fictional user loosely requests investor-facing churn analysis and chooses Word. The intake conversation settles purpose, format and decisions. OpenSocrates prepares applicable initial guides and context and delivers them to a real execution conversation. If that conversation needs a chart, it delegates to another real session through the layer. The user changes the report to lead with the decision and next actions; a scoped, uncertain candidate guide is quietly generated and the system attempts suitable in-flight application. A later similar task and an unrelated task test appropriate transfer. Do not fabricate inputs or results as a successful run.

These experiments can begin independently before implementation is complete:

1. **Interruption and lost input:** Interrupt interpretation with synthetic input and a host double. Test readable/unreadable sources and interruption before/after delivery separately; distinguish recovery, `input_unavailable`, `payload_unrecoverable`, `effect_unknown` and deduplication. A host double cannot establish actual app reread capability.
2. **One real host cell round trip:** In one available app/OS cell, observe creation of a new conversation, task identification, guide/context delivery and layer-mediated results using public synthetic material. Record unavailable and unknown stages accurately. One successful cell does not establish support for all four.
3. **Contribution of personalization:** Where feasible, compare baseline guidance, a same-information fact memo and personal guidance under matched conditions. Use held-out later work, unrelated work and changed preferences. Separate blinded and actual-user ratings where possible; preserve failures, ties, costs and delays. Failure to beat a fact memo does not automatically disprove the value of team communication or context management.
4. **Context-resumption cues:** Compare public synthetic tasks with no added cue, a cue automatically prepared from permitted evidence, and deliberately stale or conflicting cues. Match access to common sources and model/tool conditions as far as possible, while stating that the additional cue content differs by condition. Record whether host memory is controllable and account for model nondeterminism. Balance participant/task assignment and order and record learning and order effects. Where feasible blind outcome evaluators to condition and design actual-user evaluation separately. Assess task completion in the intended direction and result quality, misread historical facts or authority, wrong-file edits, missed necessary confirmations and unnecessary questions, user correction and burden, total time and cost. Time to first click alone does not establish successful resumption. Report failures, unknowns and unsupported conditions; do not retain real users' raw transcripts, screenshots or workspace contents or force note-taking for evaluation. This is an unexecuted plan and assumes no particular cue is beneficial.

Distinguish the effect of **showing a cue to a person** from the effect of **delivering it to an execution session**. An agent-only run does not establish human resumption experience or burden. In scenarios requiring session coordination, record whether actual sessions can be connected through the layer separately from the effect of this comparison. No added cue does not mean removing the current instruction or all permitted context.

Model self-report, delivery of a guide ID and the presence of a file are different observations. None alone proves changed reasoning or improved quality. The aim is an experience where a user can explain less and still obtain useful results and retain control, not merely an impressive demo; do not claim that outcome before evaluation.
