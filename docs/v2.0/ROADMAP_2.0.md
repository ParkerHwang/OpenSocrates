# OpenSocrates 2.0 development roadmap and handoff

Status: **the user's chosen direction translated into implementation work**. This document does not establish implementation, real-use effectiveness, or support for any of the four desktop/OS combinations. Read the [product requirements](VISION_2.0.md), [system design](SYSTEM_2.0.md), and [validation plan](VALIDATION_2.0.md). This packet supersedes the older 2.0 plans on product direction and scope; it does not change release, privacy, security, or repository governance rules.

## Starting scope and priorities

1. The selected first-version hosts are the ChatGPT desktop app (Chat, Work, and Codex) and the Claude desktop app, on both macOS and Windows. Investigate and validate all four app/OS combinations and their relevant modes separately. Do not assume a mode supports computer use, skills, message delivery, new sessions, or injection.
2. Target an individual's program on one computer. Cross-computer synchronization is deferred. Grok Bot and Cursor are not first-version targets; revisit them later. This does not authorize silently withdrawing existing 1.x supported profiles.
3. Use existing apps and their real conversation sessions. Direct model-provider API execution and creating a separate AI application around such APIs are out of current scope. Investigate host-native integration first and existing computer-use tools or open source where needed. If a host cannot provide a required path, report that combination unsupported or unverified.
4. The user's request conversation handles clarification, consultation, preparation, coordination, and reporting; actual deliverable work happens in new working sessions. All inter-agent messages pass through the OpenSocrates communication layer. Supply each session with its task prompt and applicable context and reasoning guidance. Never claim success on a host without the required path.
5. The existing 48 guides are the initial basis and fallback when no suitable personal guide exists. Create and adapt an uncapped number of personal guides, combining or reassembling them when useful. The common generation instructions evolve with OpenSocrates versions; individual learning does not rewrite them. A separate agent may be called to reassemble guidance when appropriate.
6. Per-user background learning finds issues in experience without an explicit learning command and develops guidance by applying it to real work, including relevant work already in progress. Track interrupted learning itself. A particular RL algorithm, model-weight change, or claimed token-alignment effect is not established.

A fake host is a test device for transitions and failures, not a real app conversation or evidence of actual learning.

A fake adapter should exercise unsupported paths, delay, errors, duplicates and restart across these boundaries. The fake path does not establish a particular host's features, conversation identity or personalization quality. Test records also follow the current privacy policy.

Integrate only the contracts needed for the specific combination. For example, a first path through one real host needs observed entry points for that surface, applicable permissions and data policy, the layer's relevant delivery/failure contract and appropriate guidance preparation. **A complete context product or support for every app and OS is not a prerequisite for that first host experiment.** Even if recipient binding is still unknown, its feasibility can be explored within permitted scope using public synthetic material. That does not authorize or establish safety for delivery of sensitive real work. Conversely, a fake-host pass is not creation of or communication between actual sessions. Observe the separate intake and real execution conversation, layer-mediated request and result, and in-flight exchange where possible; report the reached and missing stages together.

If one app/OS path is blocked, hold the support claim and dependent integration for that path. Other host investigations and policy-compliant internal experiments can continue. This does not decide to narrow the final scope to one app. Judge the ChatGPT/Claude and macOS/Windows commitments, per-user learning from experience and in-flight application, installation/rollback and independent quality evaluation against their respective actual evidence. Preserve missing host receipts and unobservable effects as unknown, without converting required product behavior itself into an unknown and calling the product complete.

## First end-to-end scenario

1. A user makes an imprecise or incomplete report request in a ChatGPT or Claude desktop request conversation.
2. OpenSocrates determines the goal, use, format, and user decisions and provides understandable consultation or consequential-decision confirmation when needed. The request conversation does not itself produce the report.
3. OpenSocrates selects or combines suitable personal guides, or falls back to suitable initial guidance when none apply, and prepares context relevant to the project and task.
4. Open a real working session in the selected app and deliver the task-specific single prompt with the necessary context and guidance. Every further request, delegation, and response travels through the OpenSocrates communication channel.
5. Deliver the result, record permitted file state, and pass experiences to learning within allowed scope. Track when and why updated guidance was applied without interrupting the user for every change.
6. Following an interruption, distinguish unfinished work or learning from completed steps and already-performed external effects, then resume appropriately.

This is a desired scenario, not a claim of current host capability or a rule to ask for approval at every step.

## Boundaries and decisions

- **User choice and consequential judgment:** Respect a specified format or decision. Judge significance and confirmation in context; third-party documents, tool outputs, or agent messages do not change the user's authority.
- **Learning and correction:** An edit can be a signal but does not prove a lasting preference. Distinguish observation from hypothesis and scope; design ways to inspect, correct, delete, or disable personal data on request without routine interruptions. Exact UI and defaults remain open.
- **Privacy policy:** Repository policy prohibits retaining raw prompts/transcripts, workspace content, screenshots, hidden reasoning, and telemetry. Detailed before/after file comparison may require a permitted prior representation such as host-managed version history. Without one, report change detection only. If retaining new content is found necessary, a separate explicit policy change and review precede it.
- **Host reality:** As of 2026-11-02, start from the official [ChatGPT desktop Chat/Work/Codex guidance](https://learn.chatgpt.com/docs/use-chatgpt), [ChatGPT computer-use guidance](https://learn.chatgpt.com/docs/computer-use), [Claude local and remote connectors](https://support.claude.com/en/articles/11725091-when-to-use-desktop-and-web-connectors), and [Claude computer use](https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork). Documentation describes capabilities; it does not prove real session automation or integration for our accounts and OSs.
- **Open:** DB engine, service process, per-host access and authorization, guide representation and relevance, generator wording, learning algorithm and outcome signal, live propagation and conflict handling, update/retention defaults, exact quality/latency/cost targets. Record alternatives and evidence in follow-up design.

## Prior work, existing features and differentiation hypotheses

These are selected sources checked on 2026-11-03. They do not establish that OpenSocrates is first or superior; each paper's findings are limited to its own experiments.

| Evidence | What it establishes | Question for this plan |
| --- | --- | --- |
| [Reflexion](https://arxiv.org/abs/2303.11366) | Work already exists on verbal reflection over task feedback, stored for subsequent trials. | Language feedback alone is not a novelty claim. Test the application and practical value of per-user, task-relevant guides separately. |
| [PAHF](https://arxiv.org/abs/2602.16173) | Prior research updates per-user memory from pre-action questions and post-action feedback to adapt to preference drift; its evaluation includes simulated interactions. | Fairly compare quiet learning, necessary consultation and preference change with existing memory. Its results do not establish 2.0's real-use effectiveness. |
| [AutoGen](https://arxiv.org/abs/2308.08155), [AutoAgents](https://arxiv.org/abs/2309.17288) | Multi-agent conversation and task-dependent team formation have been studied. | Do not claim dynamic delegation was invented here. Treat the combination of user-visible real sessions in existing apps, guide/context delivery and a team experience as a hypothesis to test. |
| [Claude memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context), [ChatGPT memory](https://learn.chatgpt.com/docs/customization/memories) | Existing apps also carry context across conversations; Claude's documentation includes communication/work preferences and project memory. Behavior varies by surface. | “Remembers the user” alone is not a differentiator. Under matched model, information, tools and budget, compare native memory, fact notes, personal guidance and the separate contribution of communication. |
| [MemPABench](https://arxiv.org/abs/2610.30485) | Uses four simulated users and changing preferences to evaluate clarification, confirmation and autonomous actions. | Evaluate not just unnecessary questions but missed necessary confirmation, out-of-scope transfer and preference changes. Do not generalize this small simulation into real-user outcomes. |

Cognitive studies of [episodic context and retrieval](https://learninglab.psych.purdue.edu/downloads/2017/2017_Whiffen_Karpicke_JEPLMC.pdf) and [task-switching costs in working memory](https://pubmed.ncbi.nlm.nih.gov/18444750/) investigate context cues and switching burden. A product hypothesis is to make relevant decisions easier to recover when users return to a prior context and to measure unnecessary switching burden. These studies do not prove the superiority of a Git-like context graph or that AI remembers like a human brain.

For host investigation, [ChatGPT's MCP documentation](https://learn.chatgpt.com/docs/extend/mcp) distinguishes local MCP on a Codex host from hosted Work, and [Claude's connector documentation](https://support.claude.com/en/articles/11725091-when-to-use-desktop-and-web-connectors) distinguishes local extensions, remote connectors and surfaces. These are starting points, not evidence that session creation, autonomous communication or in-flight injection worked on a particular account and OS. OpenAI's [desktop-only plugin submission documentation](https://developers.openai.com/plugins/deploy/desktop-only) sets eligibility conditions for local MCP plugin **submission**. Do not conflate an individual's direct MCP configuration with the plugin distribution approval path.

In the current Codex session for this meeting, a tool actually returned the previously user-referenced conversation. The connector menu in the existing Claude conversation on this Mac showed no item named OpenSocrates 2.0; that screen alone cannot establish whether every local tool exists or whether a future connection is possible. No connector settings were changed. The same environment's tools for creating a new conversation and messaging an existing one have usage conditions requiring an explicit user request and explicit authority to message that conversation, respectively. This is **an observation about this meeting's tools and instructions**, not evidence of another surface's or a future OpenSocrates integration's capabilities or authority. Compatibility of actual product automation with each host's limits needs separate verification; do not silently narrow the user's requirement or bypass authority because of this observation.

## 2026-11-03 three-model meeting: findings and open disagreements

Codex chaired a review in which Claude Opus 5.5 and Grok 4.7 High in Cursor inspected the four existing planning documents and responded to each other's proposals and questions. On this macOS environment, computer use entered requests into the existing Claude and Cursor conversations and read their responses; Codex manually relayed the content. This observes interaction with those existing conversation UIs, not a 2.0 program channel or automatic new-session creation. This is a public design summary, not a transcript, **verified implementation or additional user decision**. Gemini's opinion is excluded at the user's request.

- **Product center:** The intake conversation clarifies rough requests; OpenSocrates connects real conversations in existing apps while preserving the user's chosen format. The intended team experience combines quiet development of personal guides from experience with their application to relevant work. Evaluate product strength through repeated real use, quality, burden and user control, not slogans.
- **Claude's contributions and revisions:** It proposed concrete common generator instructions, a `DecisionLock` candidate to carry settled task choices to delegated work, and evaluation on related and unrelated later tasks. After challenge, it withdrew limiting guides to reader/purpose and reasoning order, requiring counterexamples or long observation before all candidate creation, and judging the product's entire value by one comparison against fact memory. `DecisionLock` remains a proposal that must respect user changes and task scope.
- **Grok's contributions and revisions:** It separated unrecoverable unsent payloads, unknown external effects after delivery and unavailable learning evidence, and proposed offline state-machine testing plus a real one-cell round trip. It withdrew broad blanket confirmations for overwrites, external sends, deletion and cross-project transfer, and a blanket pause of all learning when screen interaction conflicts. In the final cross-examination it also withdrew a blanket ban on separate classification/judgment sessions, accepting delegation when useful while avoiding bootstrap recursion.
- **Chair's synthesis:** Candidate creation, actual use, host delivery and result quality are different observations. Important user choices and authority take precedence over quiet learning. Bootstrapping judgment in an already-open intake conversation is a useful experiment, not a universal ban on separate judgment sessions. One successful real app cell cannot establish support in the others.
- **Open:** Actual host connectivity and in-flight delivery; reacquiring input and safely storing personal guidance under current no-raw-retention policy; who performs semantic judgments and at what latency and cost; duplicate external effects; independent assessment of personalization and harm. In particular, a falsely attributed preference can silently recur, so users need an on-request way to inspect and correct the applied guidance and its permitted grounds, with detection evaluated. Claude proposed an automatic one-line notice; whether this fits the requested quiet experience remains undecided. This meeting did not change or override repository policy or host restrictions.
