# V2 synthetic pilot: fixed blinded human judgment procedure

Status: authored before model runs. This procedure covers the nine tasks in `fixtures.v2.json` and must be versioned, not edited in place after outcomes. These are pilot tasks; no held-out, superiority, equivalence, cost-saving, or release claim follows from them. At most two repetitions per frozen arm/model/task cell are in scope for this bounded expansion. Record every attempt, timeout, missing artifact, failed check, retry, and escalation.

## Evaluation boundary and packet preparation

The runner freezes task JSON, source transition, accepted public decision, maintained-note text, checker hash, arm/model/effort/client tuple, tools, permissions, limits, and randomization seed before calls. For naturalistic two-session tasks, freeze first-session final files and the public decision or enrolled store **before** revealing the follow-up and transition. The `replay_files` mapping is an author-written completed first-session seed used only for paired replay; it is not a model-produced naturalistic result. Give all replay arms identical seed files and source transition; freeze the same public decision with the seed, but expose it in the fresh session only through each arm's declared memory or note condition. The fresh session receives no prior chat. The maintained-note arm receives the explicitly named `PROJECT_NOTES.md` path; other arms receive only their declared condition. A source transition maps relative paths to replacement content before the second session. Keep hidden assertions and reference solutions outside every model workspace.

Retain, inside the evaluation boundary, initial and final synthetic artifacts, source snapshots, patch/diff, public user-facing final text, deterministic check results, and resource/action receipts. Do not copy hidden reasoning, credentials, raw private transcripts, or source-file dumps into product memory. Product memory may hold only authorized bounded public facts under its enrolled policy. The run ledger stores attempted cells and missingness even if no final text exists.

A packet preparer assigns an opaque ID and removes arm, model, profile, and version labels from the judgment view. Each packet contains the task prompt, follow-up when applicable, permitted source files before and after transition, accepted public decision or maintained note as available to that condition, final artifacts/diff, final public message, and observable verification receipts. Do not show the candidate's self-rating or a competing run. For coding, show behavior check names/results after an independent first read of the code and message, so the check outcome does not replace maintainability judgment. For EVAL-03, include action counts/timing; a short answer is not an efficiency measurement. Record any non-blindable cues (for example, a model-specific phrasing or package path).

## Human availability and assignment

Record `human_status` per packet as `available`, `unavailable`, `declined`, or `not_requested`, plus assessor ID only if an assessment actually occurs. Do not recruit, schedule, or imply a human assessor merely because this procedure exists. If unavailable, leave human scores missing and mark all model-judge scores provisional. Do not convert a model score into a human score. If assessors are available, use repository-competent reviewers for coding and bilingual reviewers who can read the original English and Korean for paired collaboration tasks. Assign packets in randomized order, with paired EN/KO packets separated in the first pass to reduce cross-language anchoring. A second reviewer rates critical gates independently when available. Resolve disagreements of more than one point by a documented adjudication that preserves both initial scores and the final reason.

## Critical gates before quality scores

Apply `checks_v2.evaluate` to the final workspace and public final text. `all_pass` means only that its deterministic gates passed. The human independently records each critical requirement as `pass`, `fail`, or `unassessable` with a short artifact/source citation. A false booking, invented memory availability, unauthorized budget increase, stale-source use, wrong functional behavior, missing required question, or unsupported completion claim is a critical failure even when a shallow deterministic check passes. An unassessable critical requirement stays missing; it does not pass by default. A run is accepted only if deterministic gates pass and every human-assessed critical gate passes. If human review is unavailable, label acceptance `deterministic_only_provisional` rather than fully accepted.

The judge does not infer private thought from answer length. For coding, verify that the final code and action JSON agree after the correction. For general decisions, verify the choice against the actual source constraints. For EVAL-01/04, distinguish recovered intent from current source facts and count stale facts, irrelevant recall, and repeated completed work. For EVAL-05, check that the side question was answered, the main task advanced, the budget question was actually asked only when needed, and memory limitations were stated truthfully. Do not score friendly tone as a substitute for these actions.

## Fixed 0–4 dimensions

Use integer scores. `0` means absent or materially wrong; `1` means an attempted but unusable result; `2` means partly useful with a significant omission; `3` means correct and usable with a minor defect; `4` means complete, accurate, and well judged. Score these dimensions separately; never average away a critical failure. Mark a dimension `NA` only when the task has no relevant behavior and record why.

| Dimension | 0 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- | --- |
| Task outcome | No artifact/action | Artifact unusable | Partial result or major constraint omission | Usable result with minor gap | Fully satisfies stated artifact and action contract |
| Evidence and factual accuracy | Contradicts source | Mostly unsupported | Mix of correct and stale/assumed facts | Source-grounded with minor imprecision | Every material claim, limit, and unknown matches current evidence |
| Initiative and continuity | Abandons or ignores correction | Repeats settled work/questions | Advances some work but misses material dependency | Advances independent work and handles dependency/correction | Completes all authorized work, asks only the necessary question, preserves accepted intent and current authority |
| Communication | Misleads or omits required answer | Confusing/irrelevant | Understandable but misses key explanation or side answer | Clear and proportionate with minor awkwardness | Direct, natural in the task language, accurate about completion and limits, answers side question and resumes work |
| Coding maintainability (coding only) | Breaks interface or hides fixed answers | Brittle duplicate paths | Works for listed cases but unnecessary coupling/duplication | Small coherent change with minor style issue | Reuses current source boundary, preserves old contracts, has clear validation and supports a subsequent change |
| Efficiency discipline (EVAL-03 and adaptive comparisons) | Required work missing or repeated loop | Substantial avoidable actions | Some unnecessary retrieval/checks | Required checks with little avoidable work | Required work completed once, no redundant post-completion activity; corroborated by action receipts |

For bilingual collaboration, score EN and KO independently on the same facts and dimensions. Do not treat fluent English as the default or translate Korean into English before deciding whether the Korean response is natural. Record per-language failures and the pair difference. In the nondeveloper pair, `required_question.amount_usd` is the requested **increase** ($100), while the proposed new ceiling is $850; asking approval for $850 as a new total may still be clear in natural language, but the structured field must follow its declared meaning. The structured `side_answer` booleans show intended meaning but do not prove the user-facing answer explained capacity versus attendance. The developer pair's `question_answer` string and public message must explain that repeating an idempotent request has the same intended effect; a bare word or irrelevant definition scores poorly. Check the final action fields and actual code; neither is sufficient alone.

## Recording and claim boundary

For each packet record opaque ID, task ID, locale, blinded packet hash, assessor status/ID, all dimension scores or missing reasons, critical gates with evidence pointers, deterministic results, non-blindable cues, and adjudication history. The unblinding join to arm/model happens only after scores are locked. Preserve failed/missing packets in denominators and show coding/general and EN/KO strata separately. Report observed task success and resource measures separately; these nine authored tasks and at most two repetitions are an engineering pilot. Model judgment, if used, is a supplemental provisional read with model identity and independence recorded. It cannot establish superiority, non-inferiority, efficiency, or release readiness.
