## Native and external boundaries

C and D use the same source `Coordinator`, schemas, adapter, check order,
failure and repair machinery. C substitutes only complete generic role/domain
guide text at the runtime-bound guide provider in its own process. D uses the
unaltered source guidance. The source guide/schema bytes must match the
qualified D archive before calls. The native response's `client_sha256` names
the evaluation shim; the frozen record separately names and hashes the actual
bundled Codex executable.

The exact pinned client is `codex-cli 0.158.0-alpha.2`. Its legacy role flag
`--sandbox read-only` permits unrelated reads. A whole-process outer
`sandbox-exec` breaks the client's nested native sandbox with exit 71, even
under an allow-all outer profile. The versioned evaluation shim translates
the role's legacy flag and native check profile into a Codex named profile
extending `:read-only`. Its filesystem profile denies host roots and permits
only the current role or check working directory. The real client and its
native Seatbelt enforcement stay in use. This is a read-scope intervention
applied identically to all arms and must be verified by an actual synthetic
role-tool canary before the outcome matrix. A failed or missing canary holds
the dependent comparisons.

Go/TypeScript compilation, SQLite writes, HTTP/browser execution and
performance run only after candidate locking, on disposable copies. A trusted
verifier may read private expected results, but every candidate Go, TypeScript
and Chromium child runs under a separate strict policy. The policy denies
private fixture, sibling, previous evidence and host-memory reads, permits
writes only in its disposable run, and permits outbound loopback only. Native
`gofmt`/static checks remain read-only and cannot stand in for these external
obligations. Any sandbox-induced server transport failure is recorded as
`unassessable` and leaves integration pending; it is excluded from model-defect
counts.
