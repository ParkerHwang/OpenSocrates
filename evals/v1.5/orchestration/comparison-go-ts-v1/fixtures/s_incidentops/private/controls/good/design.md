# IncidentOps design control

The existing dashboard calls the incident list and the webhook posts events. Preserve those routes and the tenant/role headers. The new response binds an accepted event to the current incident projection so a late event can report the state after the complete ledger fold. The browser uses the final folded sequence when it submits an operator action and fetches rows and counts together for the same filters.

The event ledger, policy revisions and on-call intervals are authoritative persisted data. Incidents and fake outbox entries are projections. Each event insert occurs in a transaction that validates the full tenant/incident history in sequence and event-ID order. An invalid late insert rolls back without changing the ledger, incident or outbox. A replay is compared on canonical fields before any write. A new opening generation creates one outbox entry. Acknowledge or resolve cancels its work; reopening creates another generation. Configuration changes recalculate due time and assignee on pending entries. Existing cancelled generations remain cancelled.

The storage module owns schema migration and replay; the API module owns identity, method and input validation; the TypeScript API and view modules keep network effects apart from DOM rendering. The starter's basic incident list and filters remain usable. A database created by the starter acquires the added projection sequence and configuration tables, then replays valid event history. A corrupt legacy ledger causes a visible startup failure rather than a silent rewrite. External qualification must exercise the compiled Go API, SQLite restart, actual browser network responses and the separately defined performance workload. Native read-only source checks cannot establish those behaviors.
