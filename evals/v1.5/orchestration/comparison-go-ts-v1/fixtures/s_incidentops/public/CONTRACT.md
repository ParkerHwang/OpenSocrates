# IncidentOps change request (synthetic)

This is a local exercise. The Go API and TypeScript dashboard in `starter/` already list incidents and ingest basic events. Keep useful behavior and implement the change below. No real notification is sent: `outbox` is a queryable local table only. Use the supplied Go/TypeScript stack. Preserve SQLite WAL mode and `synchronous=FULL`. `GET /api/health` reports the active connection's `{status:"ok",journal_mode:"wal",synchronous:2}` so durability can be checked without relying on a new connection's defaults. All timestamps are UTC RFC3339; reject malformed timestamps. Each request declares `X-Tenant` and `X-Role` (`operator` or `viewer`); blank or unknown values are rejected. A viewer may read only its tenant and cannot mutate any data. A tenant name is an opaque case-sensitive key.

## Event and incident contract

`POST /api/events` accepts `{event_id,incident_id,sequence,kind,occurred_at,severity,note}`. `kind` is `OPEN`, `ACK`, `RESOLVE`, or `REOPEN`. `sequence` is a positive integer per tenant/incident. `severity` is `P1`, `P2`, or `P3` for `OPEN` and `REOPEN`, and may be omitted otherwise. `note` is optional text. A new accepted event returns HTTP 201; exact replay of the same tenant/event ID and canonical JSON fields returns 200 and changes nothing; reuse of that ID with different content returns 409 and changes nothing. The same ID in a different tenant is independent. Invalid transitions return 422 without changing persisted state. The response identifies the current derived incident state. Events may arrive out of sequence. The authoritative state is the fold of all accepted events in ascending sequence, then event ID. Validate the *entire resulting ledger* before committing a late insertion; if the new fold contains any invalid transition, reject the insertion atomically with 422. A valid late insertion can alter history but must not regress the current state or duplicate current side effects. `OPEN` begins a new incident; `ACK` requires open; `RESOLVE` requires open or acknowledged; `REOPEN` requires resolved. `REOPEN` starts a new notification generation. Incidents are isolated by tenant. A process restart from the same database path preserves events, incidents, configuration, and outbox state.

`GET /api/incidents` returns `{items:[...]}` in descending latest-event time, then ascending incident ID. Each item includes `incident_id,status,severity,latest_at,note,sequence`, where sequence is the final folded event's sequence and lets the UI submit the next action. Latest-event time means the `occurred_at` of the final event in fold order, not the maximum timestamp among the incident's records. Optional `status`, `severity`, and `q` filters apply; `q` searches incident ID and current note case-insensitively. `GET /api/summary` returns `{total,open,acknowledged,resolved}` counts derived from the current filtered incident result set, including zero counts, never a separately maintained counter. Both endpoints honor exactly the same query filters. `GET /api/outbox` returns `{items:[{incident_id,generation,due_at,assignee,state},...]}` for only the caller tenant's fake entries, sorted by incident ID and generation. New and replayed event responses return `{incident:{incident_id,status,severity,latest_at,note,sequence},duplicate:boolean}`. Do not contact an external service.

## Escalation configuration and effects

`POST /api/policies` with `{effective_at,severity,delay_minutes}` appends a tenant policy revision. `delay_minutes` is an integer from 0 to 1440. For a generation opened at time T, use the policy of matching severity with the greatest `effective_at <= T`; if tied, the most recently accepted revision wins. A later revision may decrease the delay, so do not select by numeric maximum. If no revision is effective, use 60 minutes. `POST /api/oncall` with `{starts_at,ends_at,person}` appends a tenant handover interval (`starts_at < ends_at`). For due time D, select the overlapping interval with latest `starts_at`; if tied, latest accepted revision wins. No match yields `unassigned`. These configuration endpoints require `operator` and return 201. The outbox records one entry per incident generation with due time, assignee, and state `pending` or `cancelled`. An `ACK` or `RESOLVE` cancels obsolete pending work. Reopening creates the next generation and its own entry. A late event or configuration revision reconciles pending effects deterministically without creating duplicate rows. Existing cancelled generations stay cancelled.

## Dashboard and delivery

The dashboard uses the real API, presents incident rows and a visible `Summary` heading with filtered counts, and shows a clear error for rejected actions. Keep visible, accessible control labels `Tenant`, `Role`, `Status`, `Severity`, and `Search`, plus accessible action names `ACK`, `RESOLVE`, and `REOPEN` where those actions apply; these are user-facing affordances, not CSS or DOM selectors. A viewer can inspect but cannot trigger writes; hiding or disabling viewer write controls are both valid. Changing filters refreshes both rows and counts from the network. Buttons inside forms must not accidentally submit/reload. Provide a useful mobile layout. Supply `design.json` plus `design.md` for the first unit: document current callers, public API and schemas, persisted versus derived fields, migration and compatibility intent, state transitions, ownership, and executable contract examples. The second unit supplies implementation files, meaningful tests and a runbook. The first unit's accepted contract governs the second.

Public native acceptance is limited to well-formed source and declarative contract examples that can run read-only. Final integration acceptance separately compiles Go/TypeScript, exercises API and SQLite persistence in disposable copies, and checks browser behavior and performance over loopback. No native read-only result proves server, browser, restart, or throughput behavior.
