# Architecture and invariants

The Python HTTP server serves `static/` at `/` and JSON routes under `/api`. SQLite in `DATA_DIR` is the sole state store. The tenant ID in every domain query comes from the authenticated user's database row, never from a client header or payload. Order IDs are global integers, but lookup always includes tenant ID; a different tenant's ID returns 404. Viewers can read but fail authorization before a mutation or idempotency replay. Stock adjustments require admin; operators and admins can change orders.

Inventory stores `on_hand`, `reserved`, catalog price, and a version for each `(tenant, sku)`. Database checks enforce `0 <= reserved <= on_hand`, nonnegative prices, and positive versions. Available stock is computed as `on_hand - reserved`. A draft stores immutable SKU, quantity, and server catalog unit-price snapshots. The order total is the sum of those snapshots, so a valid SAMPLE-only order totals zero. A unique `(tenant, client_ref)` index prevents duplicate references.

Each mutation starts `BEGIN IMMEDIATE`, which obtains SQLite's single-writer lock before reading mutable state. The transaction checks the tenant-scoped idempotency key, validates the payload and expected version, changes the order/stock, inserts exactly one audit event, stores the successful response, and commits. Any rejection rolls the transaction back, including the idempotency key. A matching retry returns the stored status and body. Its fingerprint covers method, path, and canonical JSON payload; a changed use of the same key returns 409. Authentication and role checks occur before looking up the key. Concurrent writers therefore cannot both consume the same available units or produce duplicate effects for one key. The idempotency table is persistent across restarts.

Reservation validates available units for **every** line before updating any, and the transaction makes the multi-line change atomic. Shipping subtracts each shipped quantity from both `on_hand` and `reserved`, leaving `available` unchanged at that instant. Cancelling a reservation releases it. Returns add received units to `on_hand` and each line's returned count; they cannot exceed shipped quantities. The status remains `shipped` until every line is fully returned, when it becomes `returned`. Every successful state transition increments the order version once, and every affected inventory row increments its version once. Stock adjustment also uses a required expected inventory version. JSON booleans and fractions do not pass integer validation.

Order pagination sorts by increasing order ID. The first filtered request captures the IDs of all matching orders in a persisted snapshot when multiple pages are needed. Signed cursors identify that snapshot and an offset; subsequent pages retain original membership even if status changes or new orders arrive. Current order details are returned for those IDs. Audit entries are append-only, so signed cursors use an ID high-water mark. Cursors are tied to filters and cannot be altered without the database-held HMAC secret. Dashboard totals and status counts are queried from committed tenant rows. Order snapshots remain in this local database until the store is removed; a production system would add retention or garbage collection.

Authentication uses salted PBKDF2-HMAC-SHA256 password hashes and random bearer tokens whose hashes are stored in SQLite. The UI keeps the token in `sessionStorage` and clears it on logout. This is an intentionally local demo authentication model with no token expiry or revocation route. All API errors use `{ "error": { "code": "...", "message": "..." } }`. Bad credentials or tokens return 401; forbidden roles return 403; a missing or foreign order returns 404; invalid payloads/filters/cursors return 400; stale versions, stock shortages, invalid transitions, over-returns, reference conflicts, and key conflicts return 409. Unexpected server failures return a generic 500 body.

The frontend reuses one API helper for authentication, JSON parsing, and errors, and one mutation wrapper for pending state and retry keys. It refreshes affected views after successful changes. On a stale version it keeps the entered form and shows a refresh instruction. Dynamic client references and other untrusted values are rendered with `textContent`, never interpolated into HTML. Forms use labels, native selects and inputs, and keyboard-operable buttons. Tables scroll horizontally on narrow screens.
