# DepotFlow

DepotFlow is a locally runnable, two-tenant fulfillment console. It supports
receiving orders, atomic reservations, shipping, cancellation, returns, stock
adjustments, tenant-scoped audit history, and a small responsive browser UI.

## Run it

Requirements: Python 3.10 or newer. The service uses only the Python standard
library; no package install, container, account, or external database is
needed.

```sh
./setup.sh
PORT=8000 DATA_DIR=./data SEED_DEMO=1 ./run.sh
```

`run.sh` binds only to `127.0.0.1`. `PORT` defaults to `8000`, and `DATA_DIR`
defaults to `./data`. `SEED_DEMO=1` seeds an empty database only. Starting
again with the same data directory does not reset stock, orders, sessions, or
idempotency records.

Open <http://127.0.0.1:8000/>. The UI and `/api` JSON endpoints are served by
the same process and origin.

Demo users all use the local synthetic password `DepotDemo!2026`:

| Tenant | Admin | Operator | Viewer |
| --- | --- | --- | --- |
| north | `admin@north.example` | `operator@north.example` | `viewer@north.example` |
| south | `admin@south.example` | `operator@south.example` | `viewer@south.example` |

Each tenant is seeded independently with BOLT (100 units, 1250 cents), CABLE
(60 units, 2499 cents), and SAMPLE (20 units, 0 cents).

## Chosen stack and design

`server.py` is a small `ThreadingHTTPServer` application using SQLite in the
configured data directory. SQLite WAL mode permits concurrent readers; every
mutation uses a per-request connection and `BEGIN IMMEDIATE`, so the complete
order transition, inventory changes, audit event, and idempotency record commit
or roll back together. Inventory uses integer units, cents, and optimistic
versions. `order_no` and audit IDs provide stable oldest-first pagination.

The UI is semantic HTML generated by `static/app.js`, with no frontend
framework or build step. It uses `textContent`/DOM nodes for dynamic values,
disables in-flight mutation buttons, retains form input after errors, and hides
all writable controls for viewers. `static/styles.css` includes narrow-width
layout rules and scrollable data tables.

The main trade-off is simplicity and reproducibility over horizontal write
scaling. SQLite is a good fit for a local two-operator deployment, but the
single-writer transaction boundary intentionally serializes mutation traffic.
This is a local demo/assessment application rather than a production identity,
TLS, rate-limiting, backup, or multi-process deployment solution.

## API and authorization notes

`POST /api/session` returns `{token,user:{email,role,tenant}}`; bearer tokens
are persisted in SQLite so they remain usable after a restart. `GET /api/me`
returns `{email,role,tenant}`. All other API routes require a valid bearer
token except `GET /api/health`, which returns `{"status":"ok"}`.

Admin-only stock adjustments and operator/admin order mutations require a
non-empty `Idempotency-Key`. Keys are tenant scoped and persist in SQLite.
After authentication and role checks, an exact method/path/canonical-JSON
replay returns the original status and body. A changed request with the same
key is a 409, while failed requests do not consume their key. Tenant filters
are applied in every object lookup and list query; another tenant's order is
reported as 404.

Mutation errors use the form:

```json
{"error":{"code":"stale_version","message":"order version is stale"}}
```

The implementation covers the documented inventory, order, pagination, audit,
dashboard, retry, and state-transition routes in `server.py`.

## Verification commands and observed results

The integration tests start real local servers against temporary SQLite files
and exercise HTTP routes, rather than only calling internal functions:

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Observed on 2026-09-27: **5 tests passed in 0.81 seconds**. The checks cover
health/authentication, role and tenant isolation, validation, server-side
pricing including a zero-price SAMPLE order, atomic multi-line reservation
failure, concurrent reservation, concurrent identical idempotency replay,
stale versions, partial/full returns, failed-key reuse, pagination, and a
restart with durable replay and state.

The browser exercise uses the supplied headless Chromium WebSocket. Start a
seeded server, then run:

```sh
DEPOTFLOW_URL=http://127.0.0.1:8000 node tests/browser_smoke.js
```

Observed: the workflow passed for login, inventory, multi-line order creation,
reserve, ship, partial return, audit, viewer control suppression, all required
`data-testid` markers, and a 375px viewport with no horizontal overflow.

The repeatable HTTP workload is:

```sh
python3 load_test.py --base-url http://127.0.0.1:8000 \
  --read-count 200 --write-count 50 --concurrency 8
```

Observed on the supplied arm64 Darwin host (`Python 3.12.14`, 8 worker
threads, one seeded local SQLite process, 200 reads split among inventory,
dashboard, and order-list routes plus 50 unique SAMPLE-order creates):

| Workload | Requests | Successes | Errors | Throughput | Mean | p50 | p95 | Max |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Reads | 200 | 200 | 0 | 1379.83 req/s | 3.905 ms | 3.912 ms | 5.085 ms | 6.021 ms |
| Writes | 50 | 50 | 0 | 344.96 req/s | 5.204 ms | 1.989 ms | 23.279 ms | 39.370 ms |

These are one small local run, not a capacity guarantee. The driver measures
request completion from Python clients and does not include TLS, network hops,
multiple processes, large datasets, or production contention. SQLite writer
serialization is the main known scaling limit.

## Files

- `server.py` — HTTP service, schema, seed data, auth, transactions, and APIs.
- `static/` — responsive same-origin UI.
- `tests/test_api.py` — route-level integration tests.
- `tests/browser_smoke.js` — Playwright browser workflow.
- `load_test.py` — reproducible local read/write measurement.
- `architecture.md` — invariants, transaction boundaries, auth, reuse, and errors.
